# S3 Access Logs

Registra los accesos a un bucket. Arquitectura: un **source bucket** (el que recibe los accesos que queremos loguear) y un **target bucket** (donde se depositan los logs).

**Cómo se habilita y funciona:**

- Se habilita el logging **en el source bucket**, vía consola o vía **PUT Bucket logging** (CLI/API).
- El proceso lo administra el **S3 Log Delivery Group**, un sistema que lee la configuración de logging del source.
- Es un proceso **best-effort**: habilitar la función o cambiar la configuración puede tardar **unas horas** en surtir efecto, y los accesos suelen aparecer en el target **dentro de algunas horas**.


**Formato de los logs:**

- Se entregan como **log files**, compuestos de **log records** delimitados por **newlines**.
- Cada record tiene atributos **delimitados por espacios**: fecha/hora, requester, operación, status code, error code, etc.

Cada record incluye información bastante detallada de cada acceso: quién lo hizo (la identidad o "anónimo"), la IP de origen, la operación (`REST.GET.OBJECT`), la key, el código de respuesta HTTP, el tamaño, el tiempo que tardó, y más. Es el registro para responder "quién accedió a qué objeto y cuándo" a nivel de request individual.

**Consideraciones:**

- Un mismo **target bucket puede servir a muchos source buckets**, separando los logs por **prefijos**.
- **El lifecycle de los archivos de log NO está integrado en el producto**: administrar/expirar los logs viejos es responsabilidad tuya (típicamente, con una lifecycle configuration en el target bucket — se conecta con lo que vimos arriba).

Ese último punto importa más de lo que parece: un bucket con logging activado y mucho tráfico genera **una cantidad enorme de archivos de log**, que crecen para siempre si nadie los limpia. La combinación estándar es apuntar los logs a un target dedicado y ponerle una lifecycle rule que los mueva a Glacier o los expire después de X días. Si no, los logs terminan costando más que los datos que auditan.

### Access Logs vs. CloudTrail para S3

Las dos cosas registran accesos a S3 y se confunden. La diferencia:

| |**S3 Server Access Logs**|**CloudTrail (data events)**|
|---|---|---|
|Dónde caen|En un bucket de S3, como archivos de texto|En CloudTrail (y opcionalmente S3/CloudWatch Logs)|
|Formato|Texto plano delimitado por espacios|JSON estructurado|
|Latencia|Horas (best-effort)|Minutos|
|Detalle|Muy completo a nivel HTTP|Completo a nivel de API, con identidad IAM clara|
|Costo|Solo el almacenamiento de los logs|Se cobra por data event|
|Integración|Hay que parsear el texto|Se integra con EventBridge, Athena, alertas|

La regla práctica: para **auditoría de seguridad** con identidad clara, alertas y consultas, **CloudTrail data events**. Para un **registro de acceso completo y barato** al estilo log de servidor web (analítica de tráfico, por ejemplo), **Server Access Logs**. No son excluyentes; en entornos serios se usan las dos para fines distintos.
