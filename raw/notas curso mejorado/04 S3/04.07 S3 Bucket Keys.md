# S3 Bucket Keys

### El problema

Con SSE-KMS, **cada PUT de objeto genera una llamada de S3 a KMS** para obtener una DEK única. Para 1, 2, 3 objetos, perfecto. Pero:

- Las llamadas a KMS **cuestan dinero**.
- KMS tiene **límites de throttling**: **5.500, 10.000 o 50.000 requests por segundo** según la region.

Con miles de objetos por segundo, una sola KMS Key se convierte en un **cuello de botella de escalabilidad** (y una factura de KMS considerable).


Para dimensionar el problema: una aplicación que sube 10.000 objetos por segundo genera 10.000 llamadas a KMS por segundo solo para cifrar. Eso choca de frente con el límite de la region y, aunque no lo chocara, cada bloque de 10.000 llamadas se factura. La cuenta de KMS puede terminar siendo más cara que el propio almacenamiento en S3.
### La solución

Con **bucket keys**, la arquitectura es la misma, pero en lugar de usar la KMS Key para generar **una DEK por objeto**, se usa para generar una **bucket key de tiempo limitado**. Esa bucket key vive dentro de S3 durante un período breve, y **S3 la usa para generar las DEKs localmente**, sin llamar a KMS por cada objeto.

Resultado: el trabajo se **transfiere de KMS a S3** → muchas menos llamadas a la API de KMS → **menor costo y mayor escalabilidad**.

La reducción es enorme: AWS habla de hasta un **99% menos de llamadas a KMS**. En vez de una llamada por objeto, se hace una llamada cada tanto para renovar la bucket key, y con esa clave intermedia S3 fabrica todas las DEKs que necesite sin volver a molestar a KMS.

> [!warning] No es retroactivo Habilitar bucket keys **solo afecta a los objetos subidos después** de activarlo en el bucket. Los objetos existentes conservan su cifrado tal cual estaba.

### Consideraciones

- **CloudTrail cambia**: los eventos de KMS ahora muestran el **ARN del bucket** en lugar del ARN de cada objeto. Y verás **muchos menos eventos de KMS** (y proporcionalmente más de S3) — lógico: se llama a KMS una vez por bucket key, no una vez por objeto. Si tu auditoría dependía de ver una llamada KMS por objeto, esto la cambia.
- **Funciona con replicación** (same-region y cross-region): al replicar un objeto cifrado, la configuración de cifrado del objeto **se mantiene**.

**El punto del ETAG (caso especial de replicación)**: si replicás un objeto que estaba en **plaintext** (sin cifrar, en un bucket de origen viejo) hacia un bucket **con bucket keys habilitadas**, el objeto **se cifra recién en el destino**.

La consecuencia: **el ETAG cambia** entre origen y destino. El ETAG es un identificador del contenido del objeto (relacionado con el hash de sus bytes); como en destino el objeto ya no son los mismos bytes (ahora está cifrado), el ETAG no puede ser el mismo. Importa si tenés herramientas que comparan ETAGs entre origen y destino para verificar que la réplica esté "igual" — van a reportar diferencia aunque la réplica sea correcta.

Conviene saber qué es el ETAG más allá de este caso, porque tiene otra trampa: para un objeto subido de una sola vez, el ETAG **es** el MD5 del contenido. Pero para un objeto subido con **multipart upload**, el ETAG **no es el MD5 del archivo completo** — es un hash de los hashes de las partes, con un sufijo que indica cuántas partes fueron (`-N`). Por eso comparar el ETAG de un objeto multipart contra el MD5 del archivo original **siempre da distinto**, aunque el contenido sea idéntico. Es una fuente clásica de confusión al verificar integridad.

**Cuándo activar Bucket Keys**: prácticamente siempre que se use SSE-KMS con volumen medio o alto. No tiene contras relevantes más allá del cambio en los logs de CloudTrail, y el ahorro es grande. La única razón para no activarlo sería que necesitaras auditar en KMS cada operación objeto por objeto, cosa poco común.
