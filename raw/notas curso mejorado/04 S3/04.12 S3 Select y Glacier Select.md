# S3 Select y Glacier Select

_(No hace falta entender la implementación, solo la arquitectura.)_

Son formas de **recuperar partes de un objeto** en lugar del objeto completo.

**El problema:** S3 almacena objetos de hasta **5TB**. Si necesitás consultar datos dentro de un objeto de 5TB, la operación normal te baja **los 5TB completos** — y filtrar del lado del cliente es tarde: ya te descargaste 5TB de videos de Juego de Tronos. 📺

**La solución:** S3 Select y Glacier Select permiten enviar una **expresión estilo SQL** (un SQL reducido) que se ejecuta **del lado del servicio (S3)**. S3 filtra y te entrega **solo los datos pre-filtrados**.

- Formatos soportados: **CSV, JSON, Parquet, compresión BZIP2**, entre otros.
- Resultado: hasta **400% más rápido** y **80% más barato** — porque S3 factura por lo que _entrega_, y ahora entrega solo lo filtrado.
- 
La diferencia en una línea: **filtrás del lado del servidor (S3) en lugar del lado del cliente (la app)**. Como arquitecto, esta feature mejora la performance de todo el sistema.

Vale aclarar el alcance de ese "SQL", porque es donde la gente sobreestima la herramienta: S3 Select opera sobre **un solo objeto a la vez** y soporta un subconjunto muy acotado de SQL — básicamente `SELECT ... FROM S3Object WHERE ...`. No hace JOINs, no agrupa entre varios archivos, no es una base de datos. Es un filtro de filas y columnas sobre un archivo. Si necesitás consultar **muchos** objetos a la vez, con SQL completo, la herramienta correcta es **Amazon Athena**, no S3 Select. Esa distinción (Select = un objeto, filtro simple; Athena = muchos objetos, SQL completo) es lo que suele preguntarse.

El ahorro sale de dónde se hace el trabajo: sin Select, S3 te manda el archivo entero y tu aplicación gasta ancho de banda, tiempo y CPU en descartar el 95%. Con Select, ese descarte ocurre dentro de S3 y solo viaja por la red lo que realmente te interesa. Menos transferencia = menos costo y menos latencia.
