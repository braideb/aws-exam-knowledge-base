# S3 Static Website Hosting

El **static hosting** hace a S3 infinitamente más útil: permite acceso vía **HTTP estándar** desde un navegador. Sirve para hospedar casi cualquier cosa estática — un blog, documentación, una landing page.

La palabra clave es **estático**: S3 sirve archivos tal cual están (HTML, CSS, JS, imágenes). **No ejecuta código del lado del servidor** — nada de PHP, Node ni bases de datos. La lógica dinámica, si la hay, corre en el navegador del cliente (JavaScript) llamando a APIs externas. Si el escenario necesita procesamiento del lado del servidor, S3 static hosting no alcanza.

### Cómo funciona
Al habilitarlo hay que definir dos documentos:

|Documento|Cuándo se sirve|
|---|---|
|**Index document**|Cuando el visitante no pide una página específica (ej: entra a `misitio.com` a secas). Es el **punto de entrada** del sitio.|
|**Error document**|Cuando algo sale mal (ej: piden `pagina-que-no-existe.html` → 404).|

Si pedís una página puntual (`loquesea.html`), obtenés esa página. Si no pedís nada, obtenés el index.

Al habilitar el hosting, S3 crea un **website endpoint**: una URL propia del sitio, con un formato tipo `bucket-name.s3-website-region.amazonaws.com`. El nombre lo genera AWS en base al nombre del bucket y la region — no es personalizable directamente.

Conviene no confundir los **dos endpoints** que puede tener un bucket, porque se comportan distinto:

|Endpoint|Formato|Comportamiento|
|---|---|---|
|**REST API endpoint**|`bucket.s3.region.amazonaws.com`|El endpoint "normal" de S3. Devuelve objetos, respeta permisos por objeto, respuestas en XML ante errores.|
|**Website endpoint**|`bucket.s3-website-region.amazonaws.com`|El de static hosting. Aplica index y error document, sirve HTML de error amigable. **No soporta HTTPS.**|

Ese último punto es una limitación importante: **el website endpoint solo habla HTTP, no HTTPS**. Para servir un sitio estático con HTTPS (que hoy es obligatorio en la práctica) hay que poner **CloudFront delante**, que además agrega caché y un dominio propio con certificado. Es el patrón estándar y aparece seguido en el examen: "sitio estático en S3 con HTTPS" → CloudFront + S3.

### El nombre del bucket importa (custom domain)

**Custom domain via R53 → BUCKET NAME MATTERS.** Si querés usar un dominio propio (ej: `milanuncios.com`) apuntando al sitio con Route 53, **el nombre del bucket tiene que coincidir exactamente con el nombre del dominio** (bucket llamado `milanuncios.com`). Si el bucket se llama otra cosa, el alias de R53 no puede resolverlo. Por eso "bucket name matters": si planeás un sitio con dominio propio, el nombre del bucket no es una decisión libre — y más te vale que nadie más lo haya registrado, porque los nombres son únicos a nivel global.

La razón técnica: cuando un navegador pide `milanuncios.com`, ese nombre viaja en la cabecera `Host` de la petición HTTP. S3 usa esa cabecera para decidir a qué bucket enrutar. Si no existe un bucket llamado exactamente así, S3 no sabe qué servir. Por eso el nombre del bucket y el dominio tienen que ser idénticos.

### Casos de uso típicos
- **Offloading**: servir los assets estáticos (imágenes, videos, CSS, JS) desde S3 para descargarle ese trabajo a los servidores de la aplicación. El servidor de la app se dedica a generar HTML dinámico; S3 mueve los bytes pesados. Esto abarata y acelera, porque S3 escala solo y el egress puede ir por CloudFront.
- **Out-of-band pages**: páginas de mantenimiento o de estado servidas desde S3, para que sigan funcionando aunque tu infraestructura principal esté caída. Justamente porque S3 no depende de tus servidores, es el lugar ideal para la página que dice "estamos en mantenimiento".

### Costos y detalle práctico

El modelo de costo es el de siempre en S3: se paga el almacenamiento, las requests y la transferencia de salida. Para un sitio estático de tráfico bajo o medio, suele salir **centavos por mes**, muchísimo menos que mantener un servidor web encendido. Es una de las formas más baratas que existen de tener un sitio online.

Para que el sitio sea accesible públicamente hay que abrir dos cosas a la vez: **desactivar Block Public Access** en el bucket y poner una **bucket policy** que permita `s3:GetObject` a `Principal: "*"`. Con una sola de las dos no alcanza — es la causa número uno de "configuré el hosting y me da 403".
