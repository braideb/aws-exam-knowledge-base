# CORS (Cross-Origin Resource Sharing)

Función de seguridad **de los navegadores** que aparece en varios productos de AWS.

Lo primero y más importante para el examen: **CORS es una cosa del navegador, no de AWS**. La restricción la impone el navegador del usuario, no S3. Un script del lado del servidor, o `curl`, o Postman, ignoran CORS por completo — pueden pedir lo que quieran. CORS solo entra en juego cuando **código JavaScript corriendo en una página web** intenta pedir un recurso de otro origen. Entender esto evita la confusión más común del tema.
### Same-origin vs. cross-origin

Ejemplo del curso (app **Catagram**):

1. El navegador llama a `catagram.io` y obtiene `index.html` — esa **primera solicitud define el ORIGIN**.
2. `index.html` referencia `serverless.js` y `catagram.png`, **en el mismo dominio** → **same-origin requests** → **siempre permitidas**.
3. Pero la app también llama a una **API Gateway** (dominio `...amazonaws.com`) y carga `casper_and_pixel.png` desde **otro bucket** (`catagram-img.io`) → **cross-origin requests**, porque van a **dominios distintos del origin**.

![[Pasted image 20260717161506.png]]

Conviene precisar qué es un "origin", porque es más estricto de lo que parece: un origin es la combinación de **esquema + dominio + puerto**. `http://catagram.io` y `https://catagram.io` son orígenes **distintos** (cambia el esquema). `catagram.io` y `www.catagram.io` son distintos (cambia el dominio). `catagram.io` y `catagram.io:8080` son distintos (cambia el puerto). Basta que uno de los tres difiera para que sea cross-origin.

> [!important] La regla Las **cross-origin requests están restringidas por defecto** por el navegador. Para que funcionen, **los OTROS orígenes** (no el original) deben declarar mediante su **configuración de CORS** que aceptan solicitudes desde tu origin. En el ejemplo: hay que configurar CORS en `catagram-img.io` **y** en la API Gateway — si no, alertas de seguridad y fallos en la app. Tu origin original siempre te permite conexiones (es el primer origen al que fuiste); son _los demás_ los que tienen que aprobarte.


Por qué existe todo esto: la política de **same-origin** es una defensa del navegador contra un ataque real. Sin ella, una página maliciosa que abrís podría, con el JavaScript corriendo en tu navegador, hacer requests a tu banco aprovechando tu sesión abierta y robar datos. Same-origin bloquea eso por defecto: el JS de un sitio no puede leer respuestas de otro dominio. CORS es el mecanismo **controlado** para hacer excepciones cuando el dueño del otro dominio da permiso explícito.
### Configuración de CORS en S3

Se define en **JSON** (históricamente se podía en XML; AWS ahora requiere JSON). Ejemplo de la lección, con **dos reglas**:

![[Pasted image 20260717162051.png]]


```json
[
  {
    "AllowedHeaders": ["*"],
    "AllowedMethods": ["PUT", "POST", "DELETE"],
    "AllowedOrigins": ["http://catagram.io"],
    "ExposeHeaders": []
  },
  {
    "AllowedHeaders": [],
    "AllowedMethods": ["GET"],
    "AllowedOrigins": ["*"],
    "ExposeHeaders": []
  }
]
```

- Regla 1: permite **PUT, POST y DELETE** solo desde `catagram.io`.
- Regla 2: permite **GET desde cualquier origen** (`*` = comodín).
- Las reglas se procesan **en orden** y se aplica **la primera que coincide**.

> [!warning] No son permisos La configuración de CORS **NO son permisos de AWS** (la slide lo remarca: _"these AREN'T permissions"_). CORS le dice **al navegador** qué solicitudes cross-origin están permitidas; los permisos reales sobre el bucket los siguen definiendo las bucket policies / IAM. Necesitás **ambas cosas**: que CORS permita y que los permisos permitan.

### Simple requests vs. preflight

Dos tipos de solicitud cross-origin:

|Tipo|Cómo funciona|
|---|---|
|**Simple request**|Va **directo** al otro origen. Mientras ese origen tenga CORS configurado para permitir tu origin, funciona sin nada especial. (Qué califica como "simple" lo define la spec — link abajo.)|
|**Preflight / preflighted request**|Para cualquier cosa **más complicada** que una simple request, el navegador **primero manda una solicitud HTTP de verificación** (el _preflight_, un `OPTIONS`) al otro origen para determinar si la solicitud real es **segura de enviar**. Solo si el preflight aprueba, se manda la solicitud real.|
Qué hace que una request sea "simple" (y por tanto no dispare preflight): a grandes rasgos, que use solo métodos `GET`, `HEAD` o `POST`, y solo con headers y tipos de contenido básicos. En cuanto la request usa `PUT`, `DELETE`, o headers custom como `Authorization` con ciertos formatos, deja de ser simple y el navegador hace preflight primero. Por eso los `GET` de imágenes suelen "simplemente funcionar" con CORS mínimo, mientras que los `PUT` de subida casi siempre disparan el `OPTIONS` de preflight.
### Los headers de CORS explicados

> [!note] Estos son los cuatro headers que el otro origen devuelve en su respuesta (al preflight o a la simple request) y que **le indican al navegador qué está permitido**:
> 
> |Header|Qué le dice al navegador|
> |---|---|
> |**`Access-Control-Allow-Origin`**|Desde **qué orígenes** se aceptan solicitudes. Puede ser un dominio concreto (`http://catagram.io`) o `*` (cualquiera). Si tu origin no está acá, el navegador **bloquea la respuesta**. Es el header central de CORS.|
> |**`Access-Control-Allow-Methods`**|Qué **métodos HTTP** están permitidos cross-origin (GET, PUT, POST, DELETE...). Corresponde a `AllowedMethods` del JSON de S3.|
> |**`Access-Control-Allow-Headers`**|Qué **headers custom** puede incluir la solicitud (ej: `Content-Type`, `Authorization`). Corresponde a `AllowedHeaders`. Si tu solicitud lleva un header no listado, el preflight falla.|
> |**`Access-Control-Max-Age`**|Cuántos **segundos puede cachear el navegador el resultado del preflight**. Con esto, el navegador no repite el preflight en cada solicitud — hace uno, lo cachea, y durante ese tiempo manda las solicitudes reales directo. Es una optimización de performance.|
> 
> **El flujo completo con preflight:** el navegador manda `OPTIONS` preguntando "quiero hacer un PUT con estos headers desde catagram.io, ¿puedo?" → el servidor responde con los `Access-Control-*` de arriba → si todo coincide, el navegador manda el PUT real → y cachea el permiso por `Max-Age` segundos.

**El flujo completo con preflight:** el navegador manda `OPTIONS` preguntando "quiero hacer un PUT con estos headers desde catagram.io, ¿puedo?" → el servidor responde con los `Access-Control-*` de arriba → si todo coincide, el navegador manda el PUT real → y cachea el permiso por `Max-Age` segundos.

Un quinto header que conviene conocer es **`Access-Control-Allow-Credentials`**, que indica si la request puede llevar cookies o credenciales. Tiene una restricción de seguridad importante: **no se puede combinar `Allow-Credentials: true` con `Allow-Origin: *`**. Si la request lleva credenciales, el servidor está obligado a nombrar un origin específico, no el comodín. Es una defensa para que un sitio no pueda hacer requests autenticadas a cualquier lado.

### Cómo se reconoce un problema de CORS

En la práctica, un error de CORS tiene una firma inconfundible: la consola del navegador muestra un mensaje del tipo "_blocked by CORS policy: No 'Access-Control-Allow-Origin' header_", y en la pestaña de red se ve una request `OPTIONS` que falló **antes** de la request real. El síntoma clásico: la app funciona si abrís el recurso directo en el navegador (eso es same-origin), pero falla cuando el JavaScript intenta cargarlo (eso es cross-origin). Si ves ese patrón, es CORS, no permisos.
