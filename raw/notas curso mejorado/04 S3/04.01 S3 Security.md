# S3 Security

**S3 es privado por defecto.** Inicialmente, la única identidad con acceso al bucket es el **account root user** de la cuenta propietaria. Cualquier otro permiso tiene que ser concedido explícitamente.

### Resource Policies vs. Identity Policies

La primera forma de conceder acceso es la **bucket policy**, que es un tipo de **resource policy**: como una identity policy, pero **vinculada al recurso** (el bucket) en lugar de a la identidad.

La diferencia es la **perspectiva**:

|Tipo|Pregunta que responde|Se adjunta a|
|---|---|---|
|**Identity policy**|¿Qué puede hacer **esta identidad**?|Un user, group o role|
|**Resource policy**|¿Quién puede acceder a **este recurso**?|El recurso (el bucket)|

Diferencias clave de las resource policies:

- Las identity policies solo pueden administrarse **dentro de la propia cuenta**. No podés adjuntarle una identity policy a un usuario de otra cuenta. Las resource policies, en cambio, permiten **Allow/Deny a identidades de la misma o de otras cuentas**, porque la policy vive pegada al recurso.
- Las resource policies permiten **Allow/Deny a principals anónimos** — es decir, acceso sin autenticar. Una identity policy jamás puede hacer eso, porque por definición necesita una identidad a la cual adjuntarse.

### El campo `Principal`

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicRead",
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject"],
      "Resource": ["arn:aws:s3:::secretcatproject/*"]
    }
  ]
}
```

La gran diferencia estructural con una identity policy es el campo **`Principal`**, que define **a quién afecta** la policy.

> [!tip] Truco de identificación rápida ¿La policy tiene campo `Principal`? → es una **resource policy**. ¿No lo tiene? → es una **identity policy** (el principal está implícito: es la identidad a la que está adjunta).

En el ejemplo, `"Principal": "*"` significa que aplica a **cualquiera**, incluidos anónimos: eso hace al bucket públicamente legible.

### Bucket policies con condiciones

Las bucket policies soportan **`Condition`**, lo que permite lógica más fina.

**Ejemplo 1 — Bloquear todo excepto una IP:**
```json
{
  "Version": "2012-10-17",
  "Id": "BlockUnLeet",
  "Statement": [
    {
      "Sid": "IPAllow",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "arn:aws:s3:::secretcatproject/*",
      "Condition": {
        "NotIpAddress": {"aws:SourceIp": "1.3.3.7/32"}
      }
    }
  ]
}
```

Se **deniega** el acceso a cualquier objeto de `secretcatproject` **a menos que** la solicitud venga de la IP `1.3.3.7`. Leelo así: "Deny a todos, condición: cuando la IP **no** es 1.3.3.7".

**Ejemplo 2 — Exigir MFA para un prefijo:**
```json
{
  "Version": "2012-10-17",
  "Id": "protectboris",
  "Statement": [
    {
      "Sid": "",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": "arn:aws:s3:::secretcatproject/boris/*",
      "Condition": { "Null": { "aws:MultiFactorAuthAge": true } }
    },
    {
      "Sid": "therest",
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::secretcatproject/*"
    }
  ]
}
```

- **Statement 1**: deniega todo acceso al prefijo `boris/` (una "carpeta lógica") **si la identidad no está usando MFA**. La condición `"Null": {"aws:MultiFactorAuthAge": true}` significa "la clave MFA no existe en la request" = no se autenticó con MFA.
- **Statement 2**: permite lectura (`GetObject`) de **todo el bucket**.

¿Y `boris/*` no queda cubierto por el Allow del statement 2? Sí, pero como ya sabemos de IAM: **un explicit DENY siempre le gana a un explicit ALLOW**. Resultado: todo el bucket es legible, pero `boris/` solo con MFA.

> [!important] Regla Un bucket puede tener **una sola bucket policy**, pero esa policy puede contener **múltiples statements** (como el ejemplo de arriba).

Una condición que conviene conocer porque aparece en muchos escenarios modernos de seguridad es **forzar cifrado en tránsito**: denegar cualquier request que no venga por HTTPS.

```json
{
  "Sid": "SoloHTTPS",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:*",
  "Resource": [
    "arn:aws:s3:::secretcatproject",
    "arn:aws:s3:::secretcatproject/*"
  ],
  "Condition": { "Bool": { "aws:SecureTransport": "false" } }
}
```

Y otra muy usada, **rechazar cualquier subida que no venga cifrada con una KMS Key determinada**, para garantizar que nadie guarde objetos con un cifrado distinto al aprobado:

```json
{
  "Sid": "SoloKMS",
  "Effect": "Deny",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::secretcatproject/*",
  "Condition": {
    "StringNotEquals": {
      "s3:x-amz-server-side-encryption": "aws:kms"
    }
  }
}
```

### Access Control Lists (ACLs) — legacy

Otra forma de dar acceso, poco común hoy: las **ACLs**. Aplican seguridad a objetos o buckets y son un **subrecurso** de ese objeto/bucket.

> [!warning] Son legacy **AWS recomienda no usarlas.** Son inflexibles: solo permiten permisos muy simples, **sin condiciones** ni la expresividad de las policies.

La tabla completa de lo que una ACL puede expresar (fijate lo poco que es):

|Permission|Sobre el bucket|Sobre el object|
|---|---|---|
|**READ**|Listar los objetos del bucket|Leer el object y su metadata|
|**WRITE**|Crear, sobrescribir y borrar cualquier objeto|_No aplicable_|
|**READ_ACP**|Leer la ACL del bucket|Leer la ACL del object|
|**WRITE_ACP**|Modificar la ACL del bucket|Modificar la ACL del object|
|**FULL_CONTROL**|Los cuatro anteriores|READ + READ_ACP + WRITE_ACP|

Cinco permisos. Sin condiciones. Sin negaciones. Comparalo con lo que puede hacer una bucket policy y se entiende por qué murieron.

### Block Public Access
Funcionalidad que existe para **prevenir filtraciones de datos por mala administración** — el clásico "bucket público por accidente" que generó tantos escándalos de datos filtrados.

Es una **barrera adicional** que se interpone entre los principals **públicos/anónimos** y las resource permissions del bucket. Se aplica **pase lo que pase**, por encima de cualquier bucket policy o ACL — pero **solo al acceso público**: no afecta el acceso de identidades de AWS autenticadas.

Las opciones (de la consola):

|Setting|Qué hace|
|---|---|
|**Block _all_ public access**|Activa las cuatro de abajo. El interruptor maestro.|
|Block public access via **_new_ ACLs**|Bloquea permisos públicos en ACLs nuevas; no toca las existentes.|
|Block public access via **_any_ ACLs**|**Ignora** todas las ACLs que otorguen acceso público.|
|Block public access via **_new_ bucket policies**|Bloquea policies nuevas que den acceso público; no toca las existentes.|
|Block public & cross-account access via **_any_ bucket policies**|Ignora el acceso público y cross-account de cualquier policy.|

![[Pasted image 20260709014142.png]]


> [!tip] La lógica del "new" vs "any" Las opciones "_new_" son para **no empeorar** (frenar futuras configuraciones públicas sin romper lo existente). Las "_any_" son para **cerrar todo ya** (ignorar incluso lo que ya está configurado). En una migración usás "new"; en un bucket que jamás debería ser público usás "any" o el interruptor maestro.

Un dato importante de contexto: desde 2023, **Block Public Access viene activado por defecto** en todos los buckets nuevos, y las ACLs vienen deshabilitadas. O sea que el "bucket público por accidente" hoy requiere que alguien desactive deliberadamente varias protecciones. Aun así, entender cómo funciona sigue siendo material de examen, y sigue siendo lo primero que hay que revisar cuando algo "no debería ser accesible y lo es" (o al revés).

Block Public Access se puede configurar en **dos niveles**: a nivel de cuenta (aplica a todos los buckets, presente y futuro) o a nivel de bucket individual. El de cuenta gana: si está activado ahí, ningún bucket puede ser público aunque su configuración propia lo permita.
### El orden completo de evaluación en S3

Cuando llega una request a S3, la decisión sale de combinar varias capas. El modelo mental correcto es:

1. Si **Block Public Access** aplica y la request es pública/anónima → **denegado**, sin más.
2. Si hay un **Deny explícito** en cualquier policy (bucket policy, IAM, SCP) → **denegado**.
3. Si hay un **Allow explícito** en la bucket policy, en una IAM policy, o en una ACL → **permitido**.
4. Si nada permite → **deny implícito**.

📎 Ejemplos oficiales: https://docs.aws.amazon.com/AmazonS3/latest/userguide/example-bucket-policies.html

La forma de razonar los casos cross-account: hace falta que **la cuenta dueña del bucket lo permita** (por bucket policy o ACL) **y** que **la cuenta que accede se lo permita a su identidad** (por IAM policy). Las dos cosas, siempre.

### Resumen: ¿qué uso para cada situación? (Exam powerup)

- **Identity policies** → cuando controlás _diferentes recursos_ desde un solo lugar, preferís administrar permisos en IAM, o la política es sobre _qué puede hacer una identidad_. Solo funcionan para identidades de **tu propia cuenta**.
- **Bucket policies** → cuando el foco es _un recurso_, necesitás dar acceso **anónimo** o **cross-account**.
- **ACLs** → **nunca**, salvo que algo te obligue. AWS las desaconseja.
