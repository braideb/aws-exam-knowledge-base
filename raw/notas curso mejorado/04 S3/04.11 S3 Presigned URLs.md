# S3 Presigned URLs

Una forma de darle a otra persona o aplicación **acceso temporal a un objeto** de un bucket **usando tus credenciales**, de forma segura.

### El problema
Bucket privado (default). Un **IAM admin** accede sin problema: manda credenciales con la request, AWS valida y concede. Pero una persona **no autenticada** no tiene forma de acceder — sus requests fallan.

Las tres formas clásicas de resolverlo, y por qué ninguna sirve:
1. **Darle una identidad de AWS** → esfuerzo excesivo para un acceso puntual, más riesgo de seguridad.
2. **Prestarle credenciales de AWS** → pésima práctica de seguridad.
3. **Hacer el bucket/objeto público** → inaceptable para datos privados.

### La solución
Una identidad de AWS con permisos (ej: iamadmin) le pide a S3 que **genere una presigned URL**, proporcionando:

- Sus **credenciales de seguridad**,
- El **bucket** y la **object key**,
- Una **fecha/hora de expiración**,
- El **método de acceso** (lectura o escritura).

S3 devuelve una URL que **codifica todos esos detalles en su interior**. Esa URL se le pasa al usuario no autenticado, que puede usarla para acceder a **ese objeto específico, en ese bucket específico, hasta que expire** — como si fuera (temporalmente y para esa única operación) la identidad que la generó.

Sirve tanto para **descarga (GET)** como para **upload (PUT)**.

Vale la pena entender **qué es** una presigned URL por dentro, porque explica sus propiedades: es la URL normal del objeto más un conjunto de parámetros en el query string, entre ellos las credenciales del generador, un timestamp, el tiempo de validez y una **firma criptográfica** (SigV4) de todo eso. S3 recibe la URL, recalcula la firma y verifica que nadie haya alterado los parámetros. Por eso no se puede "editar" una presigned URL para acceder a otro objeto o extender su vida: cualquier cambio invalida la firma. Y por eso tampoco requiere que el generador esté online cuando se usa: toda la autorización viaja dentro de la URL.
### Arquitectura típica: aplicación con media bucket

Aplicación que antes servía contenido desde su propio servidor y migró los archivos a un **media bucket**. Los usuarios de la app **no están registrados en AWS** — están registrados en la aplicación.

![[Pasted image 20260717143553.png]]


Flujo:

1. El usuario le pide el contenido **al servidor de la app** (como siempre).
2. El servidor, que tiene una identidad de AWS (**iamapp1**), le pide a S3 una **presigned URL** para ese objeto.
3. S3 genera la URL y se la devuelve al servidor.
4. El servidor le pasa **la URL al usuario**.
5. El usuario descarga el objeto **directo desde el bucket** con esa URL.

> [!tip] Por qué es tan buena esta arquitectura El servidor deja de ser intermediario del tráfico pesado (los bytes van directo de S3 al usuario = _offloading_), pero **la autenticación y autorización siguen siendo de la app**. AWS nunca conoce a los usuarios finales, y el bucket nunca se hace público.


El caso de **upload** es igual de útil y quizás más común hoy: para que un usuario suba un archivo (foto de perfil, documento), el servidor genera una presigned URL de tipo PUT y el usuario sube **directo al bucket**, sin que el archivo pase por el servidor de la app. Esto evita que el servidor tenga que recibir y reenviar archivos grandes, y es el patrón estándar de los formularios de carga en aplicaciones serverless.
### Consideraciones para el examen

> [!warning] Las tres trampas clásicas
> 
> **1. Podés generar una presigned URL para un objeto al que NO tenés acceso.** El único requisito es especificar objeto y expiración. La URL se genera igual... pero como está **vinculada a vos**, quien la use tampoco va a tener acceso. No hay casi ningún caso de uso legítimo — pero el examen pregunta si es _posible_, y la respuesta es sí.
> 
> **2. Los permisos de la URL coinciden con los permisos que la identidad generadora tiene EN ESTE MOMENTO** — no los que tenía al generarla. Si te llega un _access denied_ usando una presigned URL, puede ser que la identidad generadora **nunca tuvo acceso**, o que **lo perdió después** de generar la URL.
> 
> **3. NO generes presigned URLs con un IAM role.** Un role te da **credenciales temporales**, y una presigned URL puede tener una validez **mucho más larga** que esas credenciales. Cuando las credenciales temporales expiran, **la URL deja de funcionar** aunque su fecha de expiración no haya llegado. Generá presigned URLs con identidades de **largo plazo** (IAM users).

Sobre los tiempos de validez, para completar: una presigned URL generada con credenciales de un IAM user puede durar **hasta 7 días**. Pero si se genera con credenciales temporales (un rol, o SSO), su vida real es la que sea **menor** entre la expiración de la URL y la de las credenciales — que suele ser una hora. Este es exactamente el motivo de la trampa 3, y en la práctica es un dolor de cabeza recurrente cuando se generan presigned URLs desde una Lambda (que corre con un rol): las URLs "se vencen antes de tiempo" porque el rol de la Lambda caducó.
