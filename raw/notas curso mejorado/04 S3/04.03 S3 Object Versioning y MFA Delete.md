# S3 Object Versioning y MFA Delete

> [!important] Estos dos conceptos aparecen seguido en el examen.

### Los tres estados del versioning

El versioning se controla **a nivel de bucket** y arranca **deshabilitado**.

![[Pasted image 20260710060030.png]]


> [!danger] La regla de oro (pregunta de examen garantizada) **Una vez habilitado, el versioning NUNCA se puede deshabilitar.** Solo se puede **suspender**, y desde suspendido se puede volver a habilitar. `Enabled → Disabled` no existe.
> 
> ¿Por qué importa? Porque **todas las versiones ocupan espacio y se facturan**. Al suspender dejás de generar versiones nuevas, pero **las existentes permanecen** (y se siguen cobrando). La única forma de dejar de pagar por versiones viejas es borrarlas explícitamente.

### Cómo funciona

**Sin versioning**, cada objeto se identifica únicamente por su **key** (el nombre). Si modificás el objeto, la versión original **se reemplaza** — se pierde.

**Con versioning**, el objeto tiene además otro atributo: el **version ID**.

- Con versioning deshabilitado, el ID vale `null`.
- Al subir un objeto con versioning habilitado, S3 le asigna un ID (ej: `111111`).
- Si alguien sube una modificación con la misma key, S3 **no reemplaza nada**: crea una nueva versión con un nuevo ID (`222222`). Esa pasa a ser la **Latest version** (o _Current version_).

![[Pasted image 20260710060724.png]]


Al acceder a un objeto **sin explicitar versión**, S3 devuelve siempre la **current version**. Pero siempre podés pedir un **version ID específico** para recuperar esa versión en particular.

Un detalle sobre el estado `Suspended` que aclara bastante: cuando el bucket está suspendido, los objetos nuevos se guardan con version ID `null`, y las versiones que ya existían **siguen intactas**. Es decir, suspender no es "modo sin versiones": es "modo que convive con las versiones viejas pero no crea nuevas". Si subís dos veces la misma key estando suspendido, la segunda sí pisa a la primera (ambas tienen ID `null`), pero cualquier versión con ID real anterior sigue guardada abajo.

### Delete markers: el borrado que no borra

El versioning también cambia cómo funcionan las **eliminaciones**.

![[Pasted image 20260710061322.png]]

Si borrás un objeto **sin especificar version ID**, S3 **no borra nada**. Lo que hace es agregar una versión especial nueva: el **delete marker**.

- El delete marker hace que el objeto _parezca_ eliminado (si lo pedís, S3 responde como si no existiera).
- Pero todas las versiones siguen ahí, **ocultas** debajo del marker.
- Si **borrás el delete marker**, el objeto "revive": vuelve a verse la current version anterior. Eso es el **undelete**.

> [!tip] Analogía El delete marker es como poner un cartel de "CERRADO" en la puerta de un local. El local y toda su mercadería siguen intactos atrás del cartel; solo que desde afuera parece que no hay nada. Sacás el cartel y el local reabre tal cual estaba.

Un matiz que conviene tener claro: un delete marker es en sí mismo una versión, con su propio version ID. Por eso se puede borrar como cualquier versión (especificando su ID), y eso es lo que hace el undelete. Además, el delete marker **no tiene tamaño de datos** (o casi), así que prácticamente no cuesta almacenamiento — lo que cuesta son las versiones que quedan debajo.
### Version delete: el borrado que sí borra

Para eliminar de verdad, hay que borrar el objeto **especificando el version ID** en particular. Eso destruye esa versión de forma **permanente e irreversible** — sin delete marker, sin vuelta atrás.

Así también se liquidan las versiones viejas que ya no querés pagar.

![[Pasted image 20260710061342.png]]

### El costo oculto del versioning

Esto no siempre se dice y es de lo más importante en la práctica: con versioning activado, **nada se borra nunca de verdad salvo que lo hagas a propósito por version ID**. Cada modificación deja atrás la versión anterior, y todas se facturan.

Un caso típico que sorprende: un bucket con archivos que se sobrescriben seguido (logs, exports diarios, imágenes que se reemplazan) puede terminar ocupando mucho más de lo que muestra la vista normal, porque debajo de cada key hay decenas de versiones viejas. El bucket "pesa" cinco veces lo que parece.

La solución no es apagar el versioning (no se puede), sino una **lifecycle rule** que expire las versiones **no actuales** después de X días. Es la combinación estándar: versioning encendido para protección, más una regla que limpia las versiones viejas para no pagar de más.
### MFA Delete

Se habilita **dentro de la configuración de versioning** del bucket. Cuando está activo, se requiere **MFA** para:

1. **Cambiar el estado del versioning** del bucket (Enabled ⇄ Suspended).
2. **Eliminar cualquier versión** de un objeto (el version delete de arriba).

Mecánica por API: se concatena el **número de serie del token MFA + el código que genera**, y se pasa junto con la llamada a la API.

> [!tip] Para qué existe Es la protección contra el borrado catastrófico: aunque a alguien le roben las credenciales de un admin, no puede destruir versiones ni apagar el versioning sin tener además el dispositivo MFA físico en la mano.

Un par de restricciones prácticas que hay que conocer, porque MFA Delete es más incómodo de lo que parece:
- **Solo se puede activar y administrar desde el account root user** (con la CLI, no desde la consola). No lo puede activar un IAM user, ni siquiera uno con permisos de admin.
- Al ser una operación que requiere el token en cada borrado de versión, complica la automatización: cualquier proceso que borre versiones necesita el código MFA, cosa que un script desatendido no tiene. Por eso MFA Delete se reserva para buckets muy críticos donde el borrado siempre es manual y deliberado.
