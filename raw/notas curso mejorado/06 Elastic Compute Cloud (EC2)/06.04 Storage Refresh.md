# Storage Refresh

Repaso rápido de conceptos de almacenamiento que se usan todo el tiempo en EC2.

### Términos clave

**Direct Attached Storage (DAS)** o almacenamiento local: son los discos físicos conectados directamente a un dispositivo, como un portátil o un servidor. En el contexto de EC2, es el almacenamiento conectado directamente a los **EC2 hosts**, y se llama **Instance Store**. Este tipo de almacenamiento suele ser **muy rápido**, justamente porque está pegado al hardware, pero tiene varios problemas: si el disco falla, podés perder los datos; si falla el hardware del host, los perdés; y si la instancia EC2 se mueve de un host a otro (recordá el stop + start de [[06.02 EC2 Architecture and Resilience#Ciclo de vida ¿cuándo se mueve una instance de host?|Ciclo de vida]]), también los podés perder.

La alternativa es el **Network Attached Storage (NAS)**: almacenamiento donde los volúmenes se crean por separado y se conectan al dispositivo **a través de la red**. En entornos on-premises (locales) esto usa protocolos como **iSCSI** o **Fibre Channel**. En AWS, el almacenamiento conectado por red se implementa con **Elastic Block Store (EBS)**. El almacenamiento en red suele ser **muy resiliente** y está **separado del hardware de la instancia**, así que puede sobrevivir a los problemas que afecten al EC2 host.

Otras dos palabras describen la *durabilidad* del almacenamiento (no cómo se conecta):

- **Ephemeral storage** (efímero): almacenamiento temporal que no perdura; no podés confiar en que sea persistente. Ejemplo típico: el Instance Store.
- **Persistent storage** (persistente): existe como algo propio y vive **más allá de la vida del dispositivo** al que está conectado (más allá de la instancia). Ejemplo típico: EBS.

> [!note] En resumen
> **Instance Store = efímero**, **EBS = persistente**. Es la misma idea que aparece en el ciclo de vida de las instancias.

### Las tres categorías de almacenamiento en AWS

Las tres categorías principales se distinguen por **cómo se presenta** el almacenamiento, ya sea a vos o a un servidor.

**Block Storage** (almacenamiento en bloque): se crea un **volumen** (por ejemplo, dentro de EBS). Un volumen de block storage es simplemente una colección de **bloques direccionables**. Puede tener pocos bloques o una cantidad enorme, según el tamaño del volumen, pero **no tiene ninguna estructura más allá de eso**: es como un disco duro físico vacío presentado de forma lógica. Cuando le presentás un volumen de block storage a un servidor, es el **sistema operativo** el que crea encima un **sistema de archivos (file system)** —como NTFS en Windows o ext4 en Linux— y luego lo **monta**: como unidad `C:` en Windows o como volumen raíz (root) en Linux. Por debajo, ese volumen lógico está respaldado por medios físicos, ya sea discos duros giratorios (HDD) o SSD. Lo importante es que el block storage **no trae estructura propia**: depende del OS para crear y montar el file system. En AWS, además de montar un volumen EBS, también podés **arrancar (boot) desde él**: de hecho, la mayoría de las instancias EC2 usan un volumen EBS como **boot volume**, que es donde vive el sistema operativo y desde donde arranca la máquina.

**File Storage** (almacenamiento de archivos): es lo que en el mundo local te da un **servidor de archivos (file server)**. Te lo entregan como un **sistema de archivos ya listo para usar**, con la estructura ya armada: podés navegarlo, crear carpetas y guardar archivos, y accedés a ellos conociendo la estructura de carpetas. Por razones obvias, **no se puede usar como booteable**. (En AWS, el servicio de file storage es **EFS —Elastic File System—**, que se ve más adelante.)

**Object Storage** (almacenamiento de objetos): es un sistema mucho más abstracto donde solo guardás **objetos**, sin ninguna estructura: es una **colección plana** de objetos. Un objeto puede ser cualquier cosa (datos binarios, imágenes, videos, etc.) y puede llevar **metadatos** asociados, pero para recuperarlo normalmente le pasás una **clave (key)**. En AWS, esto es **S3** (ver [[01.08 S3 Buckets — Basics|S3 Buckets — Basics]]). La gran ventaja es que es **enormemente escalable** y puede ser accedido por millones de personas a la vez; la contra es que en general **no se puede montar** dentro de un sistema de archivos y **no es booteable**.

| Categoría | Qué te entrega | ¿Booteable? | Servicio en AWS |
|---|---|---|---|
| **Block** | Bloques en crudo; el OS pone el file system | **Sí** | EBS, Instance Store |
| **File** | Un file system ya armado, con carpetas | No | EFS |
| **Object** | Objetos planos con key y metadatos | No | S3 |

### Rendimiento del almacenamiento (Storage Performance)

Tres términos:

- **IO (block) size:** el tamaño de cada bloque de lectura/escritura.
- **IOPS:** operaciones de entrada/salida por segundo.
- **Throughput:** cantidad de datos transferidos por segundo (normalmente en MB/s).

Los tres se relacionan por una cuenta simple:

**IO block size × IOPS = Throughput**

Por ejemplo, con bloques de 16 KB y 100 IOPS: 16 KB × 100 = 1.600 KB/s ≈ **1,6 MB/s**. La idea a retener es que estas tres variables se afectan entre sí. En la práctica, un volumen de AWS suele tener un tope de IOPS **y** un tope de throughput por separado, así que a veces chocás con un límite antes que con el otro (se retoma al ver EBS).

> [!tip] Dato que vuelve todo el tiempo
> El **tamaño de bloque cambia según el tipo de volumen**: en los SSD de EBS la unidad es de **16 KB**, y en los HDD es de **1 MB**. Por eso las mismas IOPS dan throughputs muy distintos según el tipo (ver [[06.06 EBS Volume Types - General Purpose SSD (gp2 y gp3)|gp2 / gp3]] y [[06.08 EBS Volume Types - HDD (st1 y sc1)|st1 / sc1]]).
