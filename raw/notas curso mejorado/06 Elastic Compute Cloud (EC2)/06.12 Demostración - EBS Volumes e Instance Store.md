# Demostración: EBS Volumes e Instance Store

🔗 Parte 1: <https://learn.cantrill.io/courses/1101194/lectures/27806446>
🔗 Parte 2: <https://learn.cantrill.io/courses/1101194/lectures/28705524>
🔗 Parte 3: <https://learn.cantrill.io/courses/1101194/lectures/28705526>

**Objetivo de la demo (común a las tres partes):**

- Crear un volumen EBS y montarlo en una instancia EC2.
- Crear y montar un file system, y generar un archivo de prueba.
- Migrar el volumen a otra instancia EC2 **en la misma AZ** y verificar que el file system y el archivo siguen intactos.
- Crear un snapshot del volumen y, a partir de él, un nuevo volumen EBS en **AZ-B**; verificar que todo está intacto.
- Copiar el snapshot a **otra región**.
- Crear una instancia EC2 **con instance store volumes**, crear un file system y un archivo de prueba.
- Reiniciar (reboot) la instancia y verificar que el file system sigue presente.
- Hacer **stop + start** y verificar que el file system **ya no está** (nuevo EC2 host → instance store perdido).

> [!note] Qué demuestra cada mitad
> La primera mitad prueba que **EBS persiste** y cruza de instancia y de AZ (vía snapshot). La segunda prueba que el **instance store es efímero** y que la diferencia entre *reboot* y *stop + start* es real — justo lo que se explica en [[06.09 Instance Store Volumes|Instance Store Volumes]].

## Comandos de la demo

### Instancia 1 — crear file system y montar el volumen EBS

```bash
lsblk
sudo file -s /dev/xvdf
sudo mkfs -t xfs /dev/xvdf
sudo file -s /dev/xvdf
sudo mkdir /ebstest
sudo mount /dev/xvdf /ebstest
cd /ebstest
sudo nano amazingtestfile.txt   # escribir un mensaje, guardar y salir
ls -la
```

`lsblk` lista los block devices que ve el OS. `file -s` sobre el dispositivo dice si ya tiene un file system (si contesta `data`, está vacío). `mkfs -t xfs` crea el file system y `mount` lo cuelga de un directorio.

### Reboot de la instancia 1 y montaje persistente vía /etc/fstab

```bash
sudo reboot

# Después del reboot:
df -k
sudo blkid
sudo nano /etc/fstab
  # AGREGAR LA LÍNEA:
  UUID=TU_UUID_ACA  /ebstest  xfs  defaults,nofail
sudo mount -a
cd /ebstest
ls -la
```

Un `mount` a mano no sobrevive al reboot. Agregar la entrada en `/etc/fstab` (identificando el volumen por **UUID**, no por nombre de dispositivo, que puede cambiar) es lo que lo hace permanente. `mount -a` monta todo lo declarado en el archivo sin reiniciar.

### Instancias 2 y 3 — montar el mismo volumen migrado (sin reformatear)

```bash
lsblk
sudo file -s /dev/xvdf
sudo mkdir /ebstest
sudo mount /dev/xvdf /ebstest
cd /ebstest
ls -la
```

Acá **no** se vuelve a correr `mkfs`: el file system ya está y reformatear borraría los datos. `file -s` ahora responde con el tipo de file system, prueba de que el volumen llegó intacto.

### Instance Store — crear file system y probar persistencia

```bash
lsblk
sudo file -s /dev/nvme1n1
sudo mkfs -t xfs /dev/nvme1n1
sudo file -s /dev/nvme1n1
sudo mkdir /instancestore
sudo mount /dev/nvme1n1 /instancestore
cd /instancestore
sudo touch instancestore.txt
```

### Instance Store — después de un reboot (los datos siguen; hay que remontar)

```bash
df -k          # no aparece montado
sudo mount /dev/nvme1n1 /instancestore
cd /instancestore
ls -la          # el archivo sigue estando
```

### Instance Store — después de un stop/start (nuevo host: el volumen aparece vacío)

```bash
sudo file -s /dev/nvme1n1
```

Si responde `data`, el volumen está en blanco: la instancia se mudó de host y el instance store anterior se perdió con todo su contenido.
