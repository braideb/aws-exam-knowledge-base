# Instance Store Volumes

Los **Instance Store volumes** también proporcionan **block storage**: volúmenes en crudo que se adjuntan a una instancia, se presentan al OS y sirven de base para un file system que después usan las aplicaciones. Hasta ahí son como EBS… con una diferencia enorme: son **locales**, no se presentan a través de la red.

Están **físicamente conectados a un EC2 host**. Cada host tiene sus propios instance store volumes, aislados en ese host, y solo las instancias que corren en ese host pueden acceder a ellos. Como están conectados localmente, ofrecen **el mayor rendimiento de almacenamiento disponible en AWS**, muy por encima de lo que puede dar EBS.

Vienen **incluidos en el precio** de las instancias que los traen. Distintos tipos de instancia traen distinta cantidad (y tamaño) de instance store volumes; donde se incluyen, ya están pagos, así que es un caso de **"usarlos o perderlos"**.

### Hay que adjuntarlos al lanzar

Punto muy importante: los instance store volumes **hay que adjuntarlos en el momento del lanzamiento (launch)**. A diferencia de EBS, **no podés agregarlos después**. Según el tipo de instancia se te asigna una cantidad determinada; podés usarlos o no, pero si no lo hacés al lanzar, no los sumás más adelante.

En el diagrama, cada instancia tiene una colección de volúmenes respaldados por dispositivos físicos del host donde corre: el host A tiene tres dispositivos físicos presentados como tres instance store volumes, y el host B otros tres. ### Lo crucial: son efímeros

No son para siempre. Si falla el hardware, se pierden los datos. Y si la instancia pasa del host A al host B (recordá: un **stop + start** puede mudarla de host), se le asignan volúmenes nuevos en el host B y **los anteriores se pierden con toda su información**. Es exactamente la misma idea de "efímero" que aparece en el [[06.02 EC2 Architecture and Resilience#Ciclo de vida ¿cuándo se mueve una instance de host?|ciclo de vida de las instancias]].

> [!note] Resumen mental
> **Instance Store = local + efímero + rapidísimo**, se adjunta solo al lanzar.
> **EBS = por red + persistente**, se adjunta/desadjunta cuando quieras.

**¿Cuándo elegirlo?** Cuando necesitás el **máximo rendimiento** (más throughput y más IOPS que EBS) y podés tolerar perder esos datos — por ejemplo, cachés, archivos temporales o data que podés reconstruir.

> [!warning] La trampa clásica del examen
> **Reboot ≠ stop + start.** Un **reboot** conserva los datos del instance store (no cambia de host), aunque el volumen queda **desmontado** y hay que volver a montarlo. Un **stop + start** cambia de host y los datos **se pierden**. La demo de [[06.12 Demostración - EBS Volumes e Instance Store|EBS Volumes e Instance Store]] muestra exactamente esos dos casos.
