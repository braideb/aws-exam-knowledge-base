# Instance Metadata (IMDS)

Arquitectura muy simple, pero base de muchas de las funcionalidades más potentes de EC2. Aparece en casi todos los exámenes de AWS.

El **Instance Metadata Service** provee datos **sobre la instancia misma**, útiles para configurarla o administrarla mientras corre. Es la forma en que la instancia —o cualquier proceso corriendo dentro— accede a información sobre su propio entorno que de otra manera no podría consultar.

Es accesible desde **todas** las instancias usando siempre el mismo método: una IP fija, **169.254.169.254**.

> [!tip] Memorizate esta IP
> **169.254.169.254** aparece todo el tiempo en el examen.

A esa IP se le agrega una ruta para pedir la información más reciente: `http://169.254.169.254/latest/meta-data/`. Desde ahí podés consultar, por ejemplo, información de networking (IP pública), del entorno (region, availability zone), o relacionada con autenticación (**credenciales temporales** si la instancia tiene un [[03.06 IAM Roles|IAM Role]] asociado), entre otras cosas.

> [!warning] Dato clave de seguridad
> El servicio de metadata **NO requiere autenticación y no está encriptado**. Cualquier proceso dentro de la instancia (o que logre acceder a ella) puede consultar esa IP libremente. Si un atacante logra ejecutar código dentro de tu instancia (por ejemplo, explotando una vulnerabilidad en una app web), puede usar este endpoint para **robar credenciales temporales** u otra información sensible.

> [!warning] Revisar: el curso solo cubre IMDSv1
> Todo lo de arriba describe **IMDSv1**, donde un simple `GET` alcanza. Justamente por el riesgo que la nota anterior describe (un SSRF en la app web deriva en robo de las credenciales del role), AWS introdujo **IMDSv2**, que hoy es **el default en instancias nuevas** y es material de examen.
>
> IMDSv2 es **orientado a sesión**: primero pedís un token con un `PUT` y después lo mandás en cada consulta.
>
> ```bash
> # 1) obtener el token (TTL en segundos, máx. 21600)
> TOKEN=$(curl -X PUT "http://169.254.169.254/latest/api/token" \
>   -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
>
> # 2) usarlo en cada request
> curl -H "X-aws-ec2-metadata-token: $TOKEN" \
>   http://169.254.169.254/latest/meta-data/
> ```
>
> Por qué esto corta el ataque: el `PUT` inicial y el header personalizado son cosas que un SSRF clásico (que solo sabe pedir una URL por `GET`) **no puede hacer**, y además la respuesta del token trae un TTL de hop limit que impide que el pedido salga de la instancia. En el examen: si la pregunta habla de **proteger las credenciales del role frente a SSRF**, la respuesta es **exigir IMDSv2** (`HttpTokens: required`).

### Demo del curso

🔗 **DEMO — Viendo los metadatos en una instancia de EC2:** <https://learn.cantrill.io/courses/1101194/lectures/27806481>

Consultar la IP pública y el hostname público desde adentro de la instancia, usando `curl` para hacer la petición HTTP al servicio de metadata:

```bash
curl http://169.254.169.254/latest/meta-data/public-ipv4
curl http://169.254.169.254/latest/meta-data/public-hostname
```

Descargar un script (`ec2-metadata`) que simplifica la consulta (evita armar la URL completa a mano) y darle permiso de ejecución (`chmod u+x` agrega el permiso *execute* para el usuario dueño del archivo):

```bash
wget http://s3.amazonaws.com/ec2metadata/ec2-metadata
chmod u+x ec2-metadata
```

Con el script instalado:

```bash
ec2-metadata --help   # muestra las opciones disponibles
ec2-metadata -a       # ami-id (la AMI con la que se lanzó la instancia)
ec2-metadata -z       # availability zone en la que corre la instancia
ec2-metadata -s       # security groups asociados
```

> [!note] Aclaración de la transcripción
> El flag `-a` corresponde a **ami-id** (las notas lo dejaban dudoso). `-z` = availability zone y `-s` = security groups, según la ayuda (`--help`) del script.
