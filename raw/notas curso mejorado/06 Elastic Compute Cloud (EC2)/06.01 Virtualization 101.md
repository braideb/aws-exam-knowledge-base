# Virtualization 101

EC2 ofrece **virtualización como servicio** y es un producto de tipo **IaaS (Infrastructure as a Service)**. Para entender cómo funciona EC2 por dentro conviene repasar primero los fundamentos de la virtualización.

La **virtualización** es el proceso de ejecutar más de un sistema operativo (OS) sobre una misma pieza de hardware físico (un mismo servidor).

### Antes de la virtualización

En la arquitectura tradicional, un servidor tenía un conjunto de recursos físicos —CPU, memoria (RAM), tarjetas de red y algún dispositivo de almacenamiento— y sobre ese hardware corría un único **operating system (OS)**.

El OS tiene un nivel de acceso privilegiado al hardware. En realidad no es todo el OS el que corre con privilegios, sino una parte pequeña y central, el **kernel**, que se ejecuta en **privileged mode** y es el único componente capaz de interactuar directamente con el hardware.

Las **aplicaciones** (por ejemplo, las que usan Bob o Julie) corren en **user mode**, sin privilegios, y no pueden tocar el hardware directamente. Cuando una aplicación necesita algo del hardware, se lo pide al OS mediante una **system call**. Así funciona todo *sin* virtualización.

### El problema al querer correr varios OS

Si ponemos varios sistemas operativos independientes sobre una misma pieza de hardware, cada uno con sus propias aplicaciones, aparece un problema: una CPU (al menos en aquel momento) solo podía tener **un** proceso corriendo en modo privilegiado a la vez. Pero cada OS espera ser el único dueño del hardware y ejecutar instrucciones privilegiadas por su cuenta. Si intentás correr tres, cuatro o más sistemas operativos de esta forma, todos pelean por ese acceso privilegiado y el resultado son **cuelgues y bloqueos del sistema (crashes)**.

![[Pasted image 20260919152411.png]]

### La solución por software (primeras versiones)

La virtualización nació para resolver ese problema: permitir que varias "cosas" que necesitan privilegios corran sobre el mismo hardware. Al principio era **muy ineficiente**, porque el hardware no "sabía" que existía la virtualización y todo tenía que resolverse por software. Hubo dos enfoques.

#### 1) Emulated virtualization (por software)

- Sobre el hardware corría un **host OS** que incluía una capacidad extra: el **hypervisor**. Ese software corría en modo privilegiado, con acceso total al hardware del host.
- Alrededor corrían varios **guest OS**, cada uno dentro de un contenedor llamado **virtual machine (VM)**.
- Cada VM tenía asignados recursos *virtuales*: CPU, memoria, disco y dispositivos "mapeados" como tarjeta de red o gráfica.
- Punto clave: los guest OS **creían** correr sobre hardware real. Tenían sus drivers instalados como si los dispositivos fueran físicos, pero todo era **emulado**: el hypervisor les daba información falsa para que se lo creyeran.

Como el guest OS cree que está sobre hardware real, sigue intentando hacer **llamadas privilegiadas** (tomar el control de la CPU, leer y escribir en lo que cree que son "su" memoria y "su" disco). El hypervisor intercepta cada una de esas operaciones y las traduce al vuelo. Esto se llama **binary translation**.

- **Ventaja:** los guest OS no necesitan ninguna modificación.
- **Desventaja:** es **lentísimo** — podía llegar a la mitad de la velocidad (o menos) de un OS corriendo directo sobre el hardware.

![[Pasted image 20260919153256.png]]

#### 2) Para-virtualization

Para mejorar la velocidad apareció otro enfoque:

- Los guest OS siguen corriendo dentro de su VM con recursos virtuales.
- Pero en lugar de la lenta binary translation, se **modifica el código fuente del guest OS**: las partes que normalmente harían llamadas privilegiadas al hardware se cambian para que, en su lugar, llamen al hypervisor. Estas llamadas se llaman **hypercalls**.
- Además se usan **drivers paravirtualizados** en el guest OS.

El guest OS pasa a estar casi "consciente" de que está virtualizado, y el rendimiento mejora muchísimo.

- **Desventaja:** el OS tiene que estar **modificado específicamente para el hypervisor** que se use. Ya no es virtualización genérica: hay que adaptar cada OS al proveedor/hypervisor concreto. Aun así, sigue siendo un truco por software para engañar al guest OS.

![[Pasted image 20260919153810.png]]

### Hardware-assisted virtualization

La mejora de verdad llegó cuando el **hardware** empezó a ser consciente de la virtualización (**hardware virtualization** o **hardware-assisted virtualization**).

- La CPU incorpora instrucciones y capacidades nuevas para la virtualización, de modo que el hypervisor puede controlarla y configurarla directamente. La CPU "sabe" que la virtualización existe.
- Cuando un guest OS intenta ejecutar una instrucción privilegiada, la CPU la **atrapa (trap)**, porque está esperando ese tipo de instrucción de los guests. Así el sistema completo no se cuelga.
- Esas instrucciones no se pueden ejecutar tal cual (el guest sigue creyendo que corre directo sobre el hardware), así que se redirigen al **hypervisor**, que decide cómo ejecutarlas.

Resultado: muy poca pérdida de rendimiento respecto a correr directo sobre el hardware.

#### El cuello de botella del I/O

Lo que más importa en una VM suele ser el **I/O**: tráfico de red y lectura/escritura de disco. Las VM tienen lo que *creen* que es hardware físico (por ejemplo, una tarjeta de red), pero en realidad son **dispositivos lógicos** que, a través de un driver, terminan conectándose a una **única** pieza física de hardware en el host. Como todo pasa por ese único punto físico, salvo que tengas una tarjeta de red física por cada VM, siempre hay una capa de software en el medio. En actividades muy transaccionales (mucho I/O de red o disco) eso golpea el rendimiento y consume muchos ciclos de CPU del host.

![[Pasted image 20260919154433.png]]

### SR-IOV: dispositivos conscientes de la virtualización

La última mejora es que los **propios dispositivos de hardware** (no solo la CPU) se vuelven conscientes de la virtualización. Este proceso se llama **SR-IOV (Single Root I/O Virtualization)**.

A grandes rasgos, SR-IOV permite que una tarjeta de red (o cualquier otra tarjeta de expansión compatible) se presente **no como una sola tarjeta, sino como varias "mini-tarjetas" independientes**. Como esto está soportado por el hardware, para el sistema esas mini-tarjetas son tarjetas totalmente reales y únicas, y se presentan **directamente** a cada guest OS como si fueran hardware dedicado.

Esto significa que **el hypervisor ya no tiene que hacer ninguna traducción** para el I/O: el guest OS usa "su" tarjeta directamente. La tarjeta física compatible con SR-IOV se encarga de todo el camino, asegurando que cada mini-tarjeta lógica tenga acceso real a la red física cuando lo necesita.

En EC2 esta función se llama **Enhanced Networking**, y sus beneficios son:

- Mayor rendimiento de red (velocidades más altas).
- **Menor latencia** y, sobre todo, latencia más baja y constante incluso con cargas altas.
- Menor uso de CPU del host, incluso cuando todos los guests mueven mucho I/O.

### Cierre

Muchas de las funciones que vas a usar en EC2 se apoyan en que AWS implementa técnicas de virtualización muy avanzadas, de las más punteras de la industria. AWS tiene su propio hypervisor: la pila se llama **Nitro**.
