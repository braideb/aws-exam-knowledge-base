# EC2 Architecture and Resilience

### EC2 instances = máquinas virtuales

Una **EC2 instance** es, en el fondo, una máquina virtual (VM): un operating system (OS) más una asignación de recursos:

- **vCPU** (CPU virtual)
- memoria (RAM)
- posiblemente algo de almacenamiento local (**instance store**)
- posiblemente algo de almacenamiento de red (**EBS**)
- acceso a otro hardware, como networking y GPUs

### EC2 hosts (los servidores físicos)

Las EC2 instances corren sobre **EC2 hosts**, el hardware físico de servidor que **administra AWS** (no lo ves ni lo tocás). Hay dos tipos de hosts:

- **Shared hosts:** el host se comparte entre distintos clientes de AWS. No sos dueño de nada del hardware; pagás por cada instance individual según el tiempo que corre y los recursos que tiene asignados. Aunque varios clientes compartan el mismo host físico, están **completamente aislados** entre sí: no hay visibilidad ni interacción entre ellos. Es el modo por defecto.
- **Dedicated hosts:** pagás por el **host entero**, no por las instances que corren adentro. Es tuyo, dedicado a tu cuenta, y no lo compartís con ningún otro cliente.

> [!note] En resumen
> En **shared host** pagás por *instance*; en **dedicated host** pagás por el *host completo*. El detalle de los modelos de tenancy está en [[06.20 Dedicated Hosts y Dedicated Instances|Dedicated Hosts y Dedicated Instances]].

### EC2 es resiliente a nivel de Availability Zone (AZ)

Esto es clave. Los EC2 hosts corren dentro de **una única Availability Zone (AZ)**. Por lo tanto, si esa AZ falla, los hosts que están dentro pueden caer con ella. EC2 **no "sobrevive" solo** a la caída de una AZ: la resiliencia la tenés que diseñar vos (por ejemplo, repartiendo instances en varias AZ).

Un host corriendo, por ejemplo, en **AZ-A** tiene un **instance store** (almacenamiento local físico del propio host), **network interfaces** conectadas a subnets, y volúmenes **EBS** (almacenamiento persistente).

### Ciclo de vida: ¿cuándo se mueve una instance de host?

Una instance se crea y corre sobre un host, y **se queda en ese host** hasta que pasa una de estas dos cosas:

1. El **host falla** o AWS lo **retira por mantenimiento**.
2. La instance se **detiene (stop)** y luego se **inicia (start)**. Esto es **distinto de un reboot**: un reboot NO mueve la instance; un stop + start sí puede moverla.

Si pasa cualquiera de las dos, la instance se **reubica en otro host**, pero ese host va a estar en la **misma AZ**. Las instances **no se mueven de forma nativa entre AZ**: todo lo que las compone (hardware, networking y almacenamiento) está "encerrado" dentro de una AZ. Sí existen formas de migrar, pero en esencia significan **sacar una copia de la instance y crear una nueva** en otra AZ.

> [!warning] Muy típico de examen
> - El **instance store es efímero** (está atado al host físico). Al hacer **stop + start** (la instance se muda de host) o si el host falla, **los datos del instance store se pierden**. Un **reboot conserva** el instance store, porque no cambia de host.
> - Los datos en **EBS persisten** en todos estos casos.
> - Al hacer **stop + start**, la **IP pública** de la instance también cambia (salvo que uses una **Elastic IP**).

Este mismo mapa mental reaparece en [[06.09 Instance Store Volumes|Instance Store Volumes]] y en [[06.15 Elastic IP|Elastic IP]].

### No se puede cruzar de AZ

Lo que **nunca** vas a poder hacer es conectar una **network interface** o un volumen **EBS** de una AZ a una EC2 instance que está en **otra** AZ. Tanto **EC2 como EBS son servicios a nivel de AZ** y están aislados: no se cruza de AZ ni con instances ni con volúmenes EBS.

La forma de mover datos entre AZ es vía **snapshot**, que vive en S3 y por lo tanto es resiliente a nivel de región — ver [[06.11 EBS Snapshots, Restore y Fast Snapshot Restore (FSR)|EBS Snapshots, Restore y FSR]].

### ¿Cuándo elegir EC2?

EC2 es una buena opción cuando:

- **Necesitás un OS tradicional** para procesar tu aplicación: la app requiere correr sobre un OS determinado, con cierto runtime y configuración.
- **Cómputo de larga duración (long-running):** otros servicios de cómputo de AWS tienen límites de tiempo de ejecución (por ejemplo, Lambda corta a los 15 minutos). EC2 está pensado para procesos que corren de forma continua durante meses o años.
- **Aplicaciones tipo servidor (server-style):** apps tradicionales que esperan estar corriendo sobre un OS, a la espera de **conexiones entrantes**.
- **Cargas con ráfagas (burst) o de estado estacionario (steady-state):** hay distintos **instance types** para cargas normales bajas con ráfagas ocasionales, o para carga constante.
- **Aplicaciones monolíticas (monolithic app stacks):** si tu app necesita varios componentes en la misma pila (base de datos, middleware, runtime), especialmente si corre sobre un sistema tradicional.
- **Migración de cargas y disaster recovery:** cargas que esperan una VM tradicional o un entorno tipo servidor, o entornos de DR para sistemas tradicionales sobre servidores virtuales.
