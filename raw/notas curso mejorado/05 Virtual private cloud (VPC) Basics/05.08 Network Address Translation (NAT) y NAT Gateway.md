# Network Address Translation (NAT) y NAT Gateway

### Qué es NAT

**NAT** (*Network Address Translation*) es un conjunto de procesos distintos que pueden modificar los paquetes IP cambiando su dirección de origen o de destino. Ya se vio un tipo de NAT con el Internet Gateway, que funciona como un **static NAT**: traduce la IP privada de un recurso a su IP pública.

Cuando la gente piensa en NAT, en general piensa en un subconjunto llamado **IP masquerading**, que oculta todo un bloque de IPs privadas detrás de una única IP pública. Es decir, en lugar de traducir una IP privada a una IP pública, como hace el Internet Gateway, se traducen **muchas IPs privadas a una sola IP**. Esta técnica es popular porque las direcciones IPv4 se están agotando. En el resto de la nota, "NAT" se refiere a IP masquerading.

NAT le da a todo un rango de IPs privadas **acceso solo saliente** a la internet pública y a la AWS Public Zone. Esta es la parte más importante: como muchas IPs privadas usan una sola IP pública, el acceso entrante no funciona. Los dispositivos que usan NAT pueden iniciar conexiones salientes a internet o a los servicios de la AWS Public Zone, y esas conexiones pueden recibir datos de respuesta, pero no se pueden iniciar conexiones desde la internet pública hacia el espacio de direcciones privado.

Históricamente hay dos formas de implementar NAT en AWS: usar instancias EC2 configuradas para hacer NAT (**NAT instance**), o usar el servicio gestionado **NAT Gateway**, que se aprovisiona en una VPC y ofrece la misma funcionalidad.

> [!tip] Para el examen: para qué sirve NAT
> El caso clásico: instancias en **subnets privadas** que necesitan **salir** a internet (bajar parches, llamar a una API externa) pero que **no** deben ser accesibles desde afuera. NAT les da salida sin exponerlas. Si además necesitan hablar con servicios de AWS (S3, DynamoDB) sin salir a internet, la respuesta suele ser un **VPC Endpoint**, no NAT.

### Arquitectura de ejemplo

Por ejemplo, hay instancias de la aplicación (subnet APP) que necesitan salir a internet para actualizar software, pero, por arquitectura, no queremos que se pueda llegar a ellas desde afuera, porque es un tier oculto.

Para resolverlo se aprovisiona un NAT Gateway en una public subnet. Recordemos que la public subnet permite usar IPs públicas y tiene asociada una route table con la default route IPv4 apuntando al Internet Gateway. Como el NAT Gateway está en esa public subnet (la subnet web), puede enviar y recibir datos de la internet pública. Después, la route table de la private subnet se configura para que apunte al NAT Gateway.

El diagrama de ejemplo (VPC `10.16.0.0/16` en `us-east-1`):

- **Subnet APP** (`10.16.32.0/20`, privada, no enrutable públicamente): instancias `i-01` (`10.16.32.10`), `i-02` (`10.16.32.20`) e `i-03` (`10.16.32.30`). Su route table envía `0.0.0.0/0` al NAT Gateway.
- **Subnet WEB** (`10.16.48.0/20`, pública): tiene el NAT Gateway, con una IPv4 pública. Su route table envía `0.0.0.0/0`, a través del VPC Router, al Internet Gateway.
- El Internet Gateway, en la AWS Public Zone, conecta con la internet pública.

### NAT Gateway
- **Tiene que ejecutarse desde una public subnet**, porque necesita que se le asigne una IPv4 pública propia. Por eso, para implementar un NAT Gateway, la VPC ya tiene que tener public subnets, y para eso hace falta un Internet Gateway, subnets configuradas para asignar IPv4 pública y default routes en esas subnets apuntando al Internet Gateway.
- **Usa Elastic IPs** (IPv4 públicas estáticas): IPs estáticas que no cambian. Se asignan a tu cuenta en una región y se pueden usar para lo que quieras hasta que las liberes. Los NAT Gateways usan estas Elastic IPs.
- **Es un servicio AZ resilient** (alta disponibilidad dentro de esa AZ), no regional. Para tener un servicio totalmente resiliente en la región, al nivel de la alta disponibilidad que da el Internet Gateway, hay que implementar **un NAT Gateway en cada AZ** que use la VPC, y una **route table** para las private subnets de cada AZ con el NAT Gateway de esa AZ como target. Es decir, por cada AZ que se use hace falta un NAT Gateway y una route table que apunte a él.
- **Es un servicio gestionado:** lo implementas y AWS se encarga del resto. Puede escalar hasta **100 Gbps** de ancho de banda, y siempre se pueden implementar varios NAT Gateways y repartir las subnets entre ellos: si se necesita más ancho de banda, se agregan más NAT Gateways.
- **Costo:** se cobra por duración (tiempo de uso) y por volumen de datos procesados.


**Para el examen (importante):** el NAT Gateway es resiliente a nivel de AZ, no de región. Si falla la AZ donde está, no hay failover a otra AZ. No es como el Internet Gateway, que sí es resiliente a nivel regional. Si quieres resiliencia regional, tienes que poner un NAT Gateway en cada AZ.

> [!warning] Revisar
> Esto vale para el NAT Gateway clásico (que ahora AWS llama *zonal*). En noviembre de 2025 AWS lanzó un modo de disponibilidad regional: un único NAT Gateway que se expande y se contrae automáticamente entre las AZs de la VPC según dónde haya recursos, y que no necesita una public subnet. Verificar cómo lo trata la versión actual del examen.

### NAT instance vs NAT Gateway

| Atributo | NAT Gateway | NAT instance |
| --- | --- | --- |
| Availability | Alta disponibilidad: los NAT Gateways de cada AZ se implementan con redundancia. Hay que crear un NAT Gateway en cada AZ para tener una arquitectura independiente de la zona | Hay que usar un script para gestionar el failover entre instancias |
| Bandwidth | Escala hasta 45 Gbps | Depende del ancho de banda del tipo de instancia |
| Maintenance | Lo gestiona AWS; no hay que hacer mantenimiento | La gestionas tú, por ejemplo instalando actualizaciones de software o parches del sistema operativo |
| Performance | Software optimizado para manejar tráfico NAT | Una AMI genérica de Amazon Linux configurada para hacer NAT |
| Cost | Según la cantidad de NAT Gateways, el tiempo de uso y la cantidad de datos que se envían a través de ellos | Según la cantidad de NAT instances, el tiempo de uso y el tipo y tamaño de instancia |
| Type and size | Oferta uniforme: no hay que elegir tipo ni tamaño | Hay que elegir el tipo y tamaño de instancia según la carga de trabajo prevista |
| Security groups | No se pueden asociar a un NAT Gateway; se asocian a los recursos que están detrás para controlar el tráfico entrante y saliente | Se asocian a la NAT instance y a los recursos que están detrás para controlar el tráfico entrante y saliente |
| Network ACLs | Se usa una NACL para controlar el tráfico hacia y desde la subnet donde está el NAT Gateway | Se usa una NACL para controlar el tráfico hacia y desde la subnet donde está la NAT instance |
| Flow logs | Se usan flow logs para capturar el tráfico | Se usan flow logs para capturar el tráfico |
| Port forwarding | No soportado | Se puede personalizar la configuración manualmente para soportarlo |
| Bastion servers | No soportado | Se puede usar como bastion server |

La NAT instance es una **instancia EC2**, y para que funcione hay que **deshabilitar los Source/Destination Checks**. Por defecto, una instancia EC2 solo acepta el tráfico cuyo origen o destino es ella misma; una NAT instance tiene que reenviar tráfico de otras instancias, por eso hay que desactivar ese chequeo.

> [!tip] Para el examen: cuál elegir
> Por defecto, elegí **NAT Gateway** (gestionado, alta disponibilidad en la AZ, sin mantenimiento). Se elige NAT instance solo por casos puntuales que están en la tabla: necesitás **port forwarding**, usarla también como **bastion**, o abaratar en cargas chiquitas. Y recordá el detalle técnico: en una NAT instance hay que **deshabilitar el source/destination check**; en un NAT Gateway no, porque es gestionado.

### NAT e IPv6

- NAT no es necesario para IPv6.
- Todas las direcciones IPv6 en AWS son **públicamente enrutables**.
- El Internet Gateway funciona directamente con **todas** las IPv6.
- Los **NAT Gateways no funcionan con IPv6**.
- Route `::/0` + **Internet Gateway** → conectividad bidireccional.
- Route `::/0` + **Egress-Only Internet Gateway** → solo salida (*outbound only*).

> [!note] Egress-Only Internet Gateway
> Es el "equivalente a NAT pero para IPv6": permite que recursos con IPv6 inicien conexiones **salientes** a internet, pero impide que desde internet inicien conexiones hacia ellos. Es **stateful**. Como en IPv6 no hay direcciones privadas (todas son públicas), no se puede usar NAT para "ocultar"; el Egress-Only IGW cumple ese rol de "solo salida".

> [!warning] Revisar
> Según la documentación actual de AWS, el NAT Gateway sí procesa tráfico IPv6 en un caso: hace NAT64, que junto con DNS64 permite que recursos IPv6 se comuniquen con destinos IPv4. Lo que sigue valiendo es que para dar salida a internet por IPv6 no hace falta NAT: se usa el Internet Gateway o el Egress-Only Internet Gateway.
