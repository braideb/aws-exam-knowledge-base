# VPC Endpoints

Un **VPC Endpoint** permite conectar tu VPC de forma privada con servicios de AWS, sin necesidad de Internet Gateway, NAT, VPN ni Direct Connect. El tráfico no sale a la internet pública: se queda dentro de la red de AWS. Hay dos tipos.

> [!note] Dónde encaja esto
> Servicios como S3, DynamoDB o SQS viven en la **AWS Public Zone** (ver [[01.01 Servicios públicos vs. privados|Servicios públicos vs. privados]]), no dentro de tu VPC. Sin endpoints, una instancia en una **subnet privada** solo puede llegar a ellos saliendo por un [[05.08 Network Address Translation (NAT) y NAT Gateway|NAT Gateway]] hacia la internet pública. El VPC Endpoint es el atajo privado que evita ese rodeo.

### Gateway Endpoints

- Sirven **solo para S3 y DynamoDB**.
- Funcionan agregando una **route** en la route table de la subnet (a través de una *prefix list* que representa al servicio); no son un dispositivo dentro de la subnet.
- **No tienen costo** adicional.
- Se controlan con una **endpoint policy** (una policy de tipo recurso que limita a qué se puede acceder).
- **No** se puede acceder a ellos desde fuera de la VPC (no sirven desde on-premises).

> [!note] Cómo se ve la ruta
> El target de la ruta es el propio endpoint (`vpce-xxxx`) y el destino es una **prefix list** (`pl-xxxx`), que es un alias del conjunto de rangos IP públicos del servicio en esa región. Como es una ruta más específica que `0.0.0.0/0`, gana por [[longest-prefix-match|longest prefix match]] frente a la default route que apunta al NAT Gateway (ver [[05.04 VPC Routing e Internet Gateway#Prioridad de las routes|Prioridad de las routes]]).

### Interface Endpoints

- Sirven para **casi todos los demás servicios** de AWS (SQS, SNS, Kinesis, API Gateway, CloudWatch, Systems Manager, etc.) y también para S3.
- Están basados en **AWS PrivateLink**: colocan una [[eni|ENI]] con una IP privada dentro de una subnet que elegís (una por AZ para alta disponibilidad).
- Como son una ENI, se protegen con **Security Groups** (ver [[05.07 VPC Security Groups (SGs)|VPC Security Groups]]).
- Tienen **costo por hora y por GB** procesado.
- Usan **DNS privado**: al activarlo, el nombre normal del servicio (por ejemplo `sqs.us-east-1.amazonaws.com`) resuelve a la IP privada del endpoint, así que la app no necesita cambiar nada.
- **Sí** se puede acceder a ellos desde on-premises (vía VPN o Direct Connect), a diferencia de los gateway endpoints.

> [!note] Si no activás el DNS privado
> El endpoint igual te da un **nombre DNS propio** (del estilo `vpce-....sqs.us-east-1.vpce.amazonaws.com`) que hay que usar explícitamente en la app o en el SDK. Activar el private DNS es lo que hace que el cambio sea **transparente** para el código: por eso, si una pregunta dice "sin modificar la aplicación", la respuesta incluye *private DNS enabled*.

> [!warning] Revisar
> El curso presenta los interface endpoints como **solo TCP sobre IPv4**. Hoy AWS ofrece endpoints **dualstack** (IPv4/IPv6) para varios servicios, y el tipo de dirección se elige al crearlo. La idea de fondo (es una ENI con IP privada dentro de tu subnet) no cambia.

> [!tip] Para el examen: la comparación que cae
> | | Gateway Endpoint | Interface Endpoint |
> | --- | --- | --- |
> | Servicios | **Solo S3 y DynamoDB** | Mayoría de servicios (+ S3) |
> | Cómo funciona | Ruta en la route table | [[eni\|ENI]] con IP privada (PrivateLink) |
> | Seguridad | Endpoint policy | Security Group (+ policy) |
> | Costo | Gratis | Por hora + por GB |
> | Desde on-premises | No | Sí |
>
> Reglas rápidas: **DynamoDB → solo Gateway Endpoint**. **S3 → los dos** (Gateway si es solo desde la VPC y gratis; Interface si necesitás acceso desde on-premises o DNS privado). Si la pregunta dice "acceder a S3/DynamoDB desde una subnet privada sin NAT y sin costo" → Gateway Endpoint.

> [!note] Un tercer tipo que casi no cae en el DVA
> Existe también el **Gateway Load Balancer Endpoint**, que redirige el tráfico hacia appliances de seguridad de terceros. Aparece en exámenes de arquitectura/networking, no en el DVA-C02; alcanza con saber que existe para no confundirlo con el Gateway Endpoint de S3/DynamoDB.
