# Stateful vs Stateless Firewalls

### Conexiones TCP

![[Pasted image 20260918030815.png]]

TCP es un protocolo basado en conexiones. La conexión se establece entre dos dispositivos usando un puerto aleatorio en el cliente (**ephemeral port**, en la imagen `tcp/23060`) y un puerto conocido en el servidor (**well-known port**, en la imagen `tcp/443`). Una vez establecida, la conexión es bidireccional. Es una conexión confiable, que se logra mediante segmentos encapsulados en paquetes IP:

- Los **segmentos** TCP están vinculados a una conexión y tienen control de errores, orden y retransmisión: si el cliente no confirma que recibió un segmento, ese segmento se retransmite.
- Los **paquetes de capa 3** (IP), por sí solos, no tienen control de errores, ni orden, ni asociación entre ellos.

### Request y response

![[Pasted image 20260918031126.png]]

Lo que la mayoría imagina es una única conexión saliente, por ejemplo por HTTPS (`tcp/443`). Pero toda conexión tiene dos partes, el **request** (la iniciación) y la **response**. Lo que pasa realmente es:

1. El cliente (la laptop de Bob) elige un puerto de origen temporal, el **ephemeral port**, entre 1024 y 65535 (depende del sistema operativo).
2. El cliente inicia la conexión hacia el servidor, a un **well-known port** de destino: HTTPS, `tcp/443`.
3. El servidor responde usando como puerto de origen `tcp/443` y como puerto de destino el ephemeral port que eligió el cliente.

Una conexión queda identificada por la IP de origen, la IP de destino, el puerto de origen y el puerto de destino.

![[Pasted image 20260918031126.png]]

Que una parte sea *inbound* u *outbound* depende de la perspectiva (cliente o servidor):

| Parte de la conexión | Perspectiva del cliente | Perspectiva del servidor |
| --- | --- | --- |
| Request: `119.18.36.73:13337` → `1.3.3.7:443` | Outbound | Inbound |
| Response: `1.3.3.7:443` → `119.18.36.73:13337` | Inbound | Outbound |

### Stateless firewall

Un **stateless firewall** no entiende el estado de las conexiones. Ve el request (de la laptop de Bob al servidor de Catagram) y la response (del servidor de Catagram a la laptop de Bob) como dos partes independientes, y hay que pensar en permitir o denegar cada una por separado. Por eso se necesitan **dos reglas por conexión**: en este caso, una inbound rule para el request y una outbound rule para la response. Lo mismo pasa cuando es el servidor el que inicia una conexión (por ejemplo, para descargar actualizaciones de software): son otras dos reglas más en el firewall.

Cosas importantes de los stateless firewalls:

- En cualquier servidor que acepta conexiones y que además las inicia (algo común en los servidores web, que tienen que aceptar conexiones de clientes pero también hacer actualizaciones de software), hay que manejar dos reglas para cada una de esas situaciones, y una tiene que ser la inversa de la otra.
- La response va a un **ephemeral port**, no al well-known port de la aplicación. Por eso no alcanza con permitir las conexiones TCP al puerto 443 para el request: el firewall también tiene que permitir el rango de ephemeral ports para la response.

Todo esto hace que los stateless firewalls sean difíciles de administrar; lo ideal es usar stateful firewalls.

![[Pasted image 20260918032056.png]]

| Caso | Request | Response | Reglas |
| --- | --- | --- | --- |
| Aplicación entrante (Bob → servidor) | `119.18.36.73:1337` → `1.3.3.7:443` (inbound) | `1.3.3.7:443` → `119.18.36.73:1337` (outbound) | 1 inbound + 1 outbound |
| Actualizaciones salientes (servidor → `133.33.33.7`) | `1.3.3.7:12345` → `133.33.33.7:443` (outbound) | `133.33.33.7:443` → `1.3.3.7:12345` (inbound) | 1 outbound + 1 inbound |

### Stateful firewall

Un **stateful firewall** es lo suficientemente inteligente para identificar que el request y la response de una conexión están relacionados. Por lo general, solo hay que permitir (o no) el request, y la response se permite (o no) automáticamente: si se permite el request, sea inbound u outbound, la response se permite sola. Así se reduce el trabajo de administración (*lower admin overhead*).

![[Pasted image 20260918032310.png]]

En AWS, el **Security Group es stateful** y la **NACL es stateless**. Es de las cosas más preguntadas del examen. Traducción práctica: en un SG, si permitís el request no hace falta regla para la response; en una NACL, sí tenés que permitir explícitamente los **ephemeral ports** para la vuelta.
