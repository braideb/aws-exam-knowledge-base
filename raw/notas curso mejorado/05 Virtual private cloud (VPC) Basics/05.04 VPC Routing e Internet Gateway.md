# VPC Routing e Internet Gateway

La idea de esta nota es ver cómo funciona el routing dentro de una VPC e introducir el concepto de **Internet Gateway**, que es la forma de configurar una VPC para que los datos puedan salir hacia la AWS Public Zone y la internet pública, y entrar desde ahí.

### VPC Router

- El **VPC Router** es un dispositivo de alta disponibilidad que está presente en todas las VPCs, tanto en la Default VPC como en las custom VPCs, y mueve el tráfico de un lugar a otro.
- Funciona en todas las AZs que usa la VPC. No hay que preocuparse por su disponibilidad en cada AZ: siempre funciona.
- Tiene una network interface en cada subnet de la VPC, en la dirección network + 1.
- Por defecto, en una custom VPC sin ninguna otra configuración, el VPC Router simplemente enruta el tráfico entre las subnets de esa VPC. Si una instancia EC2 de una subnet quiere comunicarse con algo en otra subnet, el VPC Router es el que mueve el tráfico entre las dos.

### Route tables

El VPC Router se puede controlar creando **route tables**, que influyen en qué hacer con el tráfico cuando sale de una subnet. Es decir: la route table asociada a una subnet define qué hace el VPC Router con los datos que salen de esa subnet.

- Toda VPC se crea con una **main route table**. Si no le asocias explícitamente una custom route table a una subnet, la subnet usa la main route table de la VPC.
- Si le asocias a una subnet una route table que creaste, la main route table queda desasociada de esa subnet.
- Una subnet solo puede tener una route table asociada, pero una route table puede estar asociada a muchas subnets.

**Para el examen:** las route tables están asociadas a 0 o más subnets, y una subnet siempre tiene que tener una route table: la main route table de la VPC o una custom route table que hayas creado.

Evitá meterle rutas a internet a la main route table: si algún día creás una subnet nueva y te olvidás de asociarle una route table, hereda la main, y no querés que una subnet "se vuelva pública sin querer". Práctica común: dejá la main route table sin rutas hacia el IGW y usá custom route tables explícitas para las subnets públicas.

## Route Tables: prioridad de routes
Cuando un paquete sale de una subnet, el VPC Router busca en la route table la entrada cuyo `Destination` coincide con la IP de destino. Si hay más de una coincidencia, gana la ruta **más específica** (longest prefix match): cuanto más alto el número después del `/`, más chico el rango y más prioridad tiene.

### Ejemplo

|   |   |
|---|---|
|Destination|Target|
|`10.16.0.0/16`|local|
|`0.0.0.0/0`|Internet Gateway|

- Un paquete hacia `10.16.32.10` (una instancia de la subnet APP) coincide con las dos routes: con `10.16.0.0/16` y con `0.0.0.0/0`, que abarca todas las IPv4. Gana `10.16.0.0/16`, porque `/16` es más específico que `/0`, así que el tráfico se queda dentro de la VPC (local).
- Un paquete hacia `1.3.3.7` (un servidor en internet) solo coincide con `0.0.0.0/0`, así que se envía al Internet Gateway.

### Local routes
Las local routes siempre están presentes en toda route table y cubren el tráfico dentro del CIDR de la VPC. Por defecto tienen la máxima prioridad y no se modifican — aunque existen excepciones avanzadas (ver más abajo).

## Excepción: routes más específicas que la local route
La documentación actual de AWS matiza la regla de que la local route "siempre tiene prioridad y no se puede modificar". Hay dos casos avanzados a tener en cuenta:

### 1. Agregar una route más específica que la local route
Es posible, con condiciones estrictas:
- El `Destination` debe ser el **CIDR completo de una subnet** de la VPC (no un rango arbitrario más chico).
- El `Target` solo puede ser: **NAT Gateway**, **network interface (ENI)**, o **Gateway Load Balancer endpoint**.

Ejemplo:

|   |   |
|---|---|
|Destination|Target|
|172.31.0.0/16|local|
|172.31.0.0/20|eni-xxxx|

Acá tenés **dos** filas para direcciones que están dentro de la VPC. La VPC entera es `172.31.0.0/16` (todo lo que empieza con `172.31.`). Pero dentro de esa VPC hay una subnet más chica, `172.31.0.0/20` (un subconjunto de esas direcciones).

Seguimos dos paquetes:

- Paquete hacia `172.31.5.10` → esta IP cae dentro de `172.31.0.0/20` (la subnet chica) **y** también dentro de `172.31.0.0/16` (la VPC entera). Coinciden las dos filas. Gana la más específica: `/20`. Entonces el target es `eni-xxxx`, no `local`. Este paquete se desvía a la interfaz de red (el firewall, por ejemplo) en lugar de ir directo por el camino normal.
- Paquete hacia `172.31.200.5` → esta IP cae dentro de `172.31.0.0/16` pero **no** dentro de `172.31.0.0/20` (está fuera de ese rango chico). Solo coincide una fila: `local`. Este paquete va por el camino normal, sin pasar por el ENI.

Entonces: es una ruta **extra**, más quirúrgica, que solo agarra a una subnet puntual y la desvía. El resto de la VPC sigue funcionando como siempre (`local`).

### 2. Reemplazar el target de la local route
Esto aplica sobre todo a las **gateway route tables** (las asociadas a un Internet Gateway o Virtual Private Gateway, no a subnets). Ahí se puede hacer que todo el tráfico destinado a la VPC pase primero por una appliance de seguridad antes de llegar a destino, y luego restaurarlo al comportamiento local por defecto.

|                 |          |
| --------------- | -------- |
| Destination     | Target   |
| `172.31.0.0/16` | eni-xxxx |

Acá hay **una sola fila**, y es la que cubre toda la VPC. No dice `local` en ningún lado — directamente se cambió qué significa esa fila.

Seguimos un paquete:
- Paquete hacia `172.31.5.10` (o cualquier IP dentro de `172.31.0.0/16`) → solo hay una fila que coincide, y su target es `eni-xxxx`. **Todo** el tráfico dentro de la VPC, sin excepción, pasa por esa interfaz de red primero.

Acá no hay elección entre "más específico" ni nada — es que la ruta que normalmente sería `local` ahora apunta a otro lado.


### La diferencia en una frase
- **Caso 1**: le agregás una excepción puntual a una parte de la VPC, dejando `local` intacto para el resto.
- **Caso 2**: le cambiás el comportamiento a _toda_ la VPC de una — ya no hay ningún `local` en la tabla.

### ¿Por qué existe esto?

El caso de uso principal es **traffic inspection**: se quiere que cierto tráfico intra-VPC (o todo el tráfico entrante) pase por un firewall, IDS/IPS o proxy antes de llegar a destino, en vez de ir directo por la ruta local. Es funcionalidad avanzada; para el nivel introductorio, la regla simplificada ("la local route siempre gana y no se toca") es una buena base, pero conviene saber que tiene excepciones.
### Internet Gateway

El **Internet Gateway (IGW)** es una de las funciones adicionales más importantes de una VPC:

- Es un gateway **region resilient** que se asocia (*attach*) a una VPC. Una vez asociado, es válido en todas las AZs de la VPC.
- **1 VPC = 0 o 1 IGW, y 1 IGW = 0 o 1 VPC.** Una VPC puede no tener Internet Gateway, lo que la hace totalmente privada, o tener uno: esas son las dos opciones. Un Internet Gateway se puede crear sin asociarlo a ninguna VPC (cero attachments), pero solo puede estar asociado a una VPC a la vez.
- Funciona en el borde entre la VPC y la AWS Public Zone (según la diapositiva, corre dentro de la AWS Public Zone).
- Hace de gateway del tráfico entre la VPC y la internet o la AWS Public Zone: permite que los servicios de la VPC que tienen IPv4 pública o IPv6 sean accesibles desde internet, y que se conecten a la AWS Public Zone o a internet. La AWS Public Zone se usa, por ejemplo, al acceder desde la VPC a S3, SQS, SNS o cualquier otro servicio público de AWS.
- Es un servicio **gestionado**: AWS se encarga de la performance. Desde tu perspectiva como arquitecto, simplemente funciona.

### Cómo usar un Internet Gateway (public subnets)

![[Pasted image 20260918015716.png]]

Usar un Internet Gateway en una VPC es simple:

1. **Crear el Internet Gateway.**
2. **Asociarlo (attach) a la VPC.** Así queda disponible para usarse dentro de la VPC y se puede usar como target en las route tables.
3. **Crear una custom route table.**
4. **Asociarla a la subnet**, en este caso la subnet web (`10.16.48.0/20` en el diagrama).
5. **Agregar las default routes** a la route table: `0.0.0.0/0` para IPv4 y, opcionalmente, `::/0` para IPv6, con el Internet Gateway como target.
6. **Configurar la subnet para que asigne IPv4 pública** por defecto y, opcionalmente, IPv6.

Una vez hechas todas estas acciones, la subnet se considera una **public subnet**: cualquier servicio de la subnet con IP pública puede comunicarse con internet y viceversa, y también con la AWS Public Zone, siempre que no haya otras restricciones de seguridad en juego.

Si una instancia en una subnet supuestamente pública no tiene conectividad, revisá esta checklist en orden: (1) ¿la VPC tiene un IGW asociado?, (2) ¿la route table de la subnet tiene `0.0.0.0/0` → IGW?, (3) ¿la instancia tiene IPv4 pública o Elastic IP?, (4) ¿el Security Group permite el tráfico saliente/entrante?, (5) ¿la NACL de la subnet lo permite en ambos sentidos? Un solo eslabón que falte tira abajo la conectividad.

### IPv4 pública e Internet Gateway

Ejemplo de cómo funciona IPv4 con un Internet Gateway: una instancia EC2 Linux quiere hacer una actualización de software desde un servidor de actualizaciones de Linux que está en algún lugar de la internet pública.

![[Pasted image 20260918020157.png]]

A la izquierda está la instancia, en el medio el Internet Gateway y a la derecha el servidor de actualizaciones (`1.3.3.7`). Conceptualmente, se podría pensar que la instancia tiene una IP privada, por ejemplo `10.16.16.20`, y además una IPv4 pública asignada, `43.250.192.20`. Pero no es así como funciona realmente.

![[Pasted image 20260918020436.png]]

Lo que pasa en realidad es que las IPv4 públicas nunca llegan al recurso dentro de la VPC. Cuando le asignas una IPv4 pública a una instancia EC2, el Internet Gateway crea y mantiene un registro que vincula la IP privada de la instancia con su IP pública asignada. La instancia en sí no tiene configurada la IP pública: por eso, si le asignas una IPv4 pública a una instancia EC2, dentro del sistema operativo solo se ve la IP privada.

**Para el examen:** tener en cuenta este detalle, porque hay preguntas que intentan hacerte tropezar con él.

**De la instancia a internet:**

![[Pasted image 20260918020527.png]]

1. La instancia envía el paquete con Source `10.16.16.20` y Destination `1.3.3.7`.
2. El Internet Gateway reemplaza el Source por la IP pública asociada: Source `43.250.192.20`, Destination `1.3.3.7`.
3. El servidor recibe el paquete con Source `43.250.192.20`.

**De internet a la instancia:**

![[Pasted image 20260918020654.png]]

1. El servidor responde con Source `1.3.3.7` y Destination `43.250.192.20`.
2. El Internet Gateway reemplaza el Destination por la IP privada asociada, `10.16.16.20`.
3. La instancia recibe el paquete con Source `1.3.3.7` y Destination `10.16.16.20`.

El IGW hace un NAT **estático uno-a-uno** (una privada ↔ una pública) y permite tráfico **entrante y saliente**. El NAT Gateway (más adelante) hace NAT **de muchos-a-uno** y solo permite tráfico **saliente**. Los dos "traducen" direcciones, pero resuelven problemas distintos.
## Bastion host y jumpbox

Bastion host y jumpbox son lo mismo: una instancia en una **public subnet** dentro de una VPC, usada como punto de entrada para conexiones de administración. Todas las conexiones entrantes de gestión llegan a esa instancia y, una vez conectado, desde ahí se accede a los recursos internos (privados) de la VPC.

```
Vos (internet) → SSH → Bastion host (subnet pública) → SSH → Instancia privada (subnet privada)
```

### Uso típico

- Punto de gestión o punto de entrada exclusivo a VPCs privadas de alta seguridad.
- Se puede configurar para aceptar solo conexiones desde IPs determinadas, autenticación SSH, o integración con un servidor de identidad on-premises.

### Por qué es mala práctica
El problema central: hay una instancia con el puerto 22 abierto a internet de forma permanente. Aunque se restrinja por IP o se use autenticación fuerte, esto implica:

- Superficie de ataque expuesta 24/7
- Claves SSH que hay que rotar y proteger
- Punto único de falla: si se cae o se compromete, se pierde (o se filtra) el acceso administrativo

### Alternativa recomendada: AWS Systems Manager Session Manager

Session Manager invierte la dirección de la conexión: la instancia **sale** hacia el servicio de SSM (conexión saliente), en vez de recibir conexiones entrantes. Requiere:

1. El **SSM Agent** corriendo en la instancia (viene preinstalado en la mayoría de las AMIs de Amazon)
2. Un **IAM role** con permisos para SSM

Con eso, se abre una shell a la instancia desde la consola o CLI de AWS, sin abrir el puerto 22, sin bastion host y sin manejar claves SSH. Además, toda la sesión queda auditada en CloudTrail/CloudWatch.

### Regla de examen

Si la pregunta pide **acceso administrativo seguro y sin puertos abiertos** → la respuesta es **Session Manager**, no bastion host.
