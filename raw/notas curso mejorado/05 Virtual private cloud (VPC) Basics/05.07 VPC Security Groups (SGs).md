# VPC Security Groups (SGs)

Los **Security Groups (SGs)** son otra función de seguridad de la VPC, pero, a diferencia de las NACLs, se asocian a recursos de AWS y no a subnets. Frente a las NACLs tienen algunas ventajas: pueden reconocer recursos de AWS y filtrar en base a ellos, y pueden referenciar a otros SGs e incluso a sí mismos. Pero los SGs no pueden bloquear tráfico explícitamente, así que muchas veces necesitan la ayuda de las NACLs.

Los SGs y las NACLs comparten muchos conceptos generales, pero su forma de operar es diferente.

### Características

**Stateful.** Los SGs detectan automáticamente el tráfico de response: si se permite un request (IN u OUT), la response se permite automáticamente.

**Sin explicit deny.** Los SGs tienen una limitación importante: no existe el explicit deny. Solo se puede permitir tráfico (ALLOW) o no permitirlo, lo que se conoce como **implicit deny**: si no permites un tráfico explícitamente, lo estás denegando implícitamente. Pero, y esto es importante, no se puede denegar tráfico explícitamente con un SG, así que **no sirven para bloquear a actores maliciosos específicos**.

Por ejemplo: permites que cualquier IP se conecte a una instancia por el puerto 443, pero después descubres que un único actor malicioso está intentando explotar el servidor. No puedes usar un SG para bloquear esa IP o ese rango específico: si permites una IP, un rango de IPs o incluso todas las IPs, un SG no puede denegar un subconjunto de ellas. Por eso, normalmente se usa una NACL junto con el SG: las NACLs se usan para agregar los explicit deny.

**Referencias a recursos lógicos.** Los SGs operan por encima de las NACLs en el modelo OSI de 7 capas, lo que significa que tienen más funciones. Soportan reglas basadas en IPs y CIDR, pero también permiten referenciar recursos lógicos de AWS dentro de las reglas, incluidos otros Security Groups e incluso el propio SG.

> [!warning] Revisar
> La idea del curso es que los SGs tienen más funciones porque entienden recursos lógicos de AWS. Ojo con leerlo como que operan en la capa 7 (aplicación): tanto los SGs como las NACLs filtran por IP, protocolo y puerto, y ninguno inspecciona el contenido de la aplicación (por ejemplo, HTTP).

**Se asocian a ENIs.** Los SGs no están vinculados a las instancias ni conectados a las subnets, sino a **Elastic Network Interfaces (ENIs)** específicas, aunque la consola lo muestre como si estuvieran asociados a la instancia.

> [!tip] Para el examen: comportamiento y límites del SG
> - Un SG tiene un **implicit deny** al final: lo que no está permitido, está bloqueado. No hay reglas de deny.
> - **Default Security Group** de una VPC: permite todo el tráfico entre recursos que tengan ese mismo SG (regla self-reference) y todo el saliente. Un SG **nuevo/custom** arranca **sin reglas inbound** y con una regla outbound que permite **todo**.
> - Podés asociar **varios SGs a una misma ENI**: las reglas se suman (si alguno permite el tráfico, pasa).
> - Se pueden referenciar SGs de otra VPC conectada por **VPC Peering** (en la misma región).

- El SG está asociado a la **ENI primaria** de la instancia y se aplica a todo el tráfico que entra o sale de esa ENI.
- Tiene una inbound rule que permite HTTPS (TCP 443) desde `0.0.0.0/0` (descripción: *inbound HTTPS*).
- Como los SGs son stateful, el flujo de response se permite automáticamente si el request está permitido.
- Si "Bob" en realidad es un actor malicioso, la regla que permite `tcp/443` no se puede anular: no hay explicit deny.

### Logical references

En lugar de referenciar una dirección IP como source, se referencia otro Security Group, que representa a una aplicación o tier (en el ejemplo, el SG `a4l-web` de la capa web). Esto tiene otro beneficio: escala bien cuando hay muchas instancias y reduce el trabajo de administración.

![[Pasted image 20260918044517.png]]

- Bob se conecta a las instancias WEB (subnet `10.16.48.0/20`) por `tcp/443`, y las instancias WEB se conectan a las instancias APP (subnet `10.16.32.0/20`) por `tcp/1337`.
- **SG de WEB:** inbound rule HTTPS, TCP, puerto 443, source `0.0.0.0/0` (*inbound HTTPS*).
- **SG de APP:** inbound rule Custom TCP, TCP, puerto 1337, source `sg-0140ed8a682241126 / a4l-web` (*inbound from a4l-web*). Es decir, la regla del SG de APP referencia al SG de WEB.
- Escala solo: cualquier instancia nueva que use el SG de WEB puede comunicarse con cualquier instancia que use el SG de APP.

### Self references

La referencia lógica permite todavía más cosas, como las **self references**. Dentro de un SG, usar otro SG como source significa "cualquier cosa que tenga ese SG asociado"; una self reference significa "cualquier cosa que tenga **este** SG asociado".

Ejemplo: una private subnet con un número de instancias de aplicación que cambia constantemente (ahora son tres, pero pueden ser treinta o una). Se crea un SG (`a4l-app`) con dos inbound rules:

| Type | Protocol | Port range | Source | Descripción |
| --- | --- | --- | --- | --- |
| All traffic | All | All | `sg-013c186f459555252 / a4l-app` (el propio SG) | free comms between SG |
| Custom TCP | TCP | 1337 | `sg-0140ed8a682241126 / a4l-web` | inbound from a4l-web |

- La primera es la regla **self-referencing**: permite todo el tráfico desde el propio SG. Si el SG está asociado a todas las instancias de la aplicación, cualquier instancia con ese SG puede recibir todo el tráfico de las demás instancias que también lo tengan.
- La segunda permite las comunicaciones entrantes en TCP 1337 desde el SG de web.
- Esto escala con las altas y bajas de instancias en el SG, y los cambios de IP se gestionan automáticamente, porque las instancias siguen estando dentro del SG.
- Casos de uso: comunicación interna de una aplicación, como Microsoft Domain Controllers o aplicaciones en alta disponibilidad (*App HA*).

## Security Group vs NACL (tabla de examen)

Esta comparación es la que más se pregunta. Vale la pena tenerla clavada:

|                     | Security Group                             | NACL                                                    |
| ------------------- | ------------------------------------------ | ------------------------------------------------------- |
| Opera a nivel de    | ENI (recurso: instancia, RDS, etc.)        | Subnet                                                  |
| Estado              | **Stateful** (la response se permite sola) | **Stateless** (regla para request y para response)      |
| Reglas              | Solo **ALLOW** (deny implícito)            | **ALLOW** y **DENY** explícitos                         |
| Evaluación          | Se evalúan todas; si algo permite, pasa    | En orden por número; la primera que coincide gana       |
| Referencias lógicas | Sí (otros SGs, self-reference)             | No, solo IP/CIDR                                        |
| Cuántos aplican     | Varios SGs por ENI                         | Una NACL por subnet                                     |
| Caso de uso típico  | Permitir tráfico entre tiers/recursos      | Bloquear IPs/rangos específicos; control a nivel subnet |
  

> [!tip] Para el examen: cómo se combinan
> El tráfico que entra a una instancia en una subnet pasa **primero por la NACL de la subnet y después por el SG de la ENI**. Para que una conexión funcione, **los dos** tienen que permitirla. Si algo "debería andar y no anda", revisá los dos niveles: NACL (acordate de la response por ephemeral ports) y SG.
