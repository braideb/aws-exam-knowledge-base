# Network Access Control Lists (NACLs)

Una **Network Access Control List (NACL)** es una capa de seguridad opcional de la VPC que actúa como firewall para controlar el tráfico que entra y sale de una o más subnets. Se pueden configurar NACLs con reglas similares a las de los Security Groups para agregar una capa extra de seguridad a la VPC. La lección recorre las características de las NACLs, el impacto de que sean stateless y algunos puntos clave para el examen.

### Cómo funciona una NACL

Una NACL se puede pensar como un firewall tradicional disponible en las VPCs de AWS:

- Las NACLs están asociadas a subnets: cada subnet tiene una NACL asociada, que filtra los datos cuando cruzan el límite de esa subnet. En la práctica, afecta a todos los datos que entran a la subnet y a todos los que salen.
- **Importante:** las conexiones entre recursos dentro de una misma subnet (por ejemplo, entre las instancias A y B de la imagen) no se ven afectadas por las NACLs.

### Reglas

- Cada NACL contiene dos conjuntos de reglas: las **inbound rules**, que solo afectan a los datos que entran a la subnet, y las **outbound rules**, que afectan a los datos que salen de la subnet.
- Cada regla coincide con un rango de IPs (en la consola aparece como *Source* en las inbound rules y como *Destination* en las outbound rules), un puerto o rango de puertos y un protocolo, y según eso hace un **ALLOW** o un **DENY** explícito del tráfico.
- Las reglas se procesan **en orden**. Según si el tráfico entra o sale, se aplican las inbound o las outbound rules, empezando por el **número de regla más bajo**. El tráfico se evalúa contra cada regla hasta encontrar una que coincida; en ese momento el tráfico se permite o se deniega y **el procesamiento se detiene**.
- Por eso, si el tráfico coincide con dos reglas y una lo deniega y la otra lo permite, se aplica la de número más bajo (la que aparece más arriba en la lista).
- La regla `*` es un **implicit deny**: si no coincide ninguna otra regla, el tráfico se deniega.

Dejá huecos entre los números de regla (100, 200, 300…) para poder insertar reglas en el medio después. Y recordá el orden: gana la de **número más bajo** que coincida, y ahí se corta la evaluación. Una regla DENY con número bajo le gana a una ALLOW con número más alto. AWS recomienda numerar de a 100.

### Las NACLs son stateless

Las NACLs son **stateless**: tanto el request como la response de cada comunicación necesitan su propia regla (1 inbound y 1 outbound).

![[Pasted image 20260918041645.png]]

Ejemplo: Bob se conecta por HTTPS (`tcp/443`) a una instancia de la subnet WEB. La NACL de la subnet WEB necesita:

| Regla | Type | Protocol | Port range | Source / Destination | Acción | Para qué |
| --- | --- | --- | --- | --- | --- | --- |
| Inbound 110 | HTTPS (443) | TCP (6) | 443 | Source `0.0.0.0/0` | Allow | Request de Bob |
| Outbound 120 | Custom TCP | TCP (6) | 1024-65535 | Destination `0.0.0.0/0` | Allow | Response hacia los ephemeral ports de Bob |

En las dos listas, además, está la regla `*` que deniega todo lo demás.

![[Pasted image 20260918042020.png]]

Como cada comunicación necesita una regla para el request y otra para la response, si la instancia WEB además se comunica con una instancia de la subnet APP por el puerto de la aplicación, hacen falta reglas en las dos NACLs:

- **NACL de WEB:** una outbound rule para el request hacia APP (puerto de la aplicación) y una inbound rule para la response desde APP (ephemeral ports, `tcp/1024-65535`).
- **NACL de APP:** una inbound rule para el request desde WEB (puerto de la aplicación) y una outbound rule para la response hacia WEB (ephemeral ports).

Estos pares de reglas (puerto de la aplicación y ephemeral ports) hacen falta en cada NACL para cada tipo de comunicación: 1) dentro de la VPC, 2) hacia la VPC o 3) desde la VPC.

### Default NACL

Cuando se crea una VPC, también se crea una **Default NACL**. Sus inbound y outbound rules tienen el implicit deny (`*`), pero también una regla que permite todo (regla 100: *All traffic*, `0.0.0.0/0`, Allow). El efecto neto es que se permite todo el tráfico, así que la NACL no tiene efecto: AWS prefiere que esto se gestione con Security Groups.

![[Pasted image 20260918042216.png]]

### Custom NACLs

Se pueden crear **custom NACLs** para una VPC específica. Inicialmente no están asociadas a ninguna subnet y solo tienen una regla, tanto en las inbound como en las outbound rules: el implicit deny (`*`). Si se asocia esa NACL a una subnet, se deniega todo el tráfico.

### Consideraciones generales

- Son **stateless**: el request y la response se ven como cosas distintas.
- Solo afectan a los datos que **cruzan el límite de la subnet**.
- Pueden hacer **ALLOW y DENY explícitos**.
- Trabajan con IPs/CIDR, puertos y protocolos, **no con recursos lógicos**.
- No se pueden asignar a recursos de AWS, **solo a subnets**.
- Se usan junto con los Security Groups para agregar **DENY explícitos** (IPs o redes maliciosas).
- Cada subnet puede tener **una sola NACL** (la default o una custom).
- Una NACL puede estar asociada a **muchas subnets**.

El caso de uso estrella es **bloquear una IP o un rango específico** (un atacante, un país), porque el SG no puede hacer DENY explícito. También sirven como red de seguridad a nivel de subnet. Pero para el permitir/denegar del día a día entre recursos, AWS prefiere los Security Groups.
