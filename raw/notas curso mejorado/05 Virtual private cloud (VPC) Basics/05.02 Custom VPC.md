# Custom VPC

### Diseño final de la sección

Esto es lo que se va a terminar implementando a lo largo de la sección:

![[Pasted image 20260910011836.png]]

Una VPC `10.16.0.0/16` en `us-east-1`. El diseño tiene lugar para 4 AZs, es decir, 16 subnets posibles, pero solo se usan 3 AZs (A, B y C) y el espacio de la cuarta queda libre por las dudas (*spare capacity for future AZ*). En cada una de esas AZs se crean los tiers Reserved, DB (base de datos), APP (aplicación) y WEB, cada uno en una subnet /20 (los CIDR blocks de cada subnet están en la tabla de la demo de [[05.03 VPC Subnets|VPC Subnets]]). En el diagrama, las subnets WEB son public subnets (verdes) y las de DB y APP son private subnets (azules).

Además de la VPC y de las subnets, que se crean en las lecciones siguientes, a medida que avanza la sección se va a:

- Crear un **Internet Gateway**, que les da acceso público a los recursos de la VPC.
- Crear **NAT Gateways**, que les dan a las instancias privadas acceso solo saliente. En el diseño hay uno en cada subnet WEB.
- Crear un **bastion host**, que es una de las formas de conectarse a la VPC (en el diseño está en la subnet WEB B). Usar bastion hosts está mal visto y no es la mejor práctica de seguridad; se hace para entender el concepto, y a medida que avance el curso se van a mostrar mejores prácticas.
- Ver las **Network Access Control Lists (NACLs)**, que se usan para proteger la VPC.
- Ver los **costos de transferencia de datos** de todo lo que se mueve dentro y alrededor de la VPC.

### Default VPC vs Custom VPC

Cada región de una cuenta trae una **Default VPC** ya armada y lista para lanzar recursos sin configurar nada. En cambio, una **custom VPC** la creás y configurás vos de cero. Esta diferencia es un clásico de examen:

|                         | Default VPC                                | Custom VPC                                        |
| ----------------------- | ------------------------------------------ | ------------------------------------------------- |
| Cantidad                | Una por región (se puede borrar y recrear) | Hasta 5 por región (límite ampliable)             |
| CIDR                    | Siempre `172.31.0.0/16`                    | El que elijas (/16 a /28)                         |
| Subnets                 | Una `/20` pública por AZ, creada sola      | Ninguna hasta que las crees; privadas por defecto |
| Internet Gateway        | Ya viene creado y asociado                 | Lo creás y asociás vos                            |
| Auto-assign public IPv4 | Activado en las subnets default            | Desactivado por defecto                           |
| Uso típico              | Pruebas rápidas, laboratorios              | Producción, diseños serios                        |

> [!tip] Para el examen Si una pregunta dice que una instancia recibió IP pública y salió a internet "sin configurar nada", casi seguro está en la **Default VPC**. En una custom VPC eso no pasa solo: hay que crear el IGW, la route table, la ruta `0.0.0.0/0` y activar el auto-assign de IPv4 pública. Además, muchos servicios (como una instancia RDS "de prueba") caen en la Default VPC si no especificás otra.

### Características de una custom VPC

Algunos aspectos a tener en cuenta antes de empezar a crear todo:

- **Servicio regional:** las VPCs son un servicio aislado a nivel regional y resiliente a nivel de región (*regionally isolated and region resilient*). Una VPC se crea en una región y opera en todas las AZs de esa región.
- **Redes aisladas:** permiten crear redes aisladas dentro de AWS; incluso en una sola región de una cuenta se pueden tener muchas redes aisladas (*isolated networks*).
- **Nada entra ni sale** de una VPC sin una configuración explícita.
- **Hybrid networking:** las custom VPCs permiten conectar la VPC con sistemas on-premises.
- **Tenancy:** al crear la VPC se elige entre **Default** y **Dedicated** tenancy. Esto controla si los recursos creados dentro de la VPC se aprovisionan en hardware compartido o en hardware dedicado. Si eliges Dedicated, todo lo que lances en la VPC tiene que estar en hardware dedicado, y eso es bastante más caro.
- **IPs privadas y públicas:** la VPC usa CIDR blocks IPv4 privados e IPs públicas. Internamente todo usa direcciones privadas, y las IPs públicas se usan cuando hay que comunicarse con el exterior.

### Direccionamiento IP de la VPC

- A toda VPC se le asigna obligatoriamente **un CIDR block IPv4 privado primario**, que se configura al crear la VPC. Tiene dos restricciones: como mínimo **/28** (16 IPs) y como máximo **/16** (65536 IPs).
- Opcionalmente, se pueden agregar **CIDR blocks IPv4 secundarios**.
- Opcionalmente, se puede configurar 5 CIDR block IPv6 /56** asignado (*optional single assigned IPv6 /56 CIDR block*) por VPC e incluso se puede ampliar a 50.

### DNS en la VPC

Las VPCs tienen un DNS completo, provisto por **Route 53**. Dentro de la VPC está disponible en la **IP base de la VPC + 2**: por ejemplo, si la VPC es `10.0.0.0`, la IP del DNS es `10.0.0.2`.

Hay dos opciones de configuración clave:

- **enableDnsHostnames:** indica si las instancias con IP pública en la VPC reciben un nombre de host DNS público. Si está en `true`, lo reciben; si está en `false`, no.
- **enableDnsSupport:** indica si el DNS está activado o desactivado en la VPC. Si está activado, las instancias de la VPC pueden usar el DNS en la IP base de la VPC + 2; si está en `false`, ese DNS no está disponible.
