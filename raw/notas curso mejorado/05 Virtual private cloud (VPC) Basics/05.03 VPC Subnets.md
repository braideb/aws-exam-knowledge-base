# VPC Subnets

Las subnets son la forma de agregarle estructura, funcionalidad y resiliencia a una VPC.

### Diseño de la lección

Para ver el tema se usa el diseño de VPC que se viene trabajando: la VPC `a4l-vpc1`, con el CIDR block `10.16.0.0/16` y un rango IPv6 asignado, en `us-east-1`.

En los diagramas de AWS, el azul indica una private subnet y el verde, una public subnet. Las subnets de una VPC comienzan siendo totalmente privadas y necesitan alguna configuración para volverse públicas. Por eso, en este punto, incluso las subnets de la derecha (el tier WEB) se crean como private subnets.

### Qué es una subnet

Una subnet es una parte de la VPC que está dentro de una Availability Zone específica: es un elemento **AZ resilient** de la VPC. Se crea dentro de una AZ y eso nunca se puede cambiar. Como funciona dentro de esa AZ, si la AZ falla, la subnet falla, y lo mismo pasa con cualquier servicio alojado solo en esa subnet.

**Para el examen (pregunta importante):** una subnet se crea en una AZ específica de la región, eso nunca se puede cambiar, y una subnet nunca puede estar en varias AZs. En cambio, una AZ puede tener cero, una o muchas subnets.

La diferencia no es un "tipo" de subnet, sino su configuración. Una subnet es **pública** cuando cumple tres cosas a la vez: (1) su route table tiene una ruta `0.0.0.0/0` hacia un **Internet Gateway**, (2) la subnet tiene activado el auto-assign de IPv4 pública (o el recurso tiene una Elastic IP) y (3) los SG/NACL permiten el tráfico. Si le falta la ruta al IGW, es **privada**. Este patrón (web pública ↔ app/db privadas ↔ salida por NAT) es el que más se repite en el examen.

### CIDR blocks de una subnet

- **IPv4:** por defecto, la subnet usa IPv4 y se le asigna un CIDR block IPv4. Ese CIDR block es un subconjunto del CIDR block de la VPC (tiene que estar dentro del rango asignado a la VPC) y no puede superponerse con el de otras subnets de la VPC.
- **IPv6 (opcional):** a una subnet se le puede asignar un CIDR block IPv6, siempre que la VPC también tenga IPv6 habilitado. A cada subnet se le asigna un rango **/64**, que es un subconjunto del **/56** de la VPC. Entre /56 y /64 hay 8 bits de diferencia, así que un /56 tiene lugar para 2⁸ = **256 rangos /64**, uno por cada subnet que lo use.

Por defecto, las subnets de una VPC pueden comunicarse con las demás subnets de la misma VPC.

### IPs reservadas en cada subnet

Hay **5 IPs en cada subnet** que no se pueden usar porque ya están asignadas. Ejemplo con la subnet `10.16.16.0/20`, que va de `10.16.16.0` a `10.16.31.255`:

| IP | Nombre | Uso |
| --- | --- | --- |
| `10.16.16.0` | Network address | Es la dirección inicial y representa a la red |
| `10.16.16.1` | Network + 1 | La usa el **VPC Router**, el dispositivo lógico que mueve datos entre subnets (si está configurado para permitirlo). El VPC Router tiene una network interface en cada subnet y usa esta dirección |
| `10.16.16.2` | Network + 2 | Se usa para **DNS** |
| `10.16.16.3` | Network + 3 | Reservada para **uso futuro** |
| `10.16.31.255` | Broadcast address | Última IP de la subnet. Broadcast no está soportado en una VPC, pero igual se reserva |

Por lo tanto, una subnet que debería tener 16 IPs tiene, en realidad, 11 utilizables.

Regla rápida: **IPs usables = 2^(32 − prefijo) − 5**. Una subnet /24 no tiene 256 usables sino 251; una /28 tiene 11. Y ojo: la mínima subnet posible es /28 justamente porque con menos de 16 IPs las 5 reservadas no dejarían espacio útil.

### DHCP Options Set

A cada VPC se le aplica una configuración mediante un objeto llamado **DHCP Options Set**. DHCP (*Dynamic Host Configuration Protocol*) es la forma en que los dispositivos reciben direcciones IP automáticamente.

- Hay un solo DHCP Options Set aplicado a una VPC a la vez, y esa configuración se propaga a sus subnets.
- Controla cosas como los servidores DNS, los servidores NTP, los servidores NetBIOS y algunas otras.
- Se puede cambiar qué DHCP Options Set está vinculado a la VPC y se pueden crear nuevos, pero los DHCP Options Sets **no se pueden editar**.

#### ¿Qué problema resuelve?

Cuando lanzás una instancia EC2 dentro de una VPC, esa instancia necesita una dirección IP, y también necesita saber cosas como "¿a qué servidor le pregunto para resolver nombres de dominio (DNS)?" o "¿con qué servidor sincronizo la hora?". Normalmente esto se configuraría a mano en cada máquina, pero DHCP automatiza ese proceso: cuando la instancia arranca, "pregunta" por la red y recibe automáticamente su configuración de red.

#### ¿Qué es el DHCP Options Set entonces?

Es básicamente **la plantilla de configuración de red** que le decís a AWS que use para responder esas preguntas DHCP a todas las instancias de tu VPC. Incluye parámetros como:

- **domain-name-servers**: qué servidores DNS deben usar las instancias (por defecto usa el DNS interno de AWS, llamado `AmazonProvidedDNS`)
- **domain-name**: el sufijo de dominio por defecto
- **ntp-servers**: servidores de sincronización horaria
- **netbios-name-servers** y **netbios-node-type**: para resolución de nombres estilo Windows/NetBIOS (raramente usado hoy en día)

#### Los puntos clave

**1. Una VPC tiene un solo DHCP Options Set a la vez**

Es una relación 1 a 1. La VPC apunta a un Options Set, y automáticamente todas las subnets (y por lo tanto todas las instancias) dentro de esa VPC heredan esa configuración. No podés tener subnets distintas con DNS distintos dentro de la misma VPC usando este mecanismo.

**2. No se pueden editar, solo reemplazar**

Este es el punto que más confunde a la gente. Los Options Sets son **inmutables**: una vez creados, no podés modificar sus valores. Si necesitás cambiar, por ejemplo, el servidor DNS que usa tu VPC, el flujo es:

1. Creás un **nuevo** DHCP Options Set con los valores que querés
2. Asociás ese nuevo set a tu VPC (reemplazando al anterior)
3. El anterior queda "huérfano" — podés eliminarlo si ya no lo usa ninguna VPC

Es un patrón parecido al de los Security Groups inline rules vs. versiones nuevas: en vez de mutar, se reemplaza el objeto completo.

**3. ¿Por qué importa esto en la práctica?**

El caso de uso típico es cuando tenés DNS propio (por ejemplo, un Active Directory con su propio servidor DNS, o algo tipo Route 53 Resolver con reglas custom) y querés que las instancias en tu VPC usen ese DNS en lugar del DNS por defecto de Amazon. Ahí creás un Options Set custom apuntando a tus servidores DNS.

### Opciones de asignación de IP de una subnet

En cada subnet también se pueden definir dos opciones importantes de asignación de IP:

- Una controla si a los recursos de la subnet se les asigna automáticamente una **IPv4 pública**.
- La otra hace lo mismo con **IPv6**.

En la demo se implementa todo esto.

Desde el 1 de febrero de 2024, AWS cobra por hora **cada IPv4 pública en uso** (aprox. USD 0,005/hora), incluidas las de instancias EC2 y las Elastic IPs, estén o no asociadas. En laboratorios esto es centavos, pero es un cambio reciente y puede aparecer en preguntas de optimización de costos: una forma de ahorrar es no asignar IPv4 pública a recursos que no la necesitan (que salgan por NAT o por VPC Endpoints) o migrar a IPv6.

### Duda de la demo - el CIDR block IPv6 de cada subnet

![[Pasted image 20260918012418.png]]

En la captura se crea la subnet `sn-db-A`:

- **IPv4 subnet CIDR block:** `10.16.16.0/20` (4096 IPs).
- **IPv6 CIDR block:** *Manual input* (la otra opción, *No IPv6 CIDR*, deja la subnet sin IPv6).
- **IPv6 VPC CIDR block:** el /56 de la VPC donde va a estar la subnet, `2600:1f18:3985:9600::/56`.
- **IPv6 subnet CIDR block:** el /64 de la subnet, `2600:1f18:3985:9601::/64`.

Cómo se obtiene ese /64: una dirección IPv6 tiene 128 bits, escritos como 8 grupos de 4 dígitos hexadecimales separados por `:`. Cada grupo son 16 bits y cada dígito, 4 bits. El `::` abrevia uno o más grupos seguidos de ceros.

- El **/56 de la VPC** fija los primeros 56 bits: los 3 primeros grupos más los 2 primeros dígitos del 4.º grupo (`2600:1f18:3985:96`).
- El **/64 de la subnet** fija los primeros 64 bits, o sea, los 4 grupos completos. Los 8 bits de diferencia son **los 2 últimos dígitos del 4.º grupo**, y son los que se eligen para cada subnet: de `00` a `FF`, 256 opciones.
- Esos dos dígitos son el **CustomIPv6Value** del documento de la demo (los corchetes solo marcan los dígitos que cambian):

```
VPC       2600:1f18:3985:96[00]::/56
sn-db-A   2600:1f18:3985:96[01]::/64   ← el de la captura
sn-app-A  2600:1f18:3985:96[02]::/64
sn-web-C  2600:1f18:3985:96[0B]::/64
```

- Los valores son hexadecimales: después de `09` vienen `0A`, `0B`, … `0F`, y después `10`. Por eso sn-app-C es `0A` y sn-web-C es `0B`.
- AWS asigna un /56 distinto a cada VPC, así que en tu cuenta el prefijo va a ser otro. La lógica es la misma: solo cambian los 2 últimos dígitos del 4.º grupo.
- Probablemente el documento lo llama *CustomIPv6Value* porque en versiones anteriores de la consola solo se escribían esos dos dígitos. En la consola actual se ve el bloque completo, así que hay que verificar que termine en el valor que corresponde.
- `18.4Q IPs` es la cantidad de direcciones de un /64: 2⁶⁴, unos 18,4 quintillones en la escala inglesa (en español serían unos 18 trillones).
