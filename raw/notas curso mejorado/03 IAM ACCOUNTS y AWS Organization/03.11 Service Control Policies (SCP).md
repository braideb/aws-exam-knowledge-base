# Service Control Policies (SCP)
Los **SCPs** son la funcionalidad de Organizations que permite **restringir accesos**.
### Qué son

Un **documento de policy en JSON** (mismo formato que las identity policies) que se puede adjuntar a:
- El **Organization Root** → afecta a **toda** la organización.
- Una **Organizational Unit (OU)** → afecta a todas las cuentas de esa OU.
- Una **cuenta individual** de AWS.

Los SCPs se **heredan hacia abajo** en el árbol de la organización.

Para poder usarlos, la organización tiene que estar en modo **"all features"**. Si se creó en modo _consolidated billing only_, hay que habilitarlo primero (requiere que todas las cuentas miembro lo aprueben).

### La excepción crítica

> [!danger] La Management Account NUNCA es afectada por los SCPs Sin importar dónde adjuntes el SCP, la **management account** queda exenta.
> 
> **Por eso la buena práctica es no tener recursos en la management account.** Si los tuvieras, quedarían fuera de todos tus controles de seguridad organizacionales. La management account es un agujero permanente en tus defensas — la mantenés vacía para que ese agujero no importe.

### Lo más importante de entender: **los SCPs NO conceden permisos**

Un SCP es un **account permissions boundary** (límite de permisos de la cuenta). **Limita lo que una cuenta de AWS puede hacer**, incluyendo lo que puede hacer su **Account Root User**.

Pero **no le da permisos a nadie**. Solo define un **techo**.

Que alcance al Account Root User es la propiedad más valiosa de los SCPs: es **el único mecanismo de AWS capaz de limitar al root user** de una cuenta. Ninguna IAM policy puede hacerlo. Por eso los SCPs son la herramienta de gobierno por excelencia.

**Analogía: el reglamento del edificio vs. tu contrato**

Imaginate que trabajás en una oficina dentro de un edificio corporativo.

- El **SCP** es el **reglamento del edificio**: "en este edificio está prohibido entrar al subsuelo". No importa quién seas.
- La **Identity Policy** es tu **contrato de trabajo**: "Juan tiene autorización para acceder al subsuelo y al piso 5".

> [!tip] Analogía: el reglamento del edificio vs. tu contrato
> 
> Imaginate que trabajás en una oficina dentro de un edificio corporativo.
> 
> - El **SCP** es el **reglamento del edificio**: "en este edificio está prohibido entrar al subsuelo". No importa quién seas.
> - La **Identity Policy** es tu **contrato de trabajo**: "Juan tiene autorización para acceder al subsuelo y al piso 5".
> 
> ¿Juan puede entrar al subsuelo? **No.** Su contrato lo autoriza, pero el reglamento del edificio lo prohíbe.
> 
> ¿Y si el reglamento dice "se permite entrar al subsuelo" pero el contrato de Juan no lo menciona? **Tampoco entra.** El reglamento no te da permisos; solo dice qué está _permitido en principio_.
> 
> **Necesitás las dos cosas: que el SCP lo permita Y que la identity policy lo permita.**

### Ejemplo concreto

Un SCP típico: **restringir el tamaño máximo de instancia EC2** que se puede lanzar en una cuenta.

Así, aunque un desarrollador tenga `AdministratorAccess` en su cuenta de desarrollo, no puede lanzar una instancia de $30/hora "para probar" y fundir el presupuesto. El SCP se lo impide, y **ni siquiera el root user de esa cuenta puede saltárselo**.

Otros SCPs que aparecen en casi todas las organizaciones reales:

Nadie puede apagar la auditoría. Este es probablemente el SCP más importante que existe: sin él, un atacante con permisos de admin simplemente apaga CloudTrail y se vuelve invisible.
```json
{
    "Effect": "Deny",
    "Action": ["cloudtrail:StopLogging", "cloudtrail:DeleteTrail"],
    "Resource": "*"
}
```

Restricción de regiones: solo se puede operar en dos regiones. Notar que hay que exceptuar los servicios globales, porque técnicamente se invocan contra `us-east-1` y bloquearlos rompería IAM.
```json
{
    "Effect": "Deny",
    "NotAction": ["iam:*", "s3:*", "cloudfront:*", "route53:*", "support:*"],
    "Resource": "*",
    "Condition": {
        "StringNotEquals": { "aws:RequestedRegion": ["us-east-1", "sa-east-1"] }
    }
}
```

Que una cuenta no pueda escaparse de la organización (y de sus controles).
```json
{
    "Effect": "Deny",
    "Action": ["organizations:LeaveOrganization"],
    "Resource": "*"
}
```


Los SCPs también aceptan condiciones, y una muy usada es `aws:PrincipalArn`, para hacer excepciones: "denegar a todos menos al rol de automatización".

### Límites a tener en cuenta

- Máximo **5 SCPs** adjuntos a cada entidad (root, OU o cuenta).
- Tamaño máximo de **5.120 caracteres** por SCP.
- La profundidad de anidamiento de OUs es de **5 niveles**.

El límite de tamaño se alcanza más rápido de lo que parece cuando se enumeran servicios, y es una de las razones por las que la estrategia de _deny list_ resulta más práctica.

### Allow List vs. Deny List

Hay dos estrategias para usar SCPs.
#### Deny List (el default, y el recomendado)

Cuando habilitás SCPs en la organización, AWS aplica automáticamente una policy llamada **`FullAWSAccess`** al root y a todas las OUs:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "*",
            "Resource": "*"
        }
    ]
}
```

O sea: **por defecto viene todo permitido**. Vos vas **agregando restricciones** con policies de `Deny`:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Deny",
            "Action": "s3:*",
            "Resource": "*"
        }
    ]
}
```

Y como ya sabemos, **el DENY explícito le gana al ALLOW explícito**. Resultado: todo permitido, excepto S3.

#### Allow List (más seguro, más trabajo)

Se **quita** la policy `FullAWSAccess` y se reemplaza por una que enumere **exactamente** qué está permitido:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "s3:*",
                "ec2:*"
            ],
            "Resource": "*"
        }
    ]
}
```

Sin `FullAWSAccess`, todo lo que no esté explícitamente permitido cae en **Default Deny**. Resultado: solo S3 y EC2, nada más.

#### Comparación

|Criterio|Deny List|Allow List|
|---|---|---|
|**Default**|✅ Sí, es lo que AWS aplica|No|
|**Seguridad**|Menor|**Mayor** — tenés que declarar todo|
|**Carga administrativa**|**Baja**|Alta|
|**Riesgo**|Un servicio nuevo de AWS queda permitido sin que lo pienses|Bloqueás sin querer servicios que sí necesitabas|

> [!tip] Recomendación Se recomienda la **Deny List** para el uso general, justamente **para administrar menos**. La allow list es más segura pero te obliga a mantener una lista exhaustiva de servicios permitidos, y cada vez que un equipo necesita un servicio nuevo tenés que actualizarla.


### Cómo diagnosticar un bloqueo por SCP

Cuando algo falla y sospechás de un SCP, el error suele ser un `AccessDenied` genérico que **no menciona el SCP** (por diseño, para no filtrar información sobre la estructura de la organización). Las herramientas:

- El **Policy Simulator** no evalúa SCPs, así que no sirve acá.
- En la consola de Organizations, cada cuenta muestra las **políticas efectivas** heredadas.
- Verificar si la acción funciona desde la **management account**: si ahí funciona y en la cuenta miembro no, con casi total seguridad es un SCP.
