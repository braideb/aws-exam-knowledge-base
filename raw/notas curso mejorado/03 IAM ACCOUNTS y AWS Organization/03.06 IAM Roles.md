# IAM Roles

Este es el concepto más importante (si leiste las notas anteriores todo se resuelve con IAM Roles xd) y el que más cuesta. Vale la pena ir despacio.
### La idea central

Un **IAM Role** es un tipo de identidad que existe dentro de una cuenta de AWS, pero se usa de forma **completamente distinta** a un IAM User.

| Aspecto             | IAM User                                     | IAM Role                                                           |
| ------------------- | -------------------------------------------- | ------------------------------------------------------------------ |
| **Cuántos lo usan** | **Un solo principal** (una persona, una app) | Un número **desconocido / ilimitado** de principals                |
| **Duración**        | **Largo plazo**. Vos _sos_ ese usuario.      | **Corto plazo**. Vos _te **convertís_** en ese rol, temporalmente. |
| **Credenciales**    | Permanentes (password, access keys)          | **Temporales**, expiran y hay que renovarlas                       |

> [!important] La frase clave **"IAM Roles are assumed... you become that role."**
> 
> El rol **no te representa a vos**. Representa un **nivel de acceso** dentro de la cuenta. Otras identidades lo **asumen**, usan sus permisos durante un rato, y después lo dejan.

### Analogía: el casco de visitante

Imaginate una fábrica.

- Un **IAM User** es tu **credencial de empleado**. Tiene tu foto, tu nombre. Es tuya, permanente, y solo vos la usás.
- Un **IAM Role** es el **casco naranja de visitante** que está colgado en la entrada. No tiene nombre. Cualquiera que esté autorizado puede ponérselo, y mientras lo lleve puesto, tiene acceso al taller. Cuando termina, lo devuelve.

Ahora, dos preguntas obvias:

**¿Quién puede ponerse el casco?** → Eso lo define la **Trust Policy**.

**¿A qué puertas te abre el casco?** → Eso lo define la **Permissions Policy**.

### Las dos policies de un Role
Un role tiene **dos** documentos de policy, y son cosas distintas:

#### Trust Policy
Controla **qué entidades pueden asumir el rol**. Es, conceptualmente, **un muro alrededor del rol**.

Puede hacer referencia a:
- Identidades **en la misma cuenta** (otros users, otros roles).
- **Servicios de AWS** (ej: EC2, Lambda).
- Identidades **en otras cuentas de AWS**.
- Identidades **externas** (federación).

Si una identidad **no está permitida** por la trust policy, la operación `AssumeRole` **falla**. Punto.

Así se ve una trust policy que confía en el servicio EC2:
```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": { "Service": "ec2.amazonaws.com" },
            "Action": "sts:AssumeRole"
        }
    ]
}
```

Y una que confía en otra cuenta de AWS:
```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
            "Action": "sts:AssumeRole"
        }
    ]
}
```

Un detalle importante del segundo ejemplo: `:root` acá **no** significa el Account Root User. Significa "la cuenta 111122223333 completa", es decir, se delega en esa cuenta la decisión de qué identidades suyas pueden asumir el rol. Es otra de las reutilizaciones confusas de la palabra _root_.

#### Permissions Policy

Define **qué puede hacer** quien asuma el rol. Es una identity policy común y corriente: `Allow`/`Deny` sobre acciones y recursos.

La forma rápida de no confundirlas: la **trust policy mira hacia afuera** (quién entra), la **permissions policy mira hacia adentro** (qué puede tocar).

### Qué pasa cuando asumís un rol

1. Una identidad (A) pide asumir el rol.
2. AWS chequea la **Trust Policy**. Si A no está listada → falla.
3. Si A está listada → **STS** (Security Token Service) genera **Temporary Security Credentials**.
4. Esas credenciales son parecidas a las access keys, pero **caducan**.
5. Con esas credenciales, A puede hacer todo lo que dice la **Permissions Policy** del rol.
6. Cuando expiran, A tiene que volver a llamar a `sts:AssumeRole`.

La operación que hace todo esto se llama:

```
sts:AssumeRole
```

**Roles y resource policies**: los roles **sí** se pueden referenciar dentro de las policies de recursos (a diferencia de los grupos). Entonces: si un rol puede acceder a un bucket de S3 —ya sea porque una resource policy lo permite, o porque la permissions policy del rol lo permite— entonces **cualquiera que asuma ese rol podrá acceder a ese recurso**.

### Permission boundaries

Un concepto emparentado que conviene conocer: un **permission boundary** es una policy que se adjunta a un user o role y que define el **máximo** de lo que esa identidad puede hacer, sin otorgar nada por sí misma.

Los permisos efectivos son la **intersección** entre las identity policies y el boundary. Es exactamente la misma lógica de los SCPs, pero a nivel de identidad en vez de a nivel de cuenta.

El caso de uso típico: querés que un equipo pueda crear sus propios roles (para sus Lambdas, por ejemplo) sin que puedan crear un rol de administrador. Se les da permiso de crear roles **con la condición de que el rol nuevo lleve un boundary determinado**.
