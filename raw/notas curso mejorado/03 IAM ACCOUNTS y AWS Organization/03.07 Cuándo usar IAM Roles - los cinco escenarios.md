# Cuándo usar IAM Roles: Cinco escenarios de ejemplo

### 1. Servicios de AWS actuando en tu nombre (el caso más común)

**Escenario:** una función **Lambda** necesita escribir logs en CloudWatch (esto en realidad lo hace Lambda automáticamente, pero necesita permiso para hacerlo) y leer objetos de S3. (se da funciones lambda mas adelante pero son como las azure function de Azure)

Para que la función pueda hacer esto, necesita **credenciales de AWS**. La pregunta es: ¿de dónde salen esas credenciales?

#### La solución: Lambda Execution Role

Un **Execution Role** es un IAM Role que le "asignás" a la función Lambda cuando la creás. Tiene dos partes:

**1. Trust Policy (¿quién puede asumir el rol?)**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "lambda.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
```

Esto dice: "el servicio Lambda tiene permiso para asumir este rol". Sin esto, ni siquiera Lambda podría tomar el rol, aunque el rol tuviera los permisos de S3 y CloudWatch.

**2. Permission Policy (¿qué puede hacer una vez que lo asume?)**
```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents"
      ],
      "Resource": "arn:aws:logs:*:*:*"
    },
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::mi-bucket/*"
    }
  ]
}
```

#### ¿Qué pasa cuando la función se ejecuta?
1. Lambda (el servicio) llama a `sts:AssumeRole` internamente, usando la identidad del rol asignado a tu función.
2. STS (Security Token Service) responde con **credenciales temporales**: un Access Key ID, un Secret Access Key, y un Session Token, todos con una duración limitada.
3. Esas credenciales quedan disponibles para el código de tu función.
4. Tu código (usando el SDK de AWS) las usa automáticamente para llamar a S3 o escribir logs.

Nunca ves esas credenciales, nunca las escribís en ningún lado. Se generan solas, se usan, y expiran.

**¿Y si NO usáramos un rol?** Habría que **hardcodear access keys** dentro del código de la función Lambda. Eso es mala idea por dos razones:

**a) Riesgo de seguridad**: esas credenciales viven ahora en texto plano en tu código. Si subís ese código a un repo de GitHub por error (pasa todo el tiempo), quedan expuestas. Si tu backup se filtra, quedan expuestas. Si un log de debug las imprime, quedan expuestas. Y esas credenciales suelen tener permisos amplios y sin fecha de expiración.

**(b) Problema operativo**: las buenas prácticas de seguridad dicen que hay que rotar access keys periódicamente (por ejemplo, cada 90 días). Si las tenés hardcodeadas, rotar significa: generar la nueva key, editar el código, testear, y volver a desplegar la función. Es lento, propenso a errores, y si te olvidás, te quedás con keys viejas dando vueltas.

Con un role, no hay nada que rotar manualmente — las credenciales temporales se renuevan solas por detrás de escena.

**Regla de oro**: siempre que un servicio de AWS necesite acceso a otro servicio de AWS, usá un role. Nunca access keys.

Este patrón se repite en todos lados con nombres distintos: **execution role** en Lambda, **instance profile** en EC2, **task role** en ECS, **service role** en CodeBuild o CloudFormation. Es siempre lo mismo: el servicio asume un rol para actuar en tu nombre.

Un detalle práctico: la aplicación **no necesita cambiar nada** para aprovecharlo. Los SDK de AWS buscan credenciales en una cadena de proveedores y, al no encontrar nada configurado, terminan consultando el metadata de la instancia o la variable de entorno que inyecta Lambda. Por eso migrar de access keys a un rol suele ser simplemente **borrar la configuración de credenciales** y adjuntar el rol.

### 2. Emergencias — el "break glass" role

**Escenario:** Agus Pink trabaja en el helpdesk. Su grupo tiene acceso de solo lectura a la cuenta de AWS de un cliente. Eso está bien el 99% del tiempo — no necesita más que eso para su trabajo diario.

Pero en una emergencia (una caída de producción, un recurso mal configurado que hay que arreglar ya), Agus Pink necesita poder hacer cambios, no solo mirar.

**Solución:** un _Emergency Role_ que Agus Pink puede asumir puntualmente. Es literalmente el equivalente digital de la cajita roja que dice "BREAK GLASS FOR KEY": normalmente está ahí, sin usarse, pero cuando de verdad hace falta, está disponible — a costa de que todos se enteren de que la rompiste.

**Importante:** esto no es una feature nativa de AWS con un botón "Emergency Role" en la consola. Es un **patrón de arquitectura** que se construye combinando piezas normales de IAM: un rol con permisos elevados, una trust policy que dice quién puede asumirlo (en este caso, el grupo de Agus Pink), y unas cuantas capas extra de fricción y visibilidad a propósito, para que asumirlo sea una decisión consciente y no un permiso que se usa sin pensar.

**Ventajas de esta arquitectura sobre simplemente darle permisos altos a Agus Pink de forma permanente:**

- **El acceso elevado es temporal.** Las credenciales que obtiene al asumir el rol (vía `sts:AssumeRole`) expiran solas después de un rato corto (por ejemplo, 1 hora). No hay que acordarse de "sacarle" el permiso después — se vence solo.
- **Queda todo registrado.** CloudTrail loguea el momento exacto en que Agus Pink asumió el rol, y también cada acción que hizo mientras lo tenía activo. Si algo sale mal, hay trazabilidad completa de qué se cambió y quién lo cambió.
- **Es una decisión consciente, no un accidente.** Para operar con permisos de admin, Agus Pink tiene que hacer explícitamente el paso extra de "asumir el rol de emergencia" — típicamente con MFA de por medio. No anda con esos permisos todo el día por descuido, ni corre el riesgo de romper algo en la cuenta del cliente sin querer, porque en el día a día ni siquiera tiene esos permisos disponibles.

En la práctica, este patrón suele venir acompañado de una alerta automática (a Slack, a PagerDuty, etc.) cada vez que alguien asume el rol, precisamente para que el hecho de "romper el vidrio" no pase desapercibido.

### 3. Integrar AWS con un directorio corporativo existente

**Escenario:** una empresa ya tiene una red física y un **proveedor de identidades** existente (típicamente **Active Directory**) donde el personal se loguea a varios sistemas. Y tiene, digamos, 20.000 empleados.

**Dos problemas:**
- Superan el límite de **5.000 IAM users**.
- Nadie quiere mantener dos juegos de credenciales por persona.

**Solución:** **Identity Federation**. Las identidades de Active Directory asumen un **role** en AWS. Se logra **Single Sign-On (SSO)**.

**Las cuentas externas no se pueden usar directamente en AWS.** Una identidad de Active Directory no es una identidad de IAM. Lo único que puede hacer es **asumir un rol**, y el rol sí es una identidad de IAM. El rol es el puente.

### 4. Web Identity Federation

**Escenario:** una aplicación móvil popular (digamos, una app de ride sharing) tiene **millones de usuarios**, y necesita que cada uno lea y escriba sus datos en **DynamoDB**.

**Problemas:**
- Millones de usuarios >>> 5.000 IAM users.
- Para interactuar con un servicio de AWS se necesita **una identidad**.
- No podés meter credenciales de AWS en una app que se instala en teléfonos ajenos.

**Solución:** **Web Identity Federation**. Los usuarios se loguean con **Google, Facebook, Twitter**, etc. Esas _web identities_ asumen un **role** que tiene permisos sobre DynamoDB.

Ventajas:
- ✅ **No se almacenan credenciales de AWS en la app.**
- ✅ Aprovecha cuentas que los usuarios **ya tienen**. No necesitan crear una cuenta nueva.
- ✅ **Escala a cientos de millones** de usuarios.

### 5. Acceso entre múltiples cuentas de AWS

**Escenario:** tu cuenta tiene miles de identidades. Un partner tiene un bucket de S3 al que necesitás acceder.

**Solución:** el partner crea un **role** en _su_ cuenta, cuya trust policy confía en _tu_ cuenta. Tus identidades asumen ese rol y acceden al bucket.

> [!warning] Detalle importante: Object Owner Cuando tus usuarios suben objetos al bucket del partner **asumiendo un rol de la cuenta del partner**, los objetos quedan siendo propiedad de **la cuenta del partner**. Esto evita el problema clásico de "subí un archivo al bucket de otro y ahora ni el dueño del bucket puede leerlo".
