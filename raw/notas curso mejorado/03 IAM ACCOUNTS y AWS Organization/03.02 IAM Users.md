# IAM Users

Un **IAM User** es una identidad usada para cualquier cosa que requiera **acceso a AWS a largo plazo** y donde el número de identidades es **conocido y acotado**: seres humanos, aplicaciones, o cuentas de servicio.

Esa definición tiene dos condiciones y las dos importan. Si el acceso no es de largo plazo, o si el número de identidades no se conoce de antemano, la respuesta no es un IAM user: es un **role**. Esa bifurcación es la que se pregunta una y otra vez en el examen.

### Principal, autenticación y autorización

Estos tres términos se confunden todo el tiempo. Van en orden:

1. **Principal**: una persona o aplicación que **hace una solicitud** a IAM para interactuar con recursos. En este punto, IAM todavía **no sabe quién es** (por eso en el diagrama el principal aparece con un signo de interrogación).
    
2. **Authentication (autenticación)**: el principal se autentica contra una identidad dentro de IAM. Puede ser con:
    - **U&P** (username + password) → típicamente desde la consola.
    - **Access Keys** → típicamente desde CLI o API.
    Una vez autenticado, pasa a ser una **Authenticated Identity**.
    
3. **Authorization (autorización)**: IAM toma los **policy documents** asociados a esa identidad autenticada y decide si la acción solicitada está permitida.
    

> [!tip] Analogía
> 
> - **Principal** = alguien tocando el timbre del edificio. No sabés quién es.
> - **Authentication** = muestra la cédula. Ahora sabés que es tincho.
> - **Authorization** = Juan tiene llave del piso 3 y la parrilla pero no del depósito. Es tincho, sí, pero no puede entrar a cualquier lado.

### Password policy

A nivel de cuenta se puede configurar una **password policy** que aplica a todos los IAM users: longitud mínima, tipos de caracteres requeridos, expiración, si el usuario puede cambiarse la password solo, y cuántas passwords anteriores no puede reutilizar.

Un detalle práctico: si se activa la expiración de passwords, hay que darle al usuario permiso de `iam:ChangePassword` sobre sí mismo, o queda encerrado cuando le vence.

### Buenas prácticas

- **Un user por persona.** Nunca compartir credenciales entre humanos: si dos personas usan el mismo usuario, CloudTrail deja de servir para saber quién hizo qué.
- **Para aplicaciones que corren en AWS, no crear un user**: usar un rol. Un IAM user para una app solo se justifica cuando la app corre fuera de AWS y no puede usar Roles Anywhere ni federación.
- **MFA para todos los usuarios humanos**, no solo el root.
- **Revisar el credential report periódicamente** para detectar usuarios sin uso, sin MFA o con access keys viejas.
- Para organizaciones con varias cuentas, la dirección recomendada hoy es **IAM Identity Center** en lugar de crear IAM users por cuenta.

A diferencia de los grupos, los users **sí pueden aparecer como `Principal`** en una resource policy. Es la diferencia práctica más importante entre ambas entidades, y se explica en la nota de groups.
