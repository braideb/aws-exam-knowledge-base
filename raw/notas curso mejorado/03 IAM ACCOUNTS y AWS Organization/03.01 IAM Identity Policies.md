# IAM Identity Policies

### Arquitectura

Una **IAM Identity Policy** es simplemente un conjunto de **declaraciones de seguridad** que **conceden (Allow)** o **deniegan (Deny)** acceso a productos y funcionalidades de AWS, a cualquier identidad que use esa policy.

El documento se escribe en **JSON**:

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "FullAccess",
            "Effect": "Allow",
            "Action": ["s3:*"],
            "Resource": ["*"]
        },
        {
            "Sid": "DenyCatBucket",
            "Action": ["s3:*"],
            "Effect": "Deny",
            "Resource": ["arn:aws:s3:::catgifs", "arn:aws:s3:::catgifs/*"]
        }
    ]
}
```

### Anatomía de un statement

|Campo|Qué hace|
|---|---|
|**Sid**|_Statement ID_. **Opcional.** Es una etiqueta para que el lector humano entienda qué hace la declaración. No afecta el comportamiento.|
|**Effect**|`Allow` o `Deny`.|
|**Action**|Qué operaciones cubre. Ej: `s3:*` (todo S3), `s3:GetObject` (solo leer objetos).|
|**Resource**|Sobre qué recursos aplica. Se identifican por **ARN**.|
|**Condition**|**Opcional.** Restricciones extra que deben cumplirse para que el statement aplique.|
|**Principal**|Solo en **resource policies**: a quién aplica el statement. En las identity policies no existe, porque el principal ya es la identidad a la que está adjunta.|

**Sobre `Version`**: el `"Version": "2012-10-17"` **no** es la versión de tu policy. Es la versión del **lenguaje de policies de AWS**. Siempre va ese valor. No lo cambies.

### El campo Condition

Permite especificar circunstancias adicionales bajo las cuales el permiso (Allow o Deny) se aplica realmente.


```json
"Condition": {
    "OPERADOR": { "clave": "valor" }
}
```

Ejemplos que aparecen todo el tiempo:

Solo desde la red de la oficina.
```json
"Condition": {
    "IpAddress": { "aws:SourceIp": ["203.0.113.0/24"] }
}
```




Solo si el usuario se autenticó con MFA.
```json
"Condition": {
    "BoolIfExists": { "aws:MultiFactorAuthPresent": "true" }
}
```


Solo en esas dos regiones.

```json
"Condition": {
    "StringEquals": { "aws:RequestedRegion": ["us-east-1", "sa-east-1"] }
}
```


Solo sobre recursos etiquetados como `dev`. Esto es la base del **ABAC** (control de acceso basado en atributos), donde en vez de enumerar recursos uno por uno, se otorgan permisos por tags. Escala muchísimo mejor.
```json
"Condition": {
    "StringEquals": { "aws:ResourceTag/Environment": "dev" }
}
```



Operadores más usados: `StringEquals`, `StringLike` (acepta comodines), `ArnLike`, `IpAddress`, `NumericLessThan`, `DateGreaterThan`, `Bool`. Los que terminan en `IfExists` no fallan si la clave no está presente en la request, algo importante para no bloquear llamadas de servicios internos sin querer.

### Comodines y variables

- `*` reemplaza cualquier cantidad de caracteres; `?` reemplaza uno solo.
- `"Action": "s3:Get*"` cubre `GetObject`, `GetBucketPolicy`, etc.
- `"Resource": "arn:aws:s3:::logs-bucket-?` por si estan numerados ? seria 1, 2, 3 etc.
- Existen **variables de policy** que se resuelven en tiempo de evaluación. La más usada:


```json
{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::empresa-home/${aws:username}/*"
}
```

Una sola policy que le da a cada usuario acceso **únicamente a su propia carpeta** dentro del bucket. Sin variables, habría que escribir una policy por persona.

### NotAction y NotResource

Existen las versiones negadas de los campos, y se usan poco pero aparecen:

json

```json
{
    "Effect": "Deny",
    "NotAction": ["s3:*", "cloudwatch:*"],
    "Resource": "*"
}
```

Se lee como "denegar todo excepto S3 y CloudWatch". Son cómodas pero peligrosas: como incluyen implícitamente los servicios que AWS lance en el futuro, es fácil terminar con permisos más amplios (o más restrictivos) de lo que uno cree. La recomendación general es evitarlas salvo que haya un motivo claro.


### Regla de evaluación: el orden que hay que memorizar

Este es **el** concepto del módulo. AWS evalúa **todas** las policies aplicables y decide en este orden:

```
1. ¿Hay un Explicit DENY?  →  DENEGADO. Fin. No se discute.
2. ¿Hay un Explicit ALLOW? →  PERMITIDO.
3. Si no hay ninguno       →  Default DENY (implícito).
```

> [!tip] Analogía Pensalo como la lista de un baile:
> 
> - **Explicit DENY** = estás en la lista negra. No entrás, aunque seas el dueño del local, aunque tengas entrada VIP. Nada te salva.
> - **Explicit ALLOW** = estás en la lista de invitados. Entrás.
> - **Default DENY** = no estás en ninguna lista. No entrás, pero simplemente porque nadie te invitó, no porque te odien (mentira si te odian).

Aplicado al JSON de arriba: el primer statement te da acceso total a S3 (`s3:*` sobre `*`), pero el segundo te deniega explícitamente el bucket `catgifs`. **Resultado: podés hacer todo en S3 excepto tocar `catgifs`.** El DENY explícito le gana al ALLOW explícito, siempre.

> [!warning] Por qué importa tanto Un `Deny` explícito es **irrevocable** por otras policies. Esto es lo que hace que los **SCPs** (que veremos en la otra nota) y los _permission boundaries_ funcionen como topes duros de seguridad.

Notá también que en el JSON los dos statements se **superponen**: ambos cubren `catgifs`. El primero por comodín (`*`), el segundo por nombre. No hay conflicto que resolver por orden de aparición — el DENY gana sin importar si está primero o último en el array.

### La cadena completa de evaluación

La regla de tres pasos es la versión simplificada, y alcanza para la mayoría de las preguntas. La versión completa suma las otras capas que pueden intervenir, en este orden:

1. **Deny explícito** en cualquier capa → denegado, se termina la evaluación.
2. **SCPs** (si la cuenta está en una organización) → tiene que permitirlo, si no, denegado.
3. **Resource policy** → si permite explícitamente, puede alcanzar por sí sola (en la misma cuenta).
4. **Permission boundary** → si existe, la acción tiene que estar dentro del límite.
5. **Session policy** → si las credenciales vienen de STS con una session policy, también tiene que permitirlo.
6. **Identity policy** → tiene que permitirlo.
7. Si nada permitió → **deny implícito**.

La forma corta de recordarlo: **cualquier capa puede denegar; todas las capas relevantes tienen que permitir.** Cuando algo "debería funcionar y no funciona", el diagnóstico consiste en recorrer esta lista de arriba abajo.

Dos herramientas para no hacerlo a ojo:
- **IAM Policy Simulator**: se elige una identidad, una acción y un recurso, y dice si se permite y qué policy tomó la decisión.
- **IAM Access Analyzer**: valida policies mientras las escribís, detecta recursos accesibles desde fuera de la cuenta y puede generar policies a partir de la actividad real registrada en CloudTrail.

### Los dos tipos de policy

#### Inline Policies (políticas en línea)

El JSON se escribe **directamente sobre cada identidad**, individualmente.

Ejemplo: tenés tres personas — Sally (Developer), Mike (Production), Miles (Accounts). Querés darles el mismo acceso a un recurso. Con inline policies, aplicás el mismo JSON **tres veces**, una en cada usuario.

**El problema:** si mañana querés cambiar ese permiso, tenés que ir a **modificar tres JSON diferentes**. Con 3 usuarios es molesto; con 300 es inmanejable, y garantizado que alguno queda desactualizado.

![[Pasted image 20260705160114.png|564]]


#### Managed Policies (políticas administradas)

Se crea la policy **una sola vez**, como un objeto independiente, y se **adjunta (attach)** a todas las identidades que la necesiten.

Ventajas:
- **Reusable**: una policy, N identidades.
- **Low management overhead**: cambiás el JSON en un solo lugar y se propaga a todos.
- **Versionado**: una managed policy guarda hasta **5 versiones**. Si un cambio rompe algo, se vuelve a la versión anterior con un clic. Las inline no tienen historial: lo que pisaste, pisado quedó.

> [!tip] Analogía
> 
> - **Managed policy** = un reglamento maestro colgado en la pared de la oficina. Lo actualizás una vez y todos leen la versión nueva.
> - **Inline policy** = le fotocopiás el reglamento a cada empleado. Si cambia una regla, tenés que perseguir a cada uno para reemplazar su copia.


![[Pasted image 20260705160500.png]]

#### ¿Cuándo usar cada una?

**Por defecto, usá managed policies.** Las inline se reservan para **excepciones especiales**: un `Allow` o un `Deny` que aplica a **una sola identidad** y a nadie más.

Ejemplo: todos los del equipo usan la managed policy `DeveloperAccess`, pero al brayan del CAP, específicamente, le querés denegar el acceso a un bucket de finanzas por apariencia delictiva. Ese `Deny` puntual va como inline policy en brayan del CAP.

Hay una ventaja secundaria de las inline que a veces las justifica: **viven y mueren con la identidad**. Si borrás el usuario, la policy se va con él y no queda basura dando vueltas. Con managed policies hay que acordarse de limpiar las que quedaron sin usar.
#### Dos subtipos de managed policy

|Subtipo|Quién la crea y mantiene|
|---|---|
|**AWS Managed Policy**|Creada y mantenida por **AWS**. Ej: `ReadOnlyAccess`, `AdministratorAccess`.|
|**Customer Managed Policy**|Creada y mantenida por **vos**.|
Las AWS managed son cómodas para arrancar, pero tienen dos características a tener en cuenta: **no se pueden editar** (si querés una variante, la copiás a una customer managed) y **AWS las actualiza sola** cuando salen servicios nuevos. Eso último es conveniencia y riesgo al mismo tiempo: los permisos de tus identidades pueden ampliarse sin que vos hagas nada. Para entornos con requisitos estrictos de mínimo privilegio, la recomendación es customer managed.

Una subcategoría útil: las **job function policies** de AWS (`DataScientist`, `NetworkAdministrator`, `Billing`, `SupportUser`), pensadas como punto de partida para roles típicos de una organización.
