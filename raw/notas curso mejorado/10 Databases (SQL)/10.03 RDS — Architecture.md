# Relational Database Service (RDS) — Architecture

> [!note] Resumen de la lección
> RDS es un **"database server as a service"**: te da una **DB instance** (un servidor de base de datos gestionado en gran medida por AWS) que puede contener varias bases de datos. Corre **dentro de una VPC**, en subnets definidas por un **DB subnet group**. No tenés acceso al OS ni SSH.

### ¿DBaaS? No exactamente

Mucha gente llama a RDS un producto **DBaaS (Database as a Service)**, pero los detalles importan:

- En un DBaaS pagás y obtenés **una base de datos**.
- Con RDS pagás y recibís un **servidor de base de datos** (una **instance**), así que es más exacto llamarlo **"database server as a service"**. En ese servidor podés tener **varias bases de datos**.

RDS te da lo mismo que tendrías on-premises, pero sin gestionar hardware, OS, instalación ni gran parte del mantenimiento del motor.

### Database engines

**MySQL, MariaDB, PostgreSQL, Oracle y SQL Server.** Algunos son open source y otros comerciales, con implicaciones de licenciamiento.

> [!warning] Aurora ≠ RDS
> **Amazon Aurora** se menciona seguido junto con RDS, pero es un **producto distinto**: un motor creado íntegramente por AWS, compatible con algunos de los anteriores. Muchas de sus funciones son diferentes (y la mayoría mejores). En tu cabeza, separá Aurora de RDS. Ver [[10.13 Aurora — Architecture|Aurora — Architecture]].

### RDS dentro de la VPC

RDS **no es un servicio público** como S3 o DynamoDB: opera en **subnets dentro de una VPC**, en una región específica. (Ejemplo de la lección: us-east-1 con una VPC en tres AZs A, B y C; y ap-southeast-2 para las partes cross-region.)

#### DB subnet group

- Lo creás vos: es un **listado de subnets** que RDS puede usar para una instancia (o instancias).
- En el ejemplo se crean **dos**: uno con **dos subnets públicas** y otro con **tres subnets privadas**.
- Al lanzar una RDS instance (con o sin alta disponibilidad) tenés que elegir un DB subnet group.
- Con alta disponibilidad, RDS elige una subnet para la **primary** y otra para la **standby** (al azar, salvo que indiques preferencia), pero siempre en **AZs distintas**.
- En **subnets privadas**: solo accesibles desde la VPC o redes conectadas (on-premises por VPN o Direct Connect, u otra VPC con peering).
- En **subnets públicas**: se pueden hacer accesibles desde internet dándoles direcciones públicas. Está **muy mal visto** desde la seguridad, pero es una opción que tenés que conocer.
- Un DB subnet group sirve para varios casos, pero quedás limitado a sus subnets. Best practice del curso: **un DB subnet group por implementación de RDS**.

> [!tip] Para el examen
> - El acceso de red a una RDS instance se controla con un **security group** adjunto a la instancia.
> - Puertos por defecto: **MySQL/MariaDB/Aurora MySQL 3306**, **PostgreSQL 5432**, **SQL Server 1433**, **Oracle 1521**.
> - El **endpoint es un nombre DNS (CNAME)**, nunca una IP fija: las aplicaciones siempre se conectan al endpoint, no a la IP.

### Otros aspectos importantes

- Una RDS instance **puede contener varias bases de datos**.
- Cada RDS instance tiene su **propio almacenamiento dedicado, provisto por EBS**. En un par multi-AZ, primary y standby tienen cada uno su storage. (Distinto de Aurora — recordalo.)
- **Multi-AZ**: la primary replica a la standby con **replicación síncrona** — la standby tiene el mismo conjunto de datos.
- **Read replicas**: **replicación asíncrona**, en la misma región o en otras; sirven para escalar lecturas y para resiliencia cross-region. Ver [[10.09 RDS Read Replicas|RDS Read Replicas]].
- **Backups**: se guardan en **S3**, en un bucket **gestionado por AWS** (no lo ves en tu cuenta). Quedan replicados en varias AZs de la región. Con multi-AZ, los backups se toman **desde la standby**, sin impacto en el rendimiento.
