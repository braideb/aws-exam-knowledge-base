# RDS — Multi-AZ Cluster

> [!note] Resumen de la lección
> En modo **multi-AZ cluster**, RDS tiene **un writer** que replica a **dos reader instances** en AZs distintas. A diferencia de la standby del modo instance, los readers **se pueden usar para lecturas**. Se parece a Aurora, pero **no es Aurora**: acá cada instancia tiene su **propio almacenamiento local**.

### Writer y readers

- **Writer**: como la primary del modo instance; sirve para escrituras y lecturas.
- **Readers**: **utilizables**, pero solo para **operaciones de lectura**. Requiere soporte de la aplicación (tiene que saber que no puede leer y escribir en la misma instancia), pero permite **escalar lecturas**, cosa que el modo instance no permite.
- Diferencia clave con Aurora: el multi-AZ cluster de RDS tiene **solo dos readers**; Aurora puede tener más.

### Replicación y commit

Los datos se envían al writer y se consideran **committed** cuando **al menos uno de los readers** confirma que se escribió. En ese punto ya es resiliente en varias AZs.

### Endpoints

| Endpoint | Apunta a | Uso |
|---|---|---|
| **Cluster endpoint** | El **writer** | Lecturas, escrituras y administración (como el database CNAME del modo instance). |
| **Reader endpoint** | Cualquier **reader** disponible (a veces incluye al writer) | Escalar lecturas: las apps balancean sus lecturas entre los readers. |
| **Instance endpoints** | Una instancia concreta | **No recomendado** para uso normal: no tolera la falla de esa instancia. Se usa para pruebas y para encontrar fallos. |

### Punteo

- **Un writer y dos readers** en AZs distintas → mayor disponibilidad que el modo instance (una sola standby).
- Hardware más rápido: arquitectura **Graviton** y almacenamiento **local NVMe SSD**. Las escrituras van primero al storage local superrápido y después a **EBS**: ventaja del local + disponibilidad y resiliencia de EBS.
- Los readers permiten **escalar lecturas** (si la app lo soporta), liberando al writer → mayor rendimiento que cualquier otro modo de RDS. (Aurora escala todavía más.)
- Replicación con **transaction logs**: más eficiente y con **failover más rápido** — en vez de 60–120 s, puede ser de tan solo **~35 segundos** (más el tiempo de aplicar los transaction logs a los readers).

| | Multi-AZ Instance | Multi-AZ Cluster |
|---|---|---|
| Réplicas | 1 standby | 2 readers |
| ¿Se puede leer de las réplicas? | ❌ | ✅ |
| Replicación | Síncrona, nivel storage | Transaction logs, commit con ≥1 reader |
| Failover | 60–120 s | ~35 s |
| Storage | EBS por instancia | NVMe local + EBS por instancia |
