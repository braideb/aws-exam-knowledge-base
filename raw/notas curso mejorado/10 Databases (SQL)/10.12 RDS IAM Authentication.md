# RDS — IAM Authentication

> [!note] Resumen de la lección
> RDS puede permitir que identidades de **IAM** (usuarios o roles) inicien sesión con un **token de 15 minutos** generado con `generate-db-auth-token`, **sin contraseña**. Es **solo autenticación**: los permisos dentro de la base los sigue controlando el usuario local.

### Por defecto: usuarios locales

Los logins en RDS se controlan con **usuarios locales de la base de datos**: tienen su propio usuario y contraseña, no son usuarios de IAM y están fuera del control de AWS. Se crea uno al aprovisionar la instancia, nada más.

### Cómo funciona IAM authentication

1. En la RDS instance se crea un **usuario local** configurado para permitir autenticación con un **token de AWS**.
2. Usuarios o roles de IAM (por ejemplo, un **instance role**) tienen **policies** que mapean esa identidad de IAM con el usuario local de RDS.
3. Esas identidades ejecutan **`generate-db-auth-token`**, que según las policies genera un **token válido por 15 minutos**.
4. El token se usa para iniciar sesión como el usuario de RDS **sin contraseña**.

En resumen: asociar una policy a un usuario o rol de IAM le permite generar un token que **reemplaza a la contraseña** para iniciar sesión en RDS.

> [!tip] Para el examen
> - **Autenticación, no autorización**: los permisos dentro de la base los controla el **usuario local**. IAM solo interviene en la autenticación, y solo si lo **habilitás explícitamente** en la instancia.
> - Casos de uso típicos: **centralizar** la gestión de accesos en IAM (en vez de contraseñas por base), **credenciales temporales** para EC2 o Lambda vía su rol, y forzar conexión con **SSL/TLS**.
> - Contra: tiene un **límite de conexiones nuevas por segundo**; para apps que abren muchísimas conexiones conviene **RDS Proxy** o usuarios locales.
