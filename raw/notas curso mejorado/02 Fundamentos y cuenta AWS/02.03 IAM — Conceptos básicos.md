# IAM — Conceptos básicos

En la mayoría de los casos querés conceder acceso a tu cuenta de AWS a otros usuarios, grupos o incluso aplicaciones, para que puedan crear o administrar cosas — y lo ideal es **restringir** ese acceso.

**Principio de mínimo privilegio (_least privilege_)**: siempre hay que dar **solo los permisos necesarios** para hacer un trabajo o tarea específica, y no rienda suelta para hacer todo.

En la práctica, el mínimo privilegio se construye al revés de lo que uno haría por intuición: se arranca **sin permisos** y se van agregando a medida que aparecen los errores de "access denied", en vez de arrancar con `AdministratorAccess` y prometerse recortarlo después (nunca pasa). Para esto AWS da dos herramientas muy útiles: **Access Advisor**, que muestra qué servicios usó realmente una identidad y cuándo, y **IAM Access Analyzer**, que puede **generar una policy** a partir de la actividad registrada en CloudTrail.

### Características de IAM

- **Todas las cuentas de AWS vienen con IAM**, y cada una tiene su **propia base de datos de IAM**, independiente de las demás cuentas.
- IAM es un servicio **globally resilient**: opera en todas las regions, y los datos están seguros y replicados globalmente.
- La AWS Account **confía plenamente en su IAM**: lo que IAM autoriza, la cuenta lo permite.
- **IAM es gratis.** No tiene costo.
- Soporta **identidad federada** (federated identity), o sea loguearte con un proveedor externo.
- Soporta **MFA**.

Un detalle que se desprende de ser global: como IAM replica sus datos a todo el mundo, los cambios son **eventually consistent**. Crear un usuario o modificar una policy puede tardar unos segundos en propagarse a todas las regiones. Si un script crea un rol e inmediatamente lo usa, a veces falla la primera vez y funciona al reintentar — no es un bug, es la propagación.

### Las tres entidades de IAM

|Entidad|Qué es|Cuándo se usa|
|---|---|---|
|**User**|Identidad que representa a un **humano** o a una **aplicación** que necesita acceso a la cuenta.|Cuando conocés el número exacto de identidades que necesitan acceso.|
|**Group**|Una **colección de users relacionados**. Ej: el equipo de desarrollo, finanzas, RRHH.|Para asignar permisos a muchos users a la vez, sin repetirse.|
|**Role**|Identidad que puede ser **asumida** por servicios de AWS o para conceder **acceso externo** a la cuenta.|Cuando el número de accesos es **incierto** o potencialmente muy grande.|

Ejemplo de role: darle permisos a una instancia **EC2** para que ella misma acceda a otros servicios de AWS, sin tener que guardarle credenciales adentro.

> [!info] Por qué "cuando el número de accesos es incierto" Una cuenta de AWS tiene un **límite de 5.000 usuarios IAM**. Si tenés una app móvil con un millón de usuarios, no podés crearles un IAM user a cada uno. Ahí es donde entran los **roles**: se asumen temporalmente, y no hay límite práctico de cuántas veces.

### Policy (documento de política)

Una **policy** es un objeto/documento (en JSON) que se usa para **permitir (Allow) o denegar (Deny)** el acceso a servicios de AWS.

> [!warning] Una policy **por sí sola no hace nada**. Solo tiene efecto cuando está **asociada (attached)** a un user, group o role de IAM.

### Las tres funciones principales de IAM

1. **Identity Provider (IDP) / Manage Identities** — permite **crear, modificar y eliminar** identidades (users, groups, roles).
2. **Authentication (autenticación)** — verifica _quién sos_. Normalmente con username + password, pero también con access keys u otros métodos.
3. **Authorization (autorización)** — una vez autenticado, decide _qué podés hacer_. Se basa en las **policies asociadas** a la identidad con la que te autenticaste.
