# Multi-Factor Authentication (MFA)

### ¿Qué es?

Normalmente uno se loguea a un sitio con **username y password**. Si alguien roba esas dos cosas, puede hacerse pasar por vos.

Un **factor** es una pieza de evidencia que prueba tu identidad. **Más factores = más seguridad.**

La lógica de fondo: cada factor tiene una forma distinta de ser comprometido. Una password se roba con phishing, con un keylogger o con una filtración de base de datos, y el atacante puede estar del otro lado del mundo. Un dispositivo físico hay que robarlo. Combinar dos tipos distintos obliga al atacante a lograr dos cosas muy diferentes al mismo tiempo, y ahí es donde la mayoría de los ataques masivos se caen.

### Los cuatro tipos de factores

|Factor|Qué es|Ejemplos|
|---|---|---|
|**Knowledge**|Algo que **sabés**|Username, password, PIN|
|**Possession**|Algo que **tenés**|Un dispositivo MFA, una tarjeta de crédito, un token|
|**Inherent**|Algo que **sos**|Huella digital, rostro, voz, iris|
|**Location**|Un lugar **físico o de red**|Estar en la red corporativa, un WiFi específico|
> [!note] En la práctica, el MFA de AWS combina **Knowledge** (password) + **Possession** (el código del dispositivo virtual). Los factores _inherent_ y _location_ aparecen en otros sistemas, no en el MFA nativo de AWS.

Una aclaración sobre _location_: en AWS ese factor no se implementa como MFA, pero sí existe como **condición en las policies**. Con `aws:SourceIp` o `aws:SourceVpce` se puede exigir que una acción solo se permita desde ciertas IPs o desde un VPC endpoint. Es el mismo concepto aplicado en la capa de autorización en vez de la de autenticación.
### Cómo se implementa en AWS

1. Inicialmente el **root user** se loguea con username y password.
2. Al activar MFA en ese usuario, AWS **genera una secret key aleatoria** y crea información asociada (nombre de usuario, servicio) que enlaza esa clave con la identidad.
3. AWS usa la secret key + esa información para generar un **código QR**.
4. Se **escanea el QR** con una aplicación MFA del teléfono (ej: Google Authenticator). Eso transfiere la key y la info a la app.
5. La app contiene muchos **virtual devices**, uno distinto por cada cuenta/servicio.
6. A partir de ahí, al loguearse hay que ingresar **username + password + el código** que genera la app.

> [!important] El detalle clave Vos le mandás a AWS **el código, no la key**. El código cambia periódicamente (cada 30 segundos). La secret key nunca viaja de nuevo.

**Un mismo usuario puede tener varios dispositivos MFA registrados** (hasta 8). Esto es más importante de lo que parece: permite registrar el teléfono principal _y_ una llave física de respaldo guardada en otro lado. Si se pierde uno, se entra con el otro sin pasar por el proceso de recuperación de cuenta.
### Qué pasa si perdés el dispositivo MFA (la gran nico)

- **IAM user**: cualquier administrador de la cuenta puede desactivarle el MFA y volver a configurarlo. Es un trámite de dos minutos.
- **Root user**: no hay administrador por encima. Hay que pasar por el **proceso de recuperación de AWS**, que verifica el acceso al mail de la cuenta y al teléfono registrado. Puede llevar tiempo y requiere que esos datos de contacto estén actualizados.

De ahí la recomendación anterior de registrar más de un dispositivo en el root, o de guardar la secret key en un lugar seguro.


### Forzar MFA desde una policy

El MFA se puede **exigir**, no solo ofrecer. Dentro de una IAM policy existe la clave de condición `aws:MultiFactorAuthPresent`, que permite escribir reglas del tipo "estas acciones solo se pueden ejecutar si el usuario se autenticó con MFA":


```json
{
  "Effect": "Deny",
  "Action": "ec2:TerminateInstances",
  "Resource": "*",
  "Condition": {
    "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
  }
}
```

Este patrón es el que se usa para proteger operaciones destructivas. Aparece en el examen con el enunciado "cómo garantizar que ciertas acciones solo se ejecuten con MFA": la respuesta es una condición en la policy, no una configuración del usuario.

Existe también `aws:MultiFactorAuthAge`, que exige que la autenticación con MFA haya ocurrido hace menos de X segundos.

### MFA desde la CLI

Un detalle que sorprende: si un usuario tiene MFA activado, la **CLI no lo pide automáticamente**. Las access keys funcionan igual, porque el MFA aplica a la consola. Para que la CLI también respete el MFA hay que:

1. Pedir credenciales temporales con MFA:

```bash
   aws sts get-session-token \
     --serial-number arn:aws:iam::123456789012:mfa/mi-usuario \
     --token-code 123456
```

2. Usar las credenciales temporales que devuelve (access key, secret key y **session token**) para las llamadas siguientes.

Y para que sea obligatorio, se combina con la condición `aws:MultiFactorAuthPresent` de la sección anterior. Sin esa condición, un atacante con la access key robada opera sin MFA aunque el usuario lo tenga configurado.
