# IAM Access Keys

No siempre se interactúa con AWS desde la consola web. También se puede hacer desde la **línea de comandos (CLI)** o desde otras aplicaciones usando la **API de AWS**.

Eso **no** se hace con username + password + MFA. Se hace con **IAM Access Keys**.

### Características

- Las access keys son **credenciales de largo plazo** (_long-term credentials_). No son el único tipo: username + password también lo son.
- **No rotan automáticamente.** Hay que rotarlas manualmente.
- Un user puede tener **un solo username y una sola password**.
- Un user puede tener **hasta dos access keys** al mismo tiempo — justamente para poder **rotarlas** sin cortar el servicio.
- Se pueden **crear, eliminar, desactivar y reactivar**.

Los **IAM roles no tienen access keys de largo plazo**. Usan credenciales **temporales** que se renuevan solas. Por eso son más seguros que dejar access keys hardcodeadas en una instancia EC2.

### Composición de una access key

Una access key está formada por dos partes:

|Parte|Ejemplo|Analogía|
|---|---|---|
|**Access Key ID**|`AKIAIOSFODNN7EXAMPLE`|Como el **username**|
|**Secret Access Key**|`wJalrXUtnFEMI/K7MDENG/bPxRfiCYEXAMPLEKEY`|Como la **password**|

Cuando se hace una solicitud a AWS desde la CLI o la API, se proporcionan **ambas**.

**Se muestra una sola vez**: al crear una access key, AWS te muestra las dos partes. Después de eso, **no hay forma de volver a ver la Secret Access Key**. Si la perdés, hay que borrar la key y crear una nueva.

Un dato útil para reconocerlas: el **prefijo del Access Key ID** indica el tipo de credencial. `AKIA...` corresponde a una access key de largo plazo de un IAM user; `ASIA...` a credenciales **temporales** emitidas por STS (las de un rol). Ver un `AKIA` dentro de una instancia EC2 es, por sí solo, una señal de que algo está mal configurado: ahí debería haber un rol.

Además, la secret key **no viaja en la request**. Se usa localmente para firmar el pedido con el algoritmo **SigV4**; lo que se envía es la firma. Por eso una request de AWS interceptada no revela la credencial, y por eso también un reloj muy desfasado en el cliente rompe la firma.

### Credenciales temporales vs. de largo plazo

|                      | **Access keys (largo plazo)**              | **Credenciales temporales (STS)**              |
| -------------------- | ------------------------------------------ | ---------------------------------------------- |
| Vencen               | No, hasta que las borres                   | Sí (minutos u horas)                           |
| Partes               | 2: key ID + secret                         | 3: key ID + secret + **session token**         |
| Prefijo del ID       | `AKIA`                                     | `ASIA`                                         |
| Quién las tiene      | IAM users                                  | Roles, federación, MFA con `get-session-token` |
| Riesgo si se filtran | Alto: sirven hasta que alguien las revoque | Bajo: caducan solas                            |

La conclusión práctica: **las access keys se justifican cada vez menos**. Para código que corre en AWS, la respuesta es un rol. Para personas, IAM Identity Center. Para servidores fuera de AWS, existe **IAM Roles Anywhere**, que permite obtener credenciales temporales usando certificados X.509. Las access keys quedan como último recurso para herramientas o entornos que no soportan nada mejor.

### Buenas prácticas y errores caros

Los errores más comunes, en orden de frecuencia:

1. **Subirlas a un repositorio de Git.** Hay bots escaneando GitHub que encuentran una key filtrada en cuestión de minutos y levantan instancias para minar criptomonedas. Las facturas de decenas de miles de dólares por este motivo son un clásico. Para prevenirlo: `.gitignore`, `git-secrets` o herramientas de escaneo pre-commit, y nunca versionar `~/.aws/credentials`.
2. **Hardcodearlas en el código o en una AMI.** Terminan en cada copia de la imagen y en cada backup.
3. **Crear access keys para el root user.** Es la peor combinación posible: una credencial permanente, sin restricciones posibles, sobre toda la cuenta. AWS lo desaconseja explícitamente y lo ha ido restringiendo.
4. **No rotarlas nunca.** Una key de 2019 que sigue activa en producción es un riesgo acumulado.

**Qué hacer si una key se filtra**, en este orden:

1. **Desactivarla inmediatamente** (no borrarla todavía: desactivada deja de funcionar pero conserva la evidencia).
2. Revisar **CloudTrail** para ver qué se hizo con ella y desde qué IPs.
3. Crear una key nueva y actualizar los sistemas legítimos.
4. **Borrar la comprometida.**
5. Revisar si se crearon usuarios, roles o recursos no autorizados. Un atacante que entra suele dejarse una puerta trasera además del daño inmediato.

### Cómo rotar una access key sin cortar el servicio

El límite de dos keys por usuario existe exactamente para esto:

```
1. Crear una segunda access key (ahora el usuario tiene dos activas)
2. Actualizar todas las aplicaciones/scripts con la nueva
3. Verificar que todo funciona con la nueva
4. Desactivar la vieja (sin borrarla) y esperar
5. Si nada se rompió → borrar la vieja
   Si algo se rompió → reactivar la vieja y buscar qué quedó sin actualizar
```

El paso 4 es el que hace que el procedimiento sea seguro: desactivar es reversible, borrar no.

### Herramientas de auditoría

- **Credential report**: un CSV descargable desde IAM con **todos** los usuarios de la cuenta y el estado de sus credenciales: si tienen MFA, cuándo se usó por última vez cada access key, cuándo se rotó, si la password está vencida. Es la forma rápida de encontrar keys viejas y usuarios sin MFA.
- **Access Advisor** (pestaña "Last Accessed" de cada identidad): muestra qué servicios usó realmente esa identidad. Sirve para recortar permisos sobrantes con evidencia.
- **CloudTrail**: el registro de cada llamada a la API, con quién, cuándo y desde dónde.
