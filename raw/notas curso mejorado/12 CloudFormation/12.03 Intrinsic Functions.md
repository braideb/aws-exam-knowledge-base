# CloudFormation Intrinsic Functions

Las funciones intrínsecas son las que le dan vida a una template: sin ellas, una template es un documento estático; con ellas, puede calcular valores en tiempo de despliegue. Repaso de las que vamos a ver:

| Función | Para qué sirve |
|---|---|
| **Ref** / **Fn::GetAtt** | Referencian un valor de un recurso lógico o de un parameter desde otro recurso. |
| **Fn::Join** / **Fn::Split** | Unir (join) cadenas y partirlas (split). |
| **Fn::GetAZs** / **Fn::Select** | GetAZs devuelve la lista de AZs de una región, y Select elige un elemento de esa lista. |
| **Funciones lógicas** (`Fn::If`, `Fn::And`, `Fn::Equals`, `Fn::Not`, `Fn::Or`) | Aprovisionan recursos según comprobaciones condicionales. |
| **Fn::Base64** / **Fn::Sub** | Base64 codifica texto plano; Sub sustituye variables dentro de un texto con información de tiempo de ejecución. |
| **Fn::Cidr** | Genera bloques CIDR para redes (calcula los rangos de las subnets dentro del rango de una VPC). |

El uso típico de Ref/GetAtt: creás una VPC y querés que una subnet caiga dentro de ella, así que la subnet referencia a la VPC. El de Join: tomar el DNS público de una instancia EC2 y armar la URL completa para acceder a ella. El de GetAZs/Select: casi siempre van juntas, para "agarrar una AZ" de la región sin hardcodear su nombre. El de las lógicas: si un parameter dice `prod`, desplegar instancias grandes; si dice `dev`, las más chicas. El de Base64: muchas partes de AWS esperan la entrada en base64 (el user data de EC2, por caso).

Hay otras (`Fn::ImportValue`, `Fn::FindInMap`, `Fn::Transform`) que se ven en secciones dedicadas. Cada una se puede usar por separado o combinada con las demás.

### Ref y Fn::GetAtt

Vale la pena entender bien la diferencia, porque se usan en casi todas las templates.

Una template con un recurso lógico crea una stack, y esa stack crea un recurso físico (en el ejemplo, una instancia EC2 t3.micro). Todo parameter y todo recurso lógico tiene un **valor principal (principal value)** que devuelve "por defecto". Para una instancia EC2 ese valor principal es su **ID físico**; para un parameter, es directamente su valor.

La forma más simple de recordarlo:

- **!Ref** pregunta _"¿cuál es tu identificador principal?"_. Sobre un parameter devuelve su valor (en el ejemplo, junto a `ImageId` se hace `!Ref LatestAmiId`, que trae el valor del parameter). Sobre un recurso lógico devuelve su ID físico: cuando la instancia llega a CREATE_COMPLETE, `!Ref Instance` devuelve algo como `i-1234567890abcdef0`.
- **!GetAtt** (`!GetAtt LogicalResource.Attribute`) pregunta _"dame este atributo puntual"_. Le pasás el nombre del recurso lógico y el nombre de un atributo secundario. Para una EC2 puede ser la IP pública (`PublicIp` → `54.91.129.183`) o el DNS público (`PublicDnsName` → `ec2-54-91-129-183.compute-1.amazonaws.com`).

> [!tip] En una frase
> **Ref te da el identificador principal; GetAtt te da un dato específico.** Las dos son la clave para convertir una template no portable (con valores a mano) en una portable (que calcula sus valores sola).

### Fn::GetAZs y Fn::Select

Van casi siempre juntas. `!GetAZs` es una función "consciente del entorno": imaginá que desplegás en `us-east-1`, que tiene seis AZs (1a, 1b, 1c, 1d, 1e, 1f). Si quisieras lanzar una EC2 en una de ellas, tendrías que conocer de antemano los nombres válidos y elegir uno. Y como buscamos portabilidad, hardcodear nombres de AZ es justo lo que no queremos.

La solución es `!GetAZs`: le pasás explícitamente una región (vía el pseudo parameter de la región) o lo dejás en blanco (`""`) para que use la región donde se está creando la stack. Te devuelve la lista de AZs de esa región.

> [!warning] Para el examen: qué AZs devuelve realmente `!GetAZs`
> En teoría debería devolver todas las AZs de la región, pero en realidad devuelve las AZs donde la **default VPC** tiene subnets. En la práctica suele ser lo mismo, salvo que tengas una default VPC a la que le borraste subnets: ahí la lista puede quedar incompleta. Si no tenés default VPC, o la tenés con subnets en todas las AZs, la lista sale completa.

Con esa lista dinámica en la mano, usás `!Select` para quedarte con un elemento. Select recibe una lista y un **índice que empieza en 0** (índice 0 = primer elemento). Esto te deja apuntar a las AZs de la región actual sin nombrarlas nunca, que es lo que hace la template portable. Ejemplo: `AvailabilityZone: !Select [ 0, !GetAZs '' ]` significa "la primera AZ de la región actual".

### Fn::Join y Fn::Split

`!Split` toma una cadena y un delimitador y devuelve una lista, una entrada por cada trozo: `!Split [ "|", "roffle|truffles|penny|winkie" ]` → `[ "roffle", "truffles", "penny", "winkie" ]`.

`!Join` es exactamente lo inverso: le das un delimitador y una lista, y los pega en una sola cadena: `!Join [ delimiter, [ "value1", "value2", ... "valueN" ] ]`.

![[Pasted image 20261006233013.png]]

En el ejemplo de la imagen se arma la URL web de una instancia EC2 de WordPress, pegando `http://` con el DNS de la instancia, que sale de `!GetAtt Instance.DNSName`: `Value: !Join [ '', [ 'http://', !GetAtt Instance.DNSName ] ]`. Fijate cómo se combinan dos intrínsecas: GetAtt trae el dato y Join lo ensambla.

### Fn::Base64 y Fn::Sub

`UserData:` espera datos codificados en base64. `Fn::Base64` toma texto plano y devuelve esa versión codificada, que es el formato que la instancia necesita. Regla simple: si un recurso de AWS pide base64, le pasás texto normal envuelto en Base64 y listo.

`Fn::Sub` (la función de sustitución) reemplaza variables dentro de un texto con información de tiempo de ejecución. En el ejemplo, dentro del user data aparece `${Instance.InstanceId}`, que es el atributo `InstanceId` del recurso lógico `Instance`; Sub reemplaza ese `${...}` por el valor real cuando la stack se despliega.

> [!warning] Para el examen: Sub no permite autorreferencias
> En la imagen, el user data de la instancia intenta usar su propio `InstanceId`, y eso es inválido. Es un problema del huevo y la gallina: el user data se inyecta _antes_ de que la instancia exista, así que no hay todavía un `InstanceId` que sustituir. El instructor lo muestra a propósito como ejemplo roto (el formato de Sub es correcto, lo que falla es la autorreferencia).

Los tres formatos que usás dentro de Sub son: `${Parameter}` (un parameter), `${LogicalResource}` (el valor principal, equivalente a `!Ref`) y `${LogicalResource.AttributeName}` (un atributo, equivalente a `!GetAtt`).

### Fn::Cidr

Es una función que simplifica muchísimo el networking. Al crear una VPC le das un rango CIDR, y antes tenías que calcular a mano los rangos de cada subnet dentro de ese bloque: una tarea tediosa y fácil de arruinar. Con `Fn::Cidr` le pasás el rango de la VPC, le decís **cuántas subnets** querés y el **tamaño** (en bits) de cada una, y te devuelve una lista de rangos CIDR listos para usar. Después, con `!Select`, asignás cada rango a cada subnet.

En el ejemplo, Subnet1 y Subnet2 usan `CidrBlock: !Select [ "0", !Cidr [ !GetAtt VPC.CidrBlock, "16", "12" ]]` (y lo mismo con índice `"1"` para la segunda). Desglosado: le pasamos el CIDR de la VPC (`10.16.0.0/16`, vía `!GetAtt VPC.CidrBlock`), le pedimos 16 rangos en total, y el `"12"` son los bits del host por CIDR (32 − 12 = `/20`). Ambas subnets calculan la misma lista de rangos posibles, y después cada una se queda con uno distinto por el índice (0 para Subnet1, 1 para Subnet2).
