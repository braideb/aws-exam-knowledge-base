# Demostración: wait condition, cfn-signal, cfn-init y cfn-hup

🔗 Parte 1: <https://learn.cantrill.io/courses/1101194/lectures/28333069>
🔗 Parte 2: <https://learn.cantrill.io/courses/1101194/lectures/30471883>

La demo arranca de una template con los dos problemas que ya vimos y los arregla uno por uno: primero agrega la señal (cfn-signal + CreationPolicy), después mueve la configuración a cfn-init, y por último suma cfn-hup para que un UpdateStack también actualice la instancia.

### Template inicial (los dos problemas en evidencia)

El user data usa `sleep 300` para simular un bootstrapping lento:

```yaml
Parameters:
  LatestAmiId:
    Description: "AMI for EC2"
    Type: 'AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>'
    Default: '/aws/service/ami-amazon-linux-latest/amzn2-ami-hvm-x86_64-gp2'
  Message:
    Description: "Message for HTML page"
    Default: "Cats are the best"
    Type: "String"
Resources:
  InstanceSecurityGroup:
    Type: 'AWS::EC2::SecurityGroup'
    Properties:
      GroupDescription: Enable SSH and HTTP access via port 22 IPv4 & port 80 IPv4
      SecurityGroupIngress:
        - Description: 'Allow SSH IPv4 IN'
          IpProtocol: tcp
          FromPort: '22'
          ToPort: '22'
          CidrIp: '0.0.0.0/0'
        - Description: 'Allow HTTP IPv4 IN'
          IpProtocol: tcp
          FromPort: '80'
          ToPort: '80'
          CidrIp: '0.0.0.0/0'
  Bucket:
    Type: 'AWS::S3::Bucket'
  Instance:
    Type: 'AWS::EC2::Instance'
    Properties:
      InstanceType: "t2.micro"
      ImageId: !Ref "LatestAmiId"
      SecurityGroupIds:
        - !Ref InstanceSecurityGroup
      Tags:
        - Key: Name
          Value: A4L-UserData Test
      UserData:
        Fn::Base64: !Sub |
          #!/bin/bash -xe
          yum -y update
          yum -y upgrade
          # simulate some other processes here
          sleep 300
          # Continue
          yum install -y httpd
          systemctl enable httpd
          systemctl start httpd
          echo "<html><head><title>Amazing test page</title></head><body><h1><center>${Message}</center></h1></body></html>" > /var/www/html/index.html
```

Esta primera template tiene los dos problemas que ya anticipamos: (1) la **desconexión** entre el bootstrap y el estado de la stack (el `sleep 300` lo deja en evidencia: la stack dice CREATE_COMPLETE mucho antes de que el bootstrap termine); y (2) la configuración de la instancia **no se actualiza** al actualizar la stack. Esos dos son los que vamos a arreglar, uno por vez.

### Paso 1: agregar el signal (CreationPolicy + cfn-signal)

Para lo primero agregamos un **signal** (`CreationPolicy` con `Timeout: PT15M` y, al final del user data, la llamada a `cfn-signal`):

```yaml
  Instance:
    Type: 'AWS::EC2::Instance'
    CreationPolicy:
      ResourceSignal:
        Timeout: PT15M
    Properties:
      InstanceType: "t2.micro"
      ImageId: !Ref "LatestAmiId"
      SecurityGroupIds:
        - !Ref InstanceSecurityGroup
      Tags:
        - Key: Name
          Value: A4L-UserData Test
      UserData:
        Fn::Base64: !Sub |
          #!/bin/bash -xe
          yum -y update
          yum -y upgrade
          # simulate some other processes here
          sleep 300
          # Continue
          yum install -y httpd
          systemctl enable httpd
          systemctl start httpd
          echo "<html><head><title>Amazing test page</title></head><body><h1><center>${Message}</center></h1></body></html>" > /var/www/html/index.html
          /opt/aws/bin/cfn-signal -e $? --stack ${AWS::StackId} --resource Instance --region ${AWS::Region}
```

### Paso 2: mover la configuración a cfn-init

Ahora movemos la configuración a **cfn-init** en lugar de amontonarla en el user data (que queda mínimo: solo `cfn-init` + `cfn-signal`):

```yaml
  Instance:
    Type: 'AWS::EC2::Instance'
    Metadata:
      'AWS::CloudFormation::Init':
        config:
          packages:
            yum:
              httpd: []
          files:
            /var/www/html/index.html:
              content: !Sub |
                <html><head><title>Amazing test page</title></head><body><h1><center>${Message}</center></h1></body></html>
          commands:
            simulatebootstrap:
              command: "sleep 300"
          services:
            sysvinit:
              httpd:
                enabled: "true"
                ensureRunning: "true"
                files:
                  - "/var/www/html/index.html"
    CreationPolicy:
      ResourceSignal:
        Timeout: PT15M
    Properties:
      InstanceType: "t2.micro"
      ImageId: !Ref "LatestAmiId"
      SecurityGroupIds:
        - !Ref InstanceSecurityGroup
      Tags:
        - Key: Name
          Value: A4L-UserData Test
      UserData:
        Fn::Base64: !Sub |
          #!/bin/bash -xe
          /opt/aws/bin/cfn-init -v --stack ${AWS::StackId} --resource Instance --region ${AWS::Region}
          /opt/aws/bin/cfn-signal -e $? --stack ${AWS::StackId} --resource Instance --region ${AWS::Region}
```

> [!tip] Dónde se ven los errores de bootstrap
> Después de esto, el instructor entra a la instancia para mostrar dónde se ven los errores: se conecta, hace `cd /var/log`, y ahí está `cloud-init-output.log`. Al hacerle `cat` da _permission denied_, así que lo lee con `sudo`; también muestra el archivo `cfn-init-cmd.log`. Son los dos logs a los que vas a querer ir cuando un bootstrap falle.

### Paso 3: agregar cfn-hup

Todavía queda el segundo problema: la configuración **no se actualiza** si hacés UpdateStack cambiando los parameters. Para resolverlo, la siguiente template suma **cfn-hup**, que detecta cambios en la metadata del recurso (se agregan los archivos `/etc/cfn/cfn-hup.conf` y `/etc/cfn/hooks.d/cfn-auto-reloader.conf`, y el servicio `cfn-hup` en `services`):

```yaml
  Instance:
    Type: 'AWS::EC2::Instance'
    Metadata:
      'AWS::CloudFormation::Init':
        config:
          packages:
            yum:
              httpd: []
          files:
            /etc/cfn/cfn-hup.conf:
              content: !Sub |
                [main]
                stack=${AWS::StackName}
                region=${AWS::Region}
                interval=1
                verbose=true
              mode: '000400'
              owner: 'root'
              group: 'root'
            /etc/cfn/hooks.d/cfn-auto-reloader.conf:
              content: !Sub |
                [cfn-auto-reloader-hook]
                triggers=post.update
                path=Resources.Instance.Metadata.AWS::CloudFormation::Init
                action=/opt/aws/bin/cfn-init -v --stack ${AWS::StackId} --resource Instance --region ${AWS::Region}
                runas=root
              mode: '000400'
              owner: 'root'
              group: 'root'
            /var/www/html/index.html:
              content: !Sub |
                <html><head><title>Amazing test page</title></head><body><h1><center>${Message}</center></h1></body></html>
          commands:
            simulatebootstrap:
              command: "sleep 300"
          services:
            sysvinit:
              cfn-hup:
                enabled: "true"
                ensureRunning: "true"
                files:
                  - /etc/cfn/cfn-hup.conf
                  - /etc/cfn/hooks.d/cfn-auto-reloader.conf
              httpd:
                enabled: "true"
                ensureRunning: "true"
                files:
                  - "/var/www/html/index.html"
    CreationPolicy:
      ResourceSignal:
        Timeout: PT15M
    Properties:
      InstanceType: "t2.micro"
      ImageId: !Ref "LatestAmiId"
      SecurityGroupIds:
        - !Ref InstanceSecurityGroup
      Tags:
        - Key: Name
          Value: A4L-UserData Test
      UserData:
        Fn::Base64: !Sub |
          #!/bin/bash -xe
          /opt/aws/bin/cfn-init -v --stack ${AWS::StackId} --resource Instance --region ${AWS::Region}
          /opt/aws/bin/cfn-signal -e $? --stack ${AWS::StackId} --resource Instance --region ${AWS::Region}
```

Fijate cómo el archivo `cfn-auto-reloader.conf` se dispara en `post.update` y apunta justo a la ruta de la metadata (`Resources.Instance.Metadata.AWS::CloudFormation::Init`): cuando esa metadata cambia tras un UpdateStack, cfn-hup corre de nuevo cfn-init y reaplica el desired state.
