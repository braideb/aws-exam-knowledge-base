# CloudFormation Mappings

La sección opcional **Mappings** es, en esencia, un **diccionario** (una tabla de búsqueda) dentro de la template: asocia una clave con un conjunto de valores con nombre. A alto nivel, una template es solo una colección de objetos de nivel superior —`Resources` es uno, `Parameters` otro—, y `Mappings` es otro más.

El objeto `Mappings` puede contener varios **maps**, y cada map es un conjunto de clave→valores que te permite "buscar" información. Un uso típico es mapear el entorno (`prod`) a una configuración concreta de base de datos o a una SSH key específica. Los maps pueden tener un solo nivel de búsqueda (das una clave y recuperás un valor) o dos niveles (una **top-level key** y una **second-level key**). El ejemplo clásico es un map de AMI IDs, donde el primer nivel es la **region** y el segundo la **architecture**.

Para leer un map se usa la intrínseca **!FindInMap**.

> [!tip] Lo que hay que llevarse
> Los mappings **mejoran la portabilidad**, porque guardan dentro de la template los datos que hacen que se comporte distinto según la entrada (la región, la arquitectura, el entorno), sin que tengas que tocar los recursos.

El formato es `!FindInMap [ MapName, TopLevelKey, SecondLevelKey ]`:

- Primero el **nombre del map**: `"RegionMap"`.
- Después la **top-level key** (obligatoria). En el ejemplo se usa el pseudo parameter `!Ref 'AWS::Region'`, que resuelve a la región donde se aplica la template (digamos `us-east-1`). Con solo estos dos argumentos, recuperarías todo el objeto que cuelga de `us-east-1`.
- Y la **second-level key** (`"HVM64"`), que hace la segunda búsqueda y, en este caso, devuelve el AMI ID.

El resultado completo: `!FindInMap [ "RegionMap", !Ref 'AWS::Region', "HVM64" ]`. Si en `RegionMap`, bajo `us-east-1`, está `HVM64: "ami-0ff8a91507f77f867"`, ese es el valor que devuelve (el AMI ID para `us-east-1` con arquitectura HVM64).
