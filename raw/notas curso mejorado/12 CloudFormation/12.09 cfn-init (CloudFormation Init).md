# CloudFormation Init (cfn-init)

**CloudFormationInit y cfn-init** son herramientas que permiten implementar, dentro de CloudFormation, un sistema de gestión de configuración basado en **desired state** (estado deseado). Se usa el tipo `AWS::CloudFormation::Init` para guardar metadata de configuración junto al recurso EC2, y el helper script `cfn-init` la lee y la aplica. Si tu template llama a `cfn-init`, el script busca esa metadata bajo la clave `AWS::CloudFormation::Init`. Soporta todos los tipos de metadata en Linux y algunos en Windows.

Es otra manera de configurar una EC2, y conviene contrastarla con el user data. El user data lo venís usando para pasar scripts, pero no es una función de CloudFormation: es una función de EC2, que corre en el OS de la instancia. **CloudFormation::Init sí es nativo de CloudFormation**: las directivas de configuración viven en la template, pegadas al recurso lógico, en la sección `AWS::CloudFormation::Init`.

> [!tip] La distinción conceptual clave: procedural (CÓMO) vs desired state (QUÉ)
> - **User data es procedural (el CÓMO):** una lista de comandos que se ejecutan uno tras otro. Le estás dictando a la instancia, paso a paso, **cómo** configurarse.
> - **CloudFormation::Init es desired state (el QUÉ):** declarás **qué** estado final querés y dejás que el sistema averigüe cómo llegar. Es el mismo enfoque de un gestor de configuración tipo Ansible o Puppet, pero embebido en CloudFormation.

De ese enfoque desired state se desprenden dos ventajas enormes: es **multiplataforma** (distintos Linux, y en algunos casos Linux y Windows) y es **idempotente**: si algo ya está en el estado deseado, correr cfn-init no hace nada (si Apache ya está instalado, no lo reinstala; si el servicio ya corre, lo deja). Te ahorrás toda la lógica de "si ya está así, no lo toques" que tendrías que escribir a mano en un script procedural.

Se accede a CloudFormation::Init mediante el helper script **cfn-init**, preinstalado en las AMIs de EC2. cfn-init se lanza desde el user data, apunta a un recurso lógico (normalmente la propia instancia) y traduce las directivas de configuración en acciones concretas.

El flujo: una template crea una EC2 cuyo recurso lógico lleva un bloque `Metadata` → `AWS::CloudFormation::Init` con la configuración. cfn-init se dispara desde el user data, pero fijate que ese user data es **mínimo**: apenas la llamada a `cfn-init` (que aplica la config) y después `cfn-signal` (que avisa cuándo terminó). Toda la "chicha" se fue a la metadata.

Como siempre, el user data corre en el primer arranque. En el comando de cfn-init se pasan variables como el stack ID y la región; como es CloudFormation quien crea la instancia, esas variables se reemplazan por los valores reales antes de llegar a la máquina (`${AWS::Region}` → la región actual, `${AWS::StackId}` → el ID real de la stack). Así cfn-init sabe con qué stack hablar para bajarse su configuración.

Dentro de `AWS::CloudFormation::Init` se definen una o más **config keys** (contenedores de directivas), y cada una puede tener estas secciones, que cfn-init procesa **en este orden**:

| Orden | Sección | Qué hace |
|---|---|---|
| 1 | **packages** | Instala paquetes desde gestores como `yum`, `apt`, `rpm`, `python`, etc. (por ejemplo, `httpd`). |
| 2 | **groups** | Crea grupos de Linux (y, si querés, les fija el GID). |
| 3 | **users** | Crea usuarios de Linux y define a qué grupos pertenecen. |
| 4 | **sources** | Descarga archivos comprimidos (un `.zip` o `.tar.gz` desde una URL o S3) y los extrae en un directorio de la instancia. |
| 5 | **files** | Crea archivos, con contenido inline (podés usar `!Sub` para inyectar variables) o bajándolos de una URL, y les define permisos (`mode`), `owner` y `group`. |
| 6 | **commands** | Ejecuta comandos arbitrarios, **en orden alfabético** por el nombre de cada comando (detalle que importa si un comando depende de otro). |
| 7 | **services** | Controla qué servicios (por ejemplo vía `sysvinit`) deben quedar **habilitados** (`enabled`) y **corriendo** (`ensureRunning`), y puede reiniciarlos solos si cambian ciertos archivos. |

> [!warning] Para el examen
> El orden de procesamiento es fijo (packages → groups → users → sources → files → commands → services), y dentro de **commands** se ejecutan en **orden alfabético** por nombre.
