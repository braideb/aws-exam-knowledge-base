# CloudFormation WaitCondition, CreationPolicy y cfn-signal

Repaso del circuito normal: una template marca los recursos lógicos, la stack los crea y aparece el recurso físico. Cuando ese recurso termina de crearse (por ejemplo, una EC2), el servicio correspondiente le avisa a CloudFormation y el recurso lógico pasa a **CREATE_COMPLETE**. Suena a que está todo listo… pero no necesariamente.

> [!warning] El concepto más importante de la sección: CREATE_COMPLETE a veces "miente"
> Para un recurso simple, cuando EC2 le dice a CloudFormation "terminé", CloudFormation no tiene forma de saber nada más allá de eso. Pero si además de crear la instancia corrés **bootstrapping** (user data que instala y configura software), la instancia llega a CREATE_COMPLETE apenas el hardware virtual está listo —**mucho antes** de que termine el bootstrapping— y, peor todavía, aunque el bootstrapping falle, el recurso sigue mostrando CREATE_COMPLETE. Dicho de otro modo: CREATE_COMPLETE te dice "AWS terminó de crear la VM", no "tu aplicación quedó instalada y andando".

**CreationPolicy, WaitConditions y cfn-signal** existen para cerrar esa brecha: permiten que lo que corre dentro del recurso le mande a CloudFormation una señal honesta de si terminó bien o mal.

### CloudFormation Signal

La señalización se hace con el comando **cfn-signal**, que viene en el paquete `aws-cfn-bootstrap`. El principio es simple: configurás CloudFormation para que **retenga/pause** el recurso en lugar de pasarlo directo a CREATE_COMPLETE, le decís cuántas **señales de éxito (success signals)** tiene que esperar, y fijás un **Timeout** (en formato H:M:S) dentro del cual deben llegar.

| Situación | Resultado |
|---|---|
| Llegan todas las señales de éxito dentro del timeout | El recurso pasa a **CREATE_COMPLETE** (ahora sí, de verdad). |
| Llega una **señal de fallo** | La creación **falla** de inmediato. |
| Se vence el **timeout** sin señales suficientes | CloudFormation lo toma como fallo y la creación **falla**. |

> [!tip] Para el examen: el timeout máximo es **12 horas**.

cfn-signal corre en la propia instancia y manda la señal de vuelta al servicio de CloudFormation. Lo que se señaliza es un recurso lógico, y hay dos formas de hacerlo: con una **CreationPolicy** (lo que AWS recomienda para EC2 o Auto Scaling groups, porque la política vive pegada al recurso) o con un recurso aparte de tipo **WaitCondition** (más pensado para integrar CloudFormation con un sistema externo).

### CreationPolicy

Ejemplo: un Auto Scaling group que usa una launch configuration para lanzar tres instancias EC2. Al tener una `CreationPolicy`, el comportamiento cambia respecto al normal:

- La CreationPolicy agrega un **requisito de señales** y un **timeout**. Acá: **3 señales** y **15 minutos** (`Count: '3'`, `Timeout: PT15M`).
- Las instancias se aprovisionan, pero el ASG **no pasa a CREATE_COMPLETE** todavía: queda esperando a que se cumpla la política.
- El user data de cada instancia hace el bootstrapping y, al final, llama a cfn-signal. Cuando una instancia termina de configurarse (por ejemplo, instaló la app de Catagram), señaliza una vez.
- El ASG necesita las 3 señales en 15 minutos. Si llegan y son de éxito → la stack pasa a **CREATE_COMPLETE**. Si se vence el timeout o falla alguna → **CREATE_FAILED**.

El comando típico al final del user data es:

```bash
/opt/aws/bin/cfn-signal -e $? --stack ${AWS::StackName} --resource AutoScalingGroup --region ${AWS::Region}
```

Las CreationPolicy se usan sobre todo con instancias EC2 o Auto Scaling groups.

### CloudFormation WaitCondition

Las wait conditions funcionan parecido a las CreationPolicy, pero con una diferencia de forma clave: una WaitCondition es un **recurso lógico independiente**, no algo que definís adentro de otro recurso. Como es un recurso propio, puede depender de otros y otros pueden depender de ella, así que sirve como una **puerta de progreso** general dentro de la template: un punto que no se cruza hasta recibir las señales (o hasta que venza su timeout).

Una WaitCondition se apoya en un **WaitHandle**: otro recurso lógico cuyo único trabajo es generar una **URL prefirmada (pre-signed URL)**. Esa URL es el "buzón" al que se mandan las señales, y como ya viene firmada, quien la use no necesita credenciales de AWS propias (van incluidas en la URL).

El caso de uso: una EC2 o un servidor externo que tiene que hacer algo (configuración final, licenciamiento, etc.) entre una parte de la template y otra. Ese proceso manda de vuelta un **documento JSON** como señal, con un status, un reason, un ID único y datos arbitrarios. Lo potente es que esos datos no sirven solo para pausar/continuar: se pueden **leer desde otras partes de la template** con `!GetAtt` sobre la WaitCondition. Eso habilita un pequeño ida y vuelta de datos entre lo que señaliza y la stack, útil para licenciamiento o para traer info de estado de un sistema externo.

> [!tip] Para el examen: CreationPolicy vs WaitCondition
> Misma idea de fondo (pausar la creación hasta recibir señal), pero la WaitCondition es un recurso separado y puede intercambiar información. Aun así, **AWS recomienda CreationPolicy para la mayoría de los casos**, porque es más fácil de administrar.
