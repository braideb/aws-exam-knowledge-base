# FSx for Lustre — Concepts

> [!note] Resumen de la lección
> **FSx for Lustre** es un file system gestionado para **HPC** (machine learning, modelado financiero, procesamiento masivo de datos), para clientes **Linux** y con permisos **POSIX**. Tiene dos deployment types: **Scratch** (rendimiento máximo, sin resiliencia) y **Persistent** (alta disponibilidad, pero **dentro de una sola AZ**). Puede asociarse a un **repositorio S3** cuyos objetos se cargan con **lazy load** y no se sincronizan solos.

FSx for Lustre es un file system diseñado para varios tipos de cargas de trabajo de **computación de alto rendimiento (HPC)**. Para el examen importa que entiendas qué provee y cómo está diseñado, no Lustre en detalle; es un producto relativamente especializado. Lo que sí tenés que poder hacer es **distinguir escenarios** entre las dos variantes de FSx. FSx for Windows es un file system nativo de Windows, accedido vía SMB, para entornos Windows en AWS. FSx for Lustre, en cambio, es una implementación gestionada del file system **Lustre**, diseñado específicamente para HPC, compatible con instancias **Linux** y (palabra clave para el examen) con soporte para permisos estilo **POSIX**.

Lustre está pensado para casos como machine learning, modelado financiero o de datos a gran escala: cualquier cosa que necesite procesar grandes cantidades de datos con un rendimiento muy alto. Puede escalar a **cientos de GB/s** de throughput y ofrece **latencia inferior a 1 ms** al acceder al almacenamiento.

### Deployment types: Scratch y Persistent

**Scratch** está optimizado para el mejor rendimiento absoluto, pensado para cargas de trabajo de corto plazo o temporales. No aporta mucho en resiliencia ni en alta disponibilidad: si hay una falla de hardware, los datos de ese hardware se pierden.

**Persistent** es para un file system persistente y de alta disponibilidad, ideal para almacenamiento de largo plazo. Ofrece alta disponibilidad, pero **dentro de una sola AZ**: Lustre es single-AZ por naturaleza, porque necesita ese nivel de rendimiento de alta gama. Además ofrece **self-healing**, es decir, si falla hardware del file system, AWS lo reemplaza automáticamente. Es el tipo que elegís si necesitás resiliencia y alta disponibilidad de los datos.

Como FSx for Windows, FSx for Lustre está disponible vía VPN o Direct Connect desde ubicaciones on-premises (vas a necesitar bastante ancho de banda para aprovechar su rendimiento).

### El file system y el repositorio S3

El producto gira en torno a un file system gestionado, accesible desde una VPC o desde cualquier cosa conectada por una red privada; en conectividad es muy parecido a EFS o a FSx for Windows. El file system es donde residen los datos mientras se analizan o procesan.

Al crear el file system podés asociarlo a un **repositorio**, que en este caso es un **bucket de S3**. Si lo hacés, los objetos del bucket aparecen visibles en el file system, pero (y esto es crucial) **todavía no están almacenados** en Lustre: cuando un cliente los accede por primera vez, los datos se cargan de forma **lazy (lazy loaded)** desde S3 al file system, y recién ahí quedan presentes.

Tampoco hay **sincronización automática incorporada**. Conceptualmente, el file system Lustre está completamente separado y solo usa el repositorio S3 como base. Podés **exportar** los cambios de vuelta al repositorio con el comando **`hsm_archive`**. La idea para retener: Lustre es un sistema independiente, que se puede configurar para cargar datos de forma diferida desde S3 y para reescribirlos, pero que no se sincroniza solo; y es en el file system Lustre donde se produce el procesamiento.

> [!tip] Para el examen
> Objetos de S3 que "aparecen" en Lustre → **lazy load** en el primer acceso. Los cambios **no vuelven solos** a S3: hay que exportarlos (`hsm_archive`).
