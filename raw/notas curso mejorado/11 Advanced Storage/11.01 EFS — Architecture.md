# EFS — Architecture

> [!note] Resumen de la lección
> **EFS (Elastic File System)** es la implementación de AWS de **NFSv4**: file systems de red que se montan en cómputo Linux y que **muchas instancias pueden usar a la vez**. Vive dentro de una VPC (es un **servicio privado**), se expone mediante **mount targets** en subnets, y puede desplegarse como **Regional** (multi-AZ, recomendado) o **One Zone** (más barato, sin resiliencia ante la caída de la AZ).

EFS proporciona sistemas de archivos basados en red que se pueden montar, predominantemente en instancias Linux, y que pueden ser usados por varias instancias a la vez. Es la implementación de AWS de un estándar de almacenamiento compartido bastante común, **NFS (Network File System)**, específicamente la **versión 4**. Con EFS creás **file systems**, que son la entidad base del producto, y esos file systems se montan en instancias EC2 Linux (e incluso Mac). Linux usa una estructura de árbol para sus archivos, así que los dispositivos se montan en carpetas de esa jerarquía: un EFS file system, por ejemplo, podría montarse en una carpeta.

Cuando digo instancias Linux, en realidad EFS funciona en todos los tipos de cómputo de AWS que corran Linux: instancias EC2 Linux, AWS Lambda y contenedores en ECS o EKS. Lo más impresionante es que un mismo file system se puede montar en **muchos** sistemas Linux a la vez, así que los datos pueden ser compartidos, por ejemplo, por muchas instancias EC2 en ejecución al mismo tiempo. Si tenés una solución basada en EC2 donde todas las instancias necesitan acceder exactamente a los mismos datos, en lugar de preocuparte por sincronizar el almacenamiento de cada una por separado, usás EFS y compartís el mismo storage entre todas.

Este almacenamiento existe **separado de EC2** (o de cualquier otra cosa que lo use), así que tiene su propio ciclo de vida, pero puede estar conectado a múltiples cosas distintas. Cuando configurás EFS, se aprovisiona dentro de una **VPC** usando **mount targets**.

### Regional vs One Zone

Al configurar EFS por primera vez elegís entre un despliegue **Regional** o **One Zone**. Regional almacena tus datos en varias Availability Zones: es el tipo predeterminado y el recomendado. One Zone vive en una sola AZ, por lo que es más barato, pero no es resistente a la pérdida de esa AZ.

### Servicio privado, accesible por redes híbridas

Como EFS está implementado en la VPC, se considera un **servicio privado**: por defecto está aislado en la VPC en la que se aprovisiona. Aun así, se puede acceder al file system a través de **redes híbridas** si tu VPC está conectada a otras redes, ya sea con VPC peering, VPN o AWS Direct Connect (una red privada física entre una VPC y tus redes on-premises). Esas funciones de redes híbridas se tratan en otra parte del curso; por ahora alcanza con entender que EFS es privado, pero accesible desde fuera de la VPC si usás esos productos.

Un detalle que vale la pena conocer: si montás EFS desde una instalación on-premises, AWS recomienda usar la _IP del mount target_ en lugar de los nombres DNS de EFS. El nombre DNS de EFS resuelve a las IPs privadas de los mount targets a través del DNS resolver de la VPC, y una red on-premises no puede resolverlo salvo que tengas DNS híbrido configurado; por eso, desde on-premises, se usa directamente la IP.

### Arquitectura: file systems y mount targets

En el ejemplo tenemos la VPC de Animals4life. Lo principal que realmente creás en EFS son los **file systems**, y estos usan **permisos POSIX**. POSIX es un estándar de interoperabilidad que se usa en Linux, así que un file system con permisos POSIX es algo que todas las distribuciones de Linux entienden.

El file system se expone dentro de la VPC mediante **mount targets**, que corren desde subnets de la VPC y tienen una **dirección IP** tomada del rango de la subnet en la que están. Son estos mount targets los que proporcionan la conectividad al file system. Para garantizar alta disponibilidad con la opción Regional, conviene tener un mount target en **cada AZ** en la que opera la red y en la que necesitás acceso. Si no necesitás disponibilidad en múltiples AZs, podés implementar EFS como One Zone, que usa un único mount target en una sola AZ.

> [!tip] Para el examen: puerto 2049
> Cada mount target tiene un **security group**, y EFS se monta por el **puerto 2049 (NFS)**. Si una instancia EC2 no puede montar el EFS, el sospechoso habitual es que el security group del mount target no permite el puerto 2049 desde el security group de la instancia.
