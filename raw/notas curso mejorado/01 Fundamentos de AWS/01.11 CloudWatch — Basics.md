# CloudWatch — Basics

**CloudWatch** es usado por la mayoría de los servicios de AWS, especialmente para operaciones de gestión y supervisión (_monitoring_).

Es un **servicio público**, por lo que puede recolectar información tanto desde dentro de AWS como desde entornos **on-premises** o incluso desde otras plataformas de nube.

**CloudWatch vs. CloudTrail (no confundir)** Se parecen en el nombre y miden cosas totalmente distintas:

- **CloudWatch** = _performance_. Responde **"¿cómo está funcionando?"** → CPU al 90%, 300 requests/s, este log tiene errores.
- **CloudTrail** = _auditoría_. Responde **"¿quién hizo qué?"** → el usuario `juan` terminó la instancia `i-abc` a las 15:42 desde la IP tal. Si la pregunta es "quién borró el bucket", la respuesta es **CloudTrail**, no CloudWatch.

> [!warning] 🆕 Las métricas que EC2 NO reporta solo (clásico de examen)
> Por defecto, el hipervisor ve **CPU, red y disco a nivel de volumen**, pero **NO** ve dentro del SO. Por eso estas métricas **requieren el CloudWatch Agent**:
> - **Uso de memoria (RAM)** ← la más preguntada.
> - **Espacio en disco usado** (a nivel de filesystem).
> - Procesos, swap, logs de aplicación.
> Si un examen dice "no veo la métrica de memoria de mi EC2", la respuesta es: **instalar y configurar el Unified CloudWatch Agent** (con su IAM role correspondiente).
> Si un examen dice "no veo la métrica de memoria de mi EC2", la respuesta es: **instalar y configurar el Unified CloudWatch Agent** (con su IAM role correspondiente).

**La razón de fondo**: el hipervisor solo puede medir lo que ve desde afuera de la VM. Sabe cuántos ciclos de CPU le dio y cuántos paquetes pasaron por la red, pero no tiene idea de si adentro el SO tiene 2 GB o 200 MB de RAM libre. Entender esto hace que no haya que memorizar la lista.
### Las tres tareas principales de CloudWatch

#### 1. Metrics
Datos relacionados con aplicaciones o servicios de AWS.
- CloudWatch puede recolectar **métricas nativas**: hay servicios de AWS que siempre generan información por sí solos (ej: la utilización de CPU de una instancia EC2).
- Otras métricas requieren instalar software adicional, como el **CloudWatch Agent**, que permite recolectar métricas del sistema operativo (memoria, disco, procesos).

#### 2. CloudWatch Logs
Permite recopilar, almacenar y analizar información basada en **datos de registro (logs)**.

#### 3. CloudWatch Events
Funciona como un **hub de eventos**:
- Si un servicio hace algo (una instancia se inicia, se detiene, se termina), CloudWatch puede generar un **evento** y ejecutar una **acción**.
- También puede generar eventos **programados** para ejecutar algo en un momento determinado (tipo cron).

> [!note] 🆕 CloudWatch Events ahora se llama EventBridge
> **Amazon EventBridge** es la evolución de CloudWatch Events (mismo backend, API compatible). AWS recomienda usar EventBridge para todo lo nuevo. Agrega: **event buses** custom, **Schema Registry**, integración con **SaaS de terceros** (Zendesk, Datadog, etc.) y **más targets**. En el examen DOP, cuando veas "reaccionar a un evento de AWS y disparar una acción/Lambda", pensá EventBridge. Ejemplo de regla de EventBridge: _"cada vez que una instancia EC2 pase a estado `terminated`, mandar un mensaje a SNS y ejecutar una Lambda que limpie los registros de DNS"_. Se define con un patrón JSON que matchea el evento, más uno o varios targets.

### Namespace

Un **namespace** es un **contenedor** para datos de monitoreo. Sirve para agrupar métricas relacionadas y que no se mezclen entre sí.

- Todos los datos de servicios de AWS van a un namespace con el formato **`AWS/service`**. Por ejemplo: `AWS/EC2`, `AWS/S3`, `AWS/Lambda`, `AWS/RDS`.
- Para datos propios podés crear tu propio namespace con el nombre que quieras (ej: `CATAGRAM`). No puede empezar con `AWS/` — ese prefijo está reservado.

Cada namespace contiene **metrics** relacionadas.

### Metric
Una **metric** es una colección de datapoints relacionados, ordenados en el tiempo (una serie temporal). Ejemplos: `CPUUtilization`, utilización del disco, tráfico de red.

Una métrica **no** es un servidor. Es el _tipo de dato_ que se está midiendo.

### Datapoint

Un **datapoint** es **una medición individual** que se envía a CloudWatch. Se compone de:

|Campo|Ejemplo|
|---|---|
|**Timestamp**|`2019-12-03T08:45:45Z`|
|**Value**|`98.3`|
Lo que permite distinguir de qué servidor vino cada datapoint son las **dimensions**.

### Dimensions

### Dimensions

Si una métrica recibe datapoints de múltiples servidores, ¿cómo se separan los datos? Con **dimensions**.

Las **dimensions** son **pares nombre/valor** que separan los datapoints por diferentes _cosas_ o _perspectivas_ dentro de una misma métrica.

Ejemplo, para la métrica `CPUUtilization` en el namespace `AWS/EC2`:

```
Name = InstanceId,   Value = i-xxxxxxxxx
Name = InstanceType, Value = t3.small
Name = AutoScalingGroupName, Value = web-asg
```

Así se puede ver la CPU de una instancia puntual, la CPU promedio de todas las `t3.small`, o la del ASG entero.

### Alarm

CloudWatch permite **tomar acciones en función de las métricas**, y para eso se usan las **alarms**.

Una alarm se crea y se **asocia a una métrica específica**. Según cómo la configures, la alarm pasa por distintos estados:

| Estado                | Significado                                                                                                                  |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **OK**                | La métrica está dentro del umbral definido.                                                                                  |
| **ALARM**             | La métrica cruzó el umbral. Se dispara una acción: notificación por **SNS** o una **action** (ej: escalar con Auto Scaling). |
| **INSUFFICIENT_DATA** | No hay datos suficientes para determinar el estado.                                                                          |
![[Pasted image 20260627154310.png]]

> [!tip] 🆕 Qué puede disparar una alarm (las acciones que importan en DOP)
> Una alarm no solo "avisa": puede ejecutar acciones directas:
> - **SNS** → notificar (mail, SMS) o encadenar hacia Lambda/SQS.
> - **Auto Scaling** → escalar in/out.
> - **EC2 Actions** → stop / terminate / reboot / recover de la instancia (útil para auto-remediación barata).
> - **Systems Manager** → crear un OpsItem / disparar automatización.
