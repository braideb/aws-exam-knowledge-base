# DNS Record Types

### NS (Name Server)

Son los registros que permiten la **delegación de DNS**. Un servidor de una zona superior usa registros NS para decir "la autoridad sobre esta subzona la tiene aquel otro servidor".

Ejemplo, dentro de la zone `.com`:

```
amazon.com  NS  pdns1.ultradns.net.
amazon.com  NS  pdns6.ultradns.co.uk
```

Esos NS records apuntan desde la zone `.com` hacia los name servers de la zone `amazon.com`, donde viven los records reales.

La delegación es **el mecanismo que hace escalable a todo el DNS**: ningún servidor conoce todos los dominios del mundo, solo sabe a quién preguntarle en el siguiente nivel. Es la misma idea recursiva desde la raíz hasta tu subdominio.

### A y AAAA — _Host to IP_

Mapean un **hostname a una dirección IP**.

|Tipo|Apunta a|Ejemplo|
|---|---|---|
|**A**|IPv4|`A www → 172.217.25.36`|
|**AAAA**|IPv6|`AAAA www → 2404:6800:4006:802::2004`|

Normalmente se crean **ambos** para el mismo host, y el cliente pide el que soporte.

Truco para no confundirlos: **AAAA** ("cuadruple A") es cuatro veces la letra porque IPv6 es cuatro veces más largo que IPv4 (128 bits vs. 32).

### CNAME — _Host to Host_

Mapea un **hostname a otro hostname** (es un alias).

En la zone `google.com`:

```
A     server → 172.217.25.36
CNAME ftp    → server
CNAME mail   → server
CNAME www    → server
```

Así, si la IP cambia, solo hay que actualizar el record `A`; los tres CNAME siguen funcionando.

**Un CNAME no puede apuntar a una IP**, solo a otro nombre. Y no se puede crear un CNAME en el **apex** del dominio (`google.com` a secas). Para eso AWS ofrece los **ALIAS records**, propios de Route 53.**

**Por qué está prohibido el CNAME en el apex**: el apex tiene obligatoriamente registros **SOA** y **NS**, y el estándar dice que un CNAME **no puede coexistir** con ningún otro registro del mismo nombre. De ahí la restricción; no es un capricho de AWS. Otro efecto secundario del CNAME: agrega **una consulta extra** (hay que resolver el alias y después el destino), lo que suma latencia y, en R53, se cobra doble.

![[Pasted image 20260627175931.png]]

> [!important] 🆕 ALIAS records (esto CAE mucho en SAA y DVA)
> El **ALIAS record** es exclusivo de Route 53 y resuelve el problema del CNAME en el apex:
> - **Sí funciona en el apex/zone root** (`animals4life.org` a secas), donde el CNAME está prohibido.
> - Mapea un nombre directamente a un **recurso de AWS**: ELB, CloudFront, S3 static website, API Gateway, otra hosted zone.
> - **Es gratis** cuando apunta a recursos de AWS (R53 no cobra las queries a un alias hacia un recurso AWS; un CNAME sí se cobra).
> - Se comporta como un A/AAAA para el cliente (devuelve IP), pero AWS lo mantiene actualizado solo cuando la IP del recurso cambia.
> Regla de examen: "necesito apuntar `midominio.com` (apex) a un **ELB / CloudFront / S3 website**" → **ALIAS record**, nunca CNAME.

Regla de examen: "necesito apuntar `midominio.com` (apex) a un **ELB / CloudFront / S3 website**" → **ALIAS record**, nunca CNAME.

**ALIAS vs. CNAME, lado a lado**

| | **ALIAS** | **CNAME** |
|---|---|---|
| Estándar DNS | No, exclusivo de R53 | Sí |
| Funciona en el apex | ✅ **Sí** | ❌ No |
| Apunta a | Recursos de AWS (y otros records de la misma zone) | Cualquier hostname |
| Costo de las queries | **Gratis** (hacia recursos AWS) | Se cobra |
| Qué ve el cliente | Un A/AAAA con la IP | Un CNAME (resolución extra) |
| Health checks / routing policies | ✅ Sí | ✅ Sí |

Regla práctica: **si el destino es un recurso de AWS, usá ALIAS siempre.** No hay caso donde el CNAME sea mejor.

### MX — Mail Exchange

Le dicen a los servidores de correo **a dónde enviar el email** de un dominio.

Tienen dos partes:

- **Priority** (preferencia): número más **bajo** = **mayor** prioridad.
- **Value**: el host del servidor de correo.

```
MX  10  mail                → se resuelve dentro de la misma zone
MX  20  mail.other.domain.  → FQDN (termina en punto)
```

Si el valor **no** termina en punto, se interpreta como un host **dentro de la misma zone**. Si termina en punto, es un **FQDN** absoluto.

**Cómo se usa la prioridad en la práctica**: el servidor que envía el mail intenta primero con el MX de menor número. Si no responde, pasa al siguiente. Por eso se configuran varios MX con prioridades escalonadas (10, 20, 30) apuntando a servidores distintos: es _failover_ de correo. Si dos MX tienen el **mismo** número, se reparte la carga entre ellos. El destino de un MX debe ser un nombre que resuelva a un **A record**, nunca una IP directa ni un CNAME.

### TXT — Text

Permiten agregar **texto arbitrario** a un dominio. Su uso más común es **demostrar la propiedad del dominio**.

Ejemplo: un servicio externo te dice _"probá que sos dueño de `animals4life.org`: agregá un TXT record con el valor `cats are the best`"_. Vos lo agregás a la zone, el servicio hace una **query TXT**, ve el valor esperado y valida ✅.

También se usan para configuración anti-spam: **SPF**, **DKIM**, **DMARC**.

**Qué hace cada uno de los tres anti-spam**

|Registro|Qué declara|Ejemplo|
|---|---|---|
|**SPF**|Qué servidores tienen permiso de enviar mail en nombre del dominio|`v=spf1 include:amazonses.com -all`|
|**DKIM**|Una firma criptográfica que prueba que el mail no fue alterado|Un TXT en `selector._domainkey.dominio.com`|
|**DMARC**|Qué hacer con los mails que fallan SPF/DKIM (nada, cuarentena, rechazar) y a dónde mandar reportes|`v=DMARC1; p=quarantine; rua=mailto:...`|

Los tres se configuran como TXT records. Cuando se usa **Amazon SES**, hay que agregarlos para que los mails no caigan en spam — es prácticamente un paso obligatorio de cualquier setup de correo.

### Otros tipos que conviene reconocer

|Tipo|Qué hace|
|---|---|
|**SOA** (Start of Authority)|Uno por zona. Guarda los metadatos: cuál es el name server primario, el mail del administrador, el número de serie de la zona y los timers de refresco. Lo crea R53 automáticamente.|
|**PTR**|El inverso del A: mapea **IP → nombre**. Vive en zonas especiales (`in-addr.arpa`). Se usa para verificación de servidores de correo; en AWS hay que pedirlo por soporte para las Elastic IPs.|
|**SRV**|Indica **host + puerto** de un servicio (`_sip._tcp.dominio.com`). Usado por SIP, Active Directory, XMPP.|
|**CAA**|Declara qué autoridades certificadoras pueden emitir certificados para el dominio. Es una protección contra emisiones fraudulentas.|
### TTL (Time To Live)

Es un valor **en segundos** que define **cuánto tiempo se puede cachear** un DNS record.

Flujo de una consulta:

1. El **client** le pregunta al **resolver**.
2. El resolver, si no tiene el dato cacheado, consulta la jerarquía: **Root** → **`.com`** → **`amazon.com`**.
3. El name server de `amazon.com` es el **autoritativo**: devuelve la respuesta real (`www`, TTL 3600).
4. El resolver **cachea** esa respuesta por 3600 segundos y se la devuelve al cliente.

|Tipo de respuesta|De dónde viene|
|---|---|
|**Authoritative**|Directamente del name server autoritativo de la zone. Es la fuente de verdad.|
|**Non-Authoritative**|Del caché del resolver. Es más rápida, pero puede estar desactualizada.|

**Consejo práctico** Antes de migrar un dominio o cambiar registros, **bajá el TTL** con anticipación (ej: a 60 segundos). Así, cuando hagas el cambio, los resolvers de todo el mundo lo toman rápido en vez de servir el valor viejo durante horas.

El procedimiento completo de una migración sin sorpresas:

1. **Días antes**: bajar el TTL del registro a 60 s. (Hay que esperar a que expire el TTL _viejo_ para que todos los resolvers tengan el nuevo — por eso "días antes", no "una hora antes".)
2. Hacer el cambio de IP/destino.
3. Verificar la propagación desde varios lugares (`dig`, herramientas online).
4. Una vez estable, **volver a subir el TTL** (3600 o más) para reducir consultas y costo.

**El trade-off del TTL, en una línea** **TTL alto** = menos consultas, más barato, más rápido para el usuario… pero los cambios tardan en propagarse. **TTL bajo** = cambios casi inmediatos… pero más consultas y más costo. Valores típicos: 300-3600 s en operación normal; 60 s durante una migración; 60 s también en registros usados para **failover de DR**, porque si el primario cae necesitás que el cambio se propague ya.
