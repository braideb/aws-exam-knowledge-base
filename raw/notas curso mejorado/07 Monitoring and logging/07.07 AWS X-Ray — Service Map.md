# AWS X-Ray — Service Map

**AWS X-Ray** ayuda a analizar y hacer debug de **aplicaciones distribuidas** en producción, como las construidas con una arquitectura de microservicios. Da una **vista end-to-end** de cada request a medida que atraviesa la aplicación, y un **mapa** de sus componentes, para encontrar la **causa raíz** de problemas de performance y errores.

X-Ray es un sistema de **distributed application tracing**: hace el seguimiento de una sesión/request a través de todos los servicios que toca.

### Cómo funciona

1. Cuando un usuario entra a una aplicación configurada con X-Ray, se genera un **trace ID** y se inserta en un **tracing header** (`X-Amzn-Trace-Id`).
2. Ese header viaja con la request por todos los servicios soportados que participan en ella.
3. Cada servicio compatible envía a X-Ray **segments**: bloques de datos con **host/IP, request, response, work done (tiempos) e issues** (errores, excepciones).
4. Si hace falta más detalle, un segment puede contener **subsegments** (por ejemplo, una llamada puntual a DynamoDB o a una API externa dentro de una Lambda).
5. X-Ray junta todos los segments de un mismo trace ID para reconstruir el **flujo end-to-end** de esa request.

| Término | Qué es |
|---|---|
| **Trace** | Todos los segments de una misma request (mismo trace ID). |
| **Segment** | Datos que aporta un servicio sobre su parte del trabajo. |
| **Subsegment** | Detalle más fino dentro de un segment. |
| **Service graph** | Los datos combinados de todos los servicios. |
| **Service map** | La representación visual del service graph: nodos (servicios) y aristas (llamadas), con latencias y errores. |

### Integración según el servicio

| Servicio | Cómo se habilita |
|---|---|
| **EC2** | Instalar el **X-Ray agent** (daemon). |
| **ECS** | Agent en las **tasks** (contenedor sidecar). |
| **Lambda** | Opción a habilitar (**Active tracing**). |
| **Elastic Beanstalk** | Agent **preinstalado** (se activa en la configuración). |
| **API Gateway** | Opción **por stage**. |
| **SNS / SQS** | **SNS** soporta active tracing; **SQS** propaga el trace header para que el consumidor continúe el trace. |

En **todos** los casos se necesitan **permisos de IAM** para enviar datos a X-Ray (por ejemplo, la managed policy `AWSXRayDaemonWriteAccess`, que incluye `xray:PutTraceSegments` y `xray:PutTelemetryRecords`).

> [!tip] Para el examen (DVA)
> - "Instalé el SDK pero no aparecen traces en EC2" → falta el **daemon** o los **permisos IAM** del instance role.
> - El daemon escucha en **UDP 2000**.
> - **Annotations** = pares key/value **indexados** → sirven para **filtrar/buscar traces**. **Metadata** = datos **no indexados** → solo para guardar info extra. Si la pregunta dice "buscar traces por X", la respuesta es annotation.
> - **Sampling rules**: X-Ray no registra todas las requests; por defecto, la primera por segundo y el 5% del resto.

> [!info] Actualización posterior al curso
> AWS está moviendo la instrumentación hacia **OpenTelemetry** (AWS Distro for OpenTelemetry, ADOT) como alternativa a los SDKs y el daemon propios de X-Ray. Los conceptos (trace, segment, service map) siguen siendo los mismos y son los que evalúa el examen.
