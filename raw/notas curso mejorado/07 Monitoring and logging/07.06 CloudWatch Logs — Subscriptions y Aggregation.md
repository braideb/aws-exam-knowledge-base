# CloudWatch Logs — Subscriptions y Aggregation

### Subscriptions

CloudWatch Logs se puede configurar para **enviar logs en tiempo real a otros destinos**. Si CloudWatch Logs es el punto donde se concentra todo el logging de AWS, las subscriptions son la forma de repartir esa información a otros sistemas. Se configuran **por log group**.

Partiendo del log group de producción de Catagram (ver diagrama), se crea un **subscription filter** en ese log group, que define:
- **Pattern:** limita qué log events maneja el filtro.
- **ARN del destino.**
- **Distribution:** cómo se agrupan/reparten los log data a medida que se envían al destino.
- **Permisos:** el IAM role que CloudWatch Logs necesita para escribir en ese destino.

### Destinos y "qué tan real time" es cada uno

| Destino | Latencia | Comentario |
|---|---|---|
| **Kinesis Data Firehose** (hoy **Amazon Data Firehose**) | **Near real time** | Hace buffering antes de entregar (en el curso, 60 s). Ideal para dejar los logs en **S3** o en herramientas de terceros. |
| **Elasticsearch** (hoy **Amazon OpenSearch Service**) | Real time | Nativo desde la consola, a través de una **Lambda gestionada por AWS**. |
| **Lambda custom** | Real time | Código propio para entregar a cualquier destino. |
| **Kinesis Data Streams** | Real time | Base del patrón de aggregation (abajo). |

> [!info] Actualización posterior al curso
> - **Elasticsearch Service** pasó a llamarse **Amazon OpenSearch Service** (2021) y **Kinesis Data Firehose** pasó a llamarse **Amazon Data Firehose** (2024). En el examen pueden aparecer con cualquiera de los dos nombres.
> - Firehose hoy permite configurar el buffering (incluso muy bajo), pero sigue considerándose **near real time**.
> - Un log group admite **hasta 2 subscription filters**.

> [!tip] Para el examen
> - **Real time** a cualquier lado → **Lambda** (o Kinesis Data Streams).
> - **Near real time** a S3 / terceros, sin código → **Firehose**.
> - Histórico en lote → `CreateExportTask` (hasta 12 h, ver [[07.05 CloudWatch Logs — Architecture#Export a S3|Export a S3]]).

### Aggregation (multi-cuenta)

Las subscriptions también sirven para armar una arquitectura de **log aggregation**. Supongamos tres cuentas (colores distintos en la imagen), cada una con su propio CloudWatch Logs aislado:

- Cada cuenta crea subscription filters que apuntan a un **Kinesis Data Stream central**.
- Para la **persistencia**, **Kinesis Data Firehose** lee del stream y guarda todo en **S3** o lo manda a herramientas de visualización.

![[Pasted image 20260923230724.png]]

> [!info] Detalle de implementación cross-account
> Para que una cuenta envíe logs a un stream de otra cuenta, en la cuenta central se crea un **destination** de CloudWatch Logs (que envuelve al Kinesis stream) con una **destination policy** que autoriza a las cuentas origen. Las cuentas origen apuntan su subscription filter al ARN de ese destination.
