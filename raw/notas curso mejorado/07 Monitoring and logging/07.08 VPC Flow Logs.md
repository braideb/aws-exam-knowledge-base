# VPC Flow Logs

> Complementa [[05.10 VPC Flow Logs|VPC Flow Logs]] del módulo 05, que agrega el ciclo de vida del flow log, el campo `log-status` y cómo deducir si bloqueó un SG o una NACL.

### Qué capturan

Lo más importante: los VPC Flow Logs capturan **solo la metadata** de los paquetes, **no su contenido** (payload). Esa metadata incluye source IP, destination IP, source y destination ports, tamaño, protocolo, acción, etc.

> [!tip] Para el examen
> Si se necesita **ver el contenido** de los paquetes → **VPC Traffic Mirroring**, no Flow Logs.

### Dónde se aplican

Los Flow Logs funcionan como un monitor virtual que se conecta (attach) dentro de una VPC. Capturan metadata **desde el punto de captura hacia abajo**, en **tres niveles**:

| Nivel | Qué cubre |
|---|---|
| **VPC** | Todas las ENIs de todas las subnets de la VPC. |
| **Subnet** | Todas las ENIs de esa subnet. |
| **ENI** | Solo esa interfaz específica. |

Según la configuración, capturan el tráfico **ACCEPTED**, el **REJECTED** o **ALL** (ambos).

![[Pasted image 20260924000057.png]]

> **Qué muestra:** una VPC llamada `A4L-VPC` con dos subnets y dos Flow Logs configurados en puntos de captura distintos.
> - **Izquierda:** la jerarquía **VPC → Subnet(s) → Interface(s)**, con el texto "Flow logs capture **metadata** from the capture point down".
> - **Subnet `10.16.16.0/20` (azul):** dos instancias de base de datos, cada una con su ENI. Un Flow Log a nivel de subnet (el recuadro punteado rodea toda la subnet) recibe la metadata de las dos ENIs.
> - **Subnet `10.16.48.0/20` (verde):** una instancia de la app Catagram con su ENI. El recuadro punteado rodea solo la instancia, así que es un Flow Log **a nivel de ENI**.
> - **Tráfico:** el usuario **BOB** accede a la instancia de Catagram, que a su vez se comunica con una de las bases de datos de la otra subnet.
> - **Destinos:** los dos Flow Logs envían sus registros a un **S3 Bucket** y a **CloudWatch Logs**.
> - **Derecha:** "Flow Logs can capture **ACCEPTED**, **REJECTED** or **ALL** metadata".
> - **Flow Log Record de ejemplo** (el mismo en ambos destinos):
>   `2 ACC-ID eni-ID 119.18.34.78 10.16.48.20 1337 443 6 4 336 1432917027 1432917142 ACCEPT OK`

### No son real time

Hay un retraso entre que el tráfico pasa por las interfaces monitoreadas y su aparición en los Flow Logs (el intervalo de agregación es de **10 minutos** por defecto, configurable a **1 minuto**).

> [!tip] Para el examen
> Pregunta frecuente: con Flow Logs **no** se puede ver telemetría **en tiempo real** del flujo de paquetes.

### Destinos de los Flow Logs

| Destino | Ventaja |
|---|---|
| **S3** | Acceso directo a los archivos; integrar con una solución de monitoreo de terceros o propia. Consultables con **Athena** (SQL, se paga por datos leídos). Útil si hay un equipo de datos y un proceso de revisión formal. |
| **CloudWatch Logs** | Se integra con otros productos: metric filters, alarms, Logs Insights, subscriptions. |
| **Kinesis Data Firehose** | Entrega near real time a otros destinos o terceros. |

> [!info] Actualización posterior al curso
> El curso menciona solo **S3** y **CloudWatch Logs**; hoy también se pueden enviar directo a **Amazon Data Firehose** (ex Kinesis Data Firehose). **Athena** no es un destino: consulta los flow logs que ya están en S3.

### Formato de un Flow Log record

Un VPC Flow Log es una colección de filas (**Flow Log records**). Los campos importantes están resaltados en rosado en la imagen y en negrita en la tabla:

![[Pasted image 20260924000314.png]]

El record de ejemplo del diagrama anterior, campo por campo:

| Campo | Valor |
|---|---|
| version | `2` |
| account-id | `ACC-ID` |
| interface-id | `eni-ID` |
| **srcaddr** | `119.18.34.78` |
| **dstaddr** | `10.16.48.20` |
| **srcport** | `1337` |
| **dstport** | `443` |
| **protocol** | `6` (TCP) |
| packets | `4` |
| bytes | `336` |
| start | `1432917027` |
| end | `1432917142` |
| **action** | `ACCEPT` |
| log-status | `OK` |

### Ejemplo: ICMP ping

![[Pasted image 20260924000637.png]]

> **Qué muestra:** los registros que genera un **ICMP PING** entre un usuario (con su laptop) y la instancia de Catagram.
> - `2 ACC-ID eni-ID 119.18.34.78 10.16.48.20 0 0 1 4 336 1432917027 1432917142 ACCEPT OK`
> - `2 ACC-ID eni-ID 10.16.48.20 119.18.34.78 0 0 1 4 336 1432917094 1432917142 REJECT OK`
> - La primera fila va del usuario (`119.18.34.78`) a la instancia (`10.16.48.20`) y es **ACCEPT**. La segunda es la respuesta, en sentido contrario, y es **REJECT**. En ambas, srcport y dstport valen `0` (ICMP no usa puertos).
> - Una flecha señala el campo protocol (`1`), con la aclaración "**ICMP=1, TCP=6, UDP=17**".
> - Abajo: "To and from **169.254.169.254**, **169.254.169.123**, **DHCP**, Amazon **DNS** server & **Amazon Windows license** not recorded".

Dos datos que salen de este ejemplo:
- **Números de protocolo:** ICMP = `1`, TCP = `6`, UDP = `17`.
- **Tráfico que no se registra:** hacia y desde `169.254.169.254` (instance metadata), `169.254.169.123` (Amazon Time Sync), DHCP, el Amazon DNS server y la activación de licencia de Windows.

> [!tip] Para el examen
> Request **ACCEPT** + respuesta **REJECT** = el que bloquea es **stateless** → una **NACL** sin regla de salida (el Security Group es stateful y habría dejado volver la respuesta). Ver [[05.10 VPC Flow Logs|VPC Flow Logs (módulo 05)]].
