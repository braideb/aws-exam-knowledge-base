# Bootstrapping EC2 con User Data

El **bootstrapping** (arranque) no es algo exclusivo de EC2: es un término general de la automatización de sistemas para cuando un sistema se configura solo, o hace por su cuenta algunos pasos de su configuración. En EC2 sirve para automatizar la construcción de una instancia, es decir, para que al lanzarla llegue a un estado ya configurado, sin depender de una AMI predeterminada o de una AMI con la configuración ya hecha. Te permite indicarle a una instancia EC2 que haga algo al lanzarse: instalar software y, un poco después, configurarlo.

### User data

En EC2, el bootstrapping se hace con el **user data**, que se inyecta en la instancia igual que el metadata. De hecho, se lee desde la misma IP del [[06.24 Instance Metadata (IMDS)|metadata service]], pero en lugar del metadata lo que se obtiene es el user data. Ese endpoint es siempre la IP link-local **`169.254.169.254`**:

| Qué | Ruta |
|---|---|
| User data | `http://169.254.169.254/latest/user-data` |
| Metadata | `http://169.254.169.254/latest/meta-data/` |

El user data es un bloque de datos (una pieza de información) que le podés pasar a una instancia EC2, y el sistema operativo de la instancia ejecuta todo lo que le pases.

> [!tip] Para el examen: el user data se ejecuta **una sola vez, en el lanzamiento (only on launch)**
> - Si modificás el user data y reiniciás la instancia, **no se vuelve a ejecutar**. Se usa únicamente para la configuración en el momento del arranque.
> - Está limitado a **16 KB**. Si necesitás más, el script tiene que descargar lo pesado de S3.
> - Se puede **modificar con la instancia detenida (stopped)**, pero igual no se ejecuta en cada reboot.
> - En Linux, para que se ejecute como script, suele empezar con un shebang (`#!/bin/bash`).

### EC2 no valida ni interpreta el user data

EC2 como servicio **no valida ni interpreta** el user data. Si le pedís que pase datos aleatorios, los pasa; si le pasás comandos que borran todo el boot volume de la instancia, también los pasa. EC2 solo se los entrega a la instancia a través del user data, y dentro del sistema operativo hay un proceso que los ejecuta como usuario **root**. En las AMIs modernas, el que lee el user data y lo ejecuta es **`cloud-init`**. En resumen: la instancia tiene que "entender" lo que se le manda, porque lo va a ejecutar sin más.

> [!warning] Para el examen: el user data **NO es seguro**
> Cualquiera que pueda acceder al metadata de la instancia (por ejemplo, un proceso dentro de ella) puede leerlo **en texto plano**. Por eso no se usa para contraseñas ni credenciales de largo plazo. Para eso están **Secrets Manager** o **SSM Parameter Store (SecureString)** ([[09.04 SSM Parameter Store|Parameter Store]]): el script los puede leer al arrancar usando el [[09.03 EC2 Instance Roles e Instance Profiles|instance role]].

### Arquitectura

La arquitectura del bootstrapping es bastante simple:

1. Se usa una AMI para lanzar una instancia EC2 como siempre. Eso crea un EBS volume que se adjunta a la instancia, según el block device mapping que define la AMI. Hasta acá, nada nuevo.
2. Lo distinto: el servicio EC2 **le entrega el user data** a la instancia.
3. Dentro del sistema operativo de la instancia hay software que busca user data en la IP del metadata y, si lo encuentra, **lo ejecuta en el lanzamiento**.

El user data se trata como cualquier otro script que corre en el sistema operativo, así que **tiene que ser válido**. Cuando el script termina de ejecutarse, la instancia pasa a estado **running** y queda lista para el servicio: terminó de arrancar, el user data se ejecutó bien y la instancia funciona.

> [!warning] Si el user data falla, la instancia **igual queda en running**
> El user data es independiente de EC2, que solo se lo entrega a la instancia. Por eso la instancia **sigue en running** y **pasa los status checks** aunque el script haya fallado. Salvo que el script haya borrado gran parte del sistema operativo, probablemente te puedas conectar igual. Lo más probable es que quede **mal configurada (bad config)**.
