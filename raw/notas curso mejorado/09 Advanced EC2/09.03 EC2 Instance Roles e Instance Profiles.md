# EC2 Instance Roles e Instance Profiles

> [!note] Resumen de la lección
> Los EC2 instance roles y los instance profiles son la forma de dar a las aplicaciones que corren en una instancia EC2 permisos para acceder a recursos de AWS en tu nombre. Las credenciales temporales de corto plazo se obtienen a través del EC2 Instance Metadata, y EC2 y STS las renuevan automáticamente.

A lo largo del curso ya vimos que los [[03.06 IAM Roles|IAM roles]] son la best practice para que los servicios de AWS tengan permisos sobre otros servicios de AWS en tu nombre: si un servicio puede asumir un role, recibe los permisos de ese role. Un **EC2 instance role** es un role que puede asumir una instancia, y **todo lo que corre en esa instancia** obtiene los permisos que da ese role. Hay algunos detalles que importan, así que veamos cómo funciona desde el punto de vista de la arquitectura.

### Arquitectura: role → instance profile → instancia

1. Todo empieza con un **IAM role** que tiene una **permissions policy** adjunta. Quien asuma el role obtiene credenciales temporales con los permisos de esa policy.
2. Un EC2 instance role permite que **el servicio EC2** asuma ese role. Es decir, la propia instancia EC2 puede asumirlo y acceder a esas credenciales.
3. Falta una forma de **entregar** esas credenciales a la instancia para que las aplicaciones de adentro puedan usar los permisos del role. Para eso está el **instance profile**, un **contenedor del IAM role**, que es lo que efectivamente hace llegar los permisos a la instancia.

> [!tip] Para el examen: lo que se adjunta a la instancia es el **instance profile**, no el role
> - Si creás el instance role **desde la consola**, se crea automáticamente un instance profile **con el mismo nombre**.
> - Con **la CLI o CloudFormation** tenés que crear **las dos cosas por separado**.
> - Cuando en la consola parece que adjuntás un role directamente a la instancia, en realidad estás adjuntando el instance profile del mismo nombre.

### Las credenciales llegan por el instance metadata

Cuando se asume un IAM role, se obtienen credenciales de seguridad **temporales** que caducan y que dan los permisos de la permissions policy del role. Dentro de una instancia EC2, esas credenciales se entregan por el **[[06.24 Instance Metadata (IMDS)|instance metadata]]**: una aplicación que corre en la instancia puede leerlas y usarlas para acceder a recursos de AWS, como S3.

Concretamente, dentro del metadata está la ruta:

```
http://169.254.169.254/latest/meta-data/iam/security-credentials/<role-name>
```

Ahí están las credenciales temporales, que rotan todo el tiempo y son válidas mientras el role siga adjunto a la instancia.

Una de las ventajas de esta arquitectura es que las credenciales del metadata **siempre son válidas**: EC2 y [[03.09 Security Token Service (STS)|STS]] trabajan juntos para renovarlas antes de que caduquen. Mientras la aplicación siga consultando el metadata, nunca se va a quedar con credenciales caducadas.

> [!warning] Cuidado con cachear las credenciales
> Las aplicaciones de la instancia no deberían cachear estas credenciales por mucho tiempo. Alcanza con volver a consultar el metadata antes de que caduquen, o hacerlo periódicamente.

### IMDSv2

Relacionado, y cada vez más presente en el examen: **IMDSv2**, la versión 2 del metadata service.

| | IMDSv1 | IMDSv2 |
|---|---|---|
| Modelo | Request/response simple (`GET`) | **Session-oriented** |
| Cómo se consulta | `GET` directo a la ruta | 1) `PUT` a `/latest/api/token` para obtener un token (válido **hasta 6 horas**). 2) Mandar el token en el header `X-aws-ec2-metadata-token` en cada request |
| Protección contra SSRF | No | Sí: el **hop limit por defecto es 1**, así que el token no puede salir de la instancia |

Los SDK y la CLI modernos lo manejan de forma transparente. El detalle (con los comandos `curl`) está en [[06.24 Instance Metadata (IMDS)|Instance Metadata (IMDS)]].

### Usá roles, no credenciales de largo plazo

Siempre que se pueda, **usá roles** en lugar de guardar credenciales de largo plazo. Esto se repite durante todo el curso y es importante para el examen. Guardar credenciales de largo plazo ([[02.04 IAM Access Keys|access keys]]) fuera de un almacenamiento seguro, por ejemplo dentro de una instancia, nunca es buena idea. Las herramientas de la CLI usan automáticamente las credenciales del role.

La CLI y los SDK buscan credenciales siguiendo una **cadena (credentials provider chain)**, en este orden:

| Orden | Fuente |
|---|---|
| 1 | Variables de entorno |
| 2 | Perfil en `~/.aws/credentials` |
| 3 | Instance metadata (el **instance role**) |

> [!tip] Para el examen: error típico
> Si dejaste **access keys** en el archivo de credenciales de la instancia, **tienen prioridad sobre el role**. La best practice es no tener keys en la instancia y dejar que la CLI o el SDK usen el role automáticamente.
