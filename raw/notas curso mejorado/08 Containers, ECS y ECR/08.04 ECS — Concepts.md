# Elastic Container Service (ECS) — Concepts

ECS es la forma cómoda de usar Docker en AWS, sin tener que hacer todo a mano en una EC2 como en la [[08.03 Demostración - Container of cats (Docker en EC2)|demo anterior]].

> [!tip] Idea clave
> **ECS es a los containers lo que EC2 es a las virtual machines.**

ECS es un servicio que acepta containers y algunas instrucciones que le das, y **orquesta dónde y cómo ejecutar esos containers**. Es un servicio **managed** de cómputo basado en containers, y funciona en dos modos, **EC2** y **Fargate**, que cambian radicalmente cómo funciona por debajo (se ven en [[08.05 ECS — Cluster Types (EC2 y Fargate)|Cluster Types]]). Para esta lección alcanza con decir que ECS permite crear un **cluster**.

Los **clusters** son el lugar donde corren tus containers: le das a ECS una container image y ECS la ejecuta en forma de container dentro del cluster, según cómo quieras que se ejecute.

### Container images y registry

Primero necesitás una forma de decirle a ECS qué container images querés ejecutar y cómo querés que se gestionen. Esas images van a estar guardadas en algún **container registry**: ya viste Docker Hub, y AWS ofrece el suyo, **Elastic Container Registry (ECR)**. ECR tiene la ventaja de estar integrado con AWS (aplican los permisos y beneficios de escalabilidad habituales), pero en esencia es solo un container registry: podés usarlo o usar otro. Ver [[08.08 Elastic Container Registry (ECR)|ECR]].

### Container definition

Para informarle a ECS sobre tus container images creás una **container definition**. Le dice a ECS:
- **dónde está tu container image** (lógicamente, la necesita), y
- **qué puerto usa tu container** (en la demo se expuso el puerto 80, HTTP; eso también se define acá).

Da la información justa sobre **el container individual** que querés definir.

### Task definition

Una **task** en ECS representa una **aplicación autónoma** (self-contained). Puede tener **uno o varios containers**: una aplicación muy simple podría usar uno solo (como la app de los gatos), o podría usar varios, por ejemplo uno para la web app y otro para la base de datos. La task representa la aplicación en su conjunto, y por eso **guarda las container definitions** que se usan para armarla.

Un caso típico de task con varios containers es el **patrón sidecar**: un container auxiliar que corre al lado del container de la app, dentro de la misma task.

> [!tip] Para el examen
> El ejemplo clásico es **X-Ray**: para tener tracing en ECS, el **X-Ray daemon se corre como sidecar container** en la task, y la app le manda los datos de tracing a ese container. Ver [[07.07 AWS X-Ray — Service Map|AWS X-Ray]].

La task definition guarda:

| Qué define | Detalle |
|---|---|
| **Recursos** | CPU y memoria que usa la task |
| **Network mode** | Cómo se conectan los containers a la red (ver `awsvpc` vs `bridge` en [[08.05 ECS — Cluster Types (EC2 y Fargate)#Networking y cómo se conecta un ALB\|Cluster Types]]) |
| **Compatibilidad** | Si la task corre en EC2 mode o en Fargate |
| **Task role** | El IAM role que asume la task (ver abajo) — algo realmente importante |
| **Volúmenes** | Los volúmenes que usan los containers. Para storage **persistente y compartido entre tasks** se usa **EFS**, que también funciona con Fargate |
| **Container definitions** | Uno o más containers |

Recordá la diferencia: la container definition es **solo un indicador de dónde está guardado el container y qué puertos expone**; todo lo demás se define en la task definition.

Cuando creás una task definition desde la consola de ECS, en realidad también creás una container definition junto con ella, pero desde el punto de vista de la arquitectura son cosas separadas. Esto confunde todavía más porque muchas tasks tienen **una sola** container definition (va a ser el caso de la [[08.07 Demostración - Container of cats en Fargate|demo de container of cats en Fargate]]). Pero **tasks y containers son cosas distintas**: una task puede incluir uno o más containers, y que muchas tasks tengan uno solo no ayuda con la confusión.

### Task role

El **task role** es un **IAM role que la task puede asumir**. Cuando la task lo asume, obtiene **credenciales temporales** que se pueden usar dentro de la task para interactuar con recursos de AWS. Los task roles son la **best practice** para darles a los containers de ECS permisos para acceder a productos y servicios de AWS.

> [!tip] Para el examen
> Según el instructor, el task role aparece en **al menos una pregunta del examen**.

### Los tres roles de ECS

El task role no es el único rol. Para el examen hay que distinguir tres que se confunden seguido:

| Rol | Quién lo usa | Para qué |
|---|---|---|
| **Task role** | **Tu código** dentro del container | Llamar a servicios de AWS: leer de S3, escribir en DynamoDB, etc. |
| **Task execution role** | El **ECS agent** o **Fargate**, no tu app | Hacer **pull de la image** desde ECR, mandar los **logs a CloudWatch Logs** y leer los **secrets** de Secrets Manager o Parameter Store referenciados en la task definition |
| **Container instance role** | El **ECS agent** — **solo en EC2 mode** | Es el instance profile de las instancias EC2; se usa para **registrar la instancia en el cluster** |

> [!tip] Regla práctica
> - La task **no puede hacer pull** de la image o **no aparecen los logs** → el problema está en el **task execution role**.
> - La **app no puede acceder a S3** (u otro servicio de AWS) → está en el **task role**.

### Service

Una task en ECS **no escala por sí sola ni tiene high availability (HA)** por sí sola. Para eso está el **ECS service**, que se configura mediante una **service definition**.

El service es la forma que tiene ECS de definir **cómo queremos que escale una task**, es decir, **cuántas copias** queremos ejecutar. Agrega capacidad y resiliencia, porque podemos tener múltiples copias independientes de la task corriendo, y se puede poner un **load balancer** delante del service para que la carga entrante se distribuya entre todas sus tasks.

Para tasks que vas a correr a largo plazo y que son críticas para el negocio (business critical), normalmente usarías un service. El service es lo que te permite configurar:
- el **reemplazo de tasks que fallan** (restarts),
- el **scaling**,
- cómo **distribuir la carga** entre varias copias de la misma task.

En la demo de container of cats **no se usa un service**, porque solo se quiere ejecutar una copia, y una sola copia de una task puede correr por sí sola.

#### Service auto scaling

El scaling de un service se configura con **service auto scaling** (que usa **Application Auto Scaling**) y cambia **la cantidad de tasks** del service. Lo más común es **target tracking**: mantener en un valor objetivo el uso promedio de **CPU** o de **memoria** del service, o la cantidad de **requests por target del ALB**.

> [!tip] Para el examen
> Service auto scaling agrega o quita **tasks**, no **instancias**. En EC2 mode la capacidad del cluster se escala aparte (capacity provider). Ver [[08.05 ECS — Cluster Types (EC2 y Fargate)#EC2 mode|EC2 mode]].

#### Deployments

Para desplegar una versión nueva de la app, **registrás una nueva revisión de la task definition** y **actualizás el service** para que la use. El deploy puede ser de dos tipos:

| Tipo | Cómo funciona |
|---|---|
| **Rolling update** | ECS va reemplazando las tasks viejas por nuevas. Se controla con `minimumHealthyPercent` (mínimo de tasks, como % del desired count, que tienen que seguir corriendo durante el deploy) y `maximumPercent` (máximo de tasks que puede haber corriendo durante el deploy). |
| **Blue/green con CodeDeploy** | Se levanta la versión nueva al lado de la vieja y el tráfico del ALB se pasa de una a otra, **todo de una vez** o **de a poco** (canary o linear). |

### Resumen: el cluster y sus building blocks

Tanto las tasks como los services se despliegan en un **ECS cluster**, y esto aplica igual si el cluster está basado en EC2 o en Fargate. A alto nivel los building blocks son los mismos: **creás un cluster y después desplegás tasks o services en ese cluster**.
