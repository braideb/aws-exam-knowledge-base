# Containers — Virtualización vs Containerization

Cuando hablamos de virtualización, en realidad hablamos de la **virtualización del sistema operativo**: el proceso de ejecutar múltiples sistemas operativos sobre el mismo hardware físico. Ya se vio en [[06.01 Virtualization 101|Virtualization 101]]; acá va un repaso para entender la diferencia con los **containers**.

### El problema de la virtualización: uso pesado y duplicación

Tenemos un **EC2 host** ejecutando el **Nitro hypervisor**, y sobre él corren varias **virtual machines (VMs)**. Cada VM es un **sistema operativo completo** con sus recursos asociados.

Lo que a veces se malinterpreta es **cuánto de una VM usa únicamente el sistema operativo**. Si ejecutás una VM con, digamos, 4 GB de RAM y un disco de 4 GB, el OS puede consumir fácilmente entre el **60 y el 70% del disco** y gran parte de la memoria disponible, dejando relativamente poco para las aplicaciones que corren en esa VM y su **runtime** (entorno de ejecución). En el diagrama se ve que el **guest OS** consume un gran porcentaje de los recursos asignados a cada VM.

Ahora bien, ¿qué probabilidad hay de que muchos de esos sistemas operativos sean en realidad **el mismo**? Pensá en los servidores de tu propia empresa: ¿cuántos corren Windows? ¿Cuántos Linux? ¿Cuántos comparten la misma versión principal del OS? Eso es **duplicación**: si todos los guest OS usan el mismo sistema operativo (o uno similar), estamos desperdiciando recursos.

Además, como el OS consume tantos recursos, **cada operación sobre una VM** (cada reinicio, cada parada, cada arranque) implica manejar el sistema operativo completo.

Lo que realmente queremos es ejecutar las aplicaciones 1 a 6 en **entornos separados, aislados y protegidos**. ¿Hacen falta seis copias del mismo sistema operativo ocupando disco y recursos del host para eso? No, si usamos containers.

### Containerization

Con **containerization** las cosas son muy distintas. Seguimos teniendo el **host hardware**, pero en lugar de virtualización tenemos **un** sistema operativo (**host OS**) corriendo sobre ese hardware y, encima de él, un **container engine**. Uno muy popular es **Docker**.

En cierto modo, un container es similar a una VM: proporciona un **entorno aislado** en el que se puede ejecutar una aplicación. La diferencia:

| | VM | Container |
|---|---|---|
| Qué corre | Un sistema operativo completo y aislado | Un **proceso** dentro del host OS |
| Sobre qué | Un hypervisor | El host OS + el container engine |
| Qué comparte con el host | Nada (tiene su propio OS) | Usa el host OS para muchas cosas, como **networking** y **file I/O** |

Por ejemplo, si el host OS fuera Linux, podría usar Docker como container engine: Linux más el Docker engine pueden ejecutar un container, y ese container corre como **un único proceso** dentro del sistema operativo (potencialmente uno de muchos).

Pero **dentro** de ese proceso, el container es como un sistema operativo aislado: tiene **su propio filesystem**, separado del resto, y puede ejecutar **procesos hijos** (child processes) que también están aislados de todo lo demás. Por lo tanto, un container podría ejecutar un web server o un application server de forma completamente aislada.

![[Pasted image 20260926194132.png]]


Un container corre encima del host OS y del container engine, pero consume **muy poca memoria**: el único consumo de memoria o disco es el de **la aplicación y los elementos del runtime** que necesita (librerías y dependencias). El sistema operativo puede correr muchos otros containers, cada uno con una aplicación.

Así, con containers logramos una arquitectura parecida a la de virtualización (las mismas seis aplicaciones, aisladas), pero **sin un sistema operativo completo para cada una**. Los containers son mucho más livianos que las VMs, lo que significa que podemos correr **muchos más containers por host**.

> [!tip] Idea clave
> **Densidad**: la capacidad de ejecutar más aplicaciones en el mismo hardware es uno de los principales beneficios de los containers frente a las VMs.
