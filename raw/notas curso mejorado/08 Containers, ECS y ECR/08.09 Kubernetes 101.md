# Kubernetes 101

Un cluster de Kubernetes es un **cluster highly available de recursos de cómputo, organizados para trabajar como una sola unidad**.

### Cluster Structure

| Pieza | Qué es |
|---|---|
| **Cluster control plane** | La parte que **administra el cluster**: scheduling, gestión de aplicaciones, scaling, deployment y mucho más |
| **Nodes** | Servidores **virtuales o físicos** que funcionan como **workers** dentro del cluster. Son los que realmente ejecutan tus aplicaciones en containers |

En cada node corre software; como mínimo:
- **containerd** (u otro **container runtime**, como Docker): el software que se encarga de las operaciones con containers.
- **kubelet**: un agente que interactúa con el cluster control plane. El kubelet de cada node se comunica con el control plane usando la **Kubernetes API**.

Esa es la funcionalidad de alto nivel: **el control plane orquesta aplicaciones en containers que se ejecutan en nodes**.

#### Pods

Los **pods** son la **unidad de cómputo más chica en Kubernetes**. Un pod puede tener varios containers, y les proporciona **almacenamiento y networking compartidos**. Pero es muy común la arquitectura **one-container-one-pod**: cada pod contiene un solo container.

Cuando pienses en Kubernetes, **no pienses en containers: pensá en pods**. Vas a trabajar con pods y a gestionar pods, y son los pods los que manejan los containers que tienen adentro. A nivel de arquitectura, generalmente solo se ponen varios containers en un mismo pod cuando están **tightly coupled** (fuertemente acoplados): necesitan estar muy cerca y dependen mucho unos de otros. Además, aunque vas a estar expuesto a los pods, rara vez los vas a administrar directamente.

> [!warning] Los pods no son permanentes
> Para aprovechar Kubernetes al máximo tenés que verlos como algo **temporal**: se crean, hacen un trabajo y se descartan. Un pod se puede eliminar cuando terminás, puede ser **desalojado** (evicted) por falta de recursos o puede caerse si falla el propio node. No están diseñados para verse como entidades highly available. Hay otros elementos relacionados con los pods que dan más permanencia, pero eso se ve en otro lado.

#### Control plane

| Componente | Función |
|---|---|
| **kube-apiserver** | La API, el **front end del control plane**. Es con lo que interactúa todo lo que necesita comunicarse con el control plane (nodes y demás elementos del cluster). Se puede **escalar horizontalmente** para mejorar el rendimiento y garantizar HA |
| **etcd** | Un **key-value store highly available**; básicamente, una base de datos simple corriendo dentro del cluster, que actúa como el **backing store principal** de los datos del cluster |
| **kube-scheduler** | Revisa constantemente si hay pods **sin un node asignado** y les asigna uno según sus requerimientos de recursos. Se asegura de que el cómputo de los nodes se use de manera eficiente |
| **cloud-controller-manager** (opcional) | Permite que Kubernetes se **integre con proveedores cloud** (AWS, Azure, GCP): el control plane interactúa de cerca con esa plataforma. Si corrés un deployment chico en tu casa, probablemente no lo uses |
| **kube-controller-manager** | Una colección de procesos (ver abajo) |

Procesos del **kube-controller-manager**:
- **Node controller:** monitorea y responde ante cualquier caída (outage) de un node.
- **Job controller:** se encarga de ejecutar pods para correr jobs (tareas puntuales).
- **Endpoint controller:** completa (populates) los endpoints del cluster; es lo que **vincula los services con los pods**.
- **Service Account & Token controllers:** se encargan de crear cuentas y API tokens.

#### Nodes

En cada node, además del container runtime y el kubelet, corre **kube-proxy** (k-proxy): un network proxy que **coordina el networking** con el cluster control plane. Ayuda a implementar los **services** y configura las reglas que permiten la comunicación con los pods **desde dentro o fuera del cluster**. Podés tener un cluster de Kubernetes, pero vas a querer cierto nivel de comunicación con el mundo exterior, y eso es lo que ofrece kube-proxy.

### Resumen

| Concepto | Qué es |
|---|---|
| **Cluster** | Un deployment de Kubernetes: management, orquestación… |
| **Node** | Recursos: los pods se ubican en nodes para correr |
| **Pod** | 1+ containers; la unidad más chica en Kubernetes; a menudo 1 container por pod |
| **Service** | Abstracción: un servicio que corre en uno o más pods |
| **Job** | Ad hoc: crea uno o más pods hasta completarse |
| **Ingress** | Expone una forma de entrar a un service: **Ingress ⇒ Routing ⇒ Service ⇒ 1+ Pods** |
| **Ingress Controller** | Lo que provee el ingress (por ejemplo, el **AWS Load Balancer Controller** usa **ALB/NLB**) |
| **Persistent Storage (PV)** | Un volumen cuyo ciclo de vida **va más allá de cualquier pod** que lo use |
