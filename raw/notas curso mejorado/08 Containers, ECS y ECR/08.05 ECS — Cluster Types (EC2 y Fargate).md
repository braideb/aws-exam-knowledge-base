# ECS — Cluster Types (EC2 y Fargate)

Hay dos tipos (modos) de cluster: **EC2** y **Fargate**.

El cluster mode define varias cosas, pero una de las principales es **cuánto del admin overhead** de ejecutar un conjunto de container hosts **administrás vos y cuánto administra AWS**. Los fundamentos técnicos de ambos son importantes, pero el principal diferenciador es qué partes son responsabilidad tuya y cuáles gestiona AWS. También hay diferencias de costos y escenarios que favorecen uno u otro (ver [[08.06 EC2 vs ECS (EC2) vs Fargate|EC2 vs ECS (EC2) vs Fargate]]).

A este nivel alcanza con entender la arquitectura básica de ambos modos y en qué situaciones elegirías uno u otro.

### Lo que comparten: el management de ECS

En los dos modos existen los mismos componentes de gestión de alto nivel:

| Componente | Función |
|---|---|
| **Scheduling and orchestration** | Decide qué correr y cuándo |
| **Cluster manager** | Gestiona el cluster |
| **Placement engine** | Decide **dónde** se ejecutan los containers (en qué container host) |

También en los dos se usan **registries** para las container images, y **task definitions** y **service definitions** para definir tasks y services (ver [[08.04 ECS — Concepts|ECS — Concepts]]). Lo que cambia es **cómo se hostean realmente los containers**.

### EC2 mode

Con EC2 mode, el ECS cluster se crea **dentro de una VPC de tu cuenta de AWS**, y se beneficia de las múltiples Availability Zones (AZs) disponibles en ella (en el ejemplo, AZ A y AZ B).

En EC2 mode se usan **instancias EC2 para ejecutar los containers**. Cuando creás el cluster especificás un tamaño inicial, que controla la cantidad de **container instances**, y eso lo gestiona un **Auto Scaling Group (ASG)**. Los ASGs todavía no se vieron en el curso, pero son una forma de controlar el **scaling horizontal** de las instancias EC2: agregan instancias cuando los requerimientos lo exigen y las eliminan cuando ya no hacen falta.

Supongamos que tenemos cuatro container instances. **Son simplemente instancias EC2**: las vas a ver en tu cuenta, te las van a cobrar e incluso podés conectarte a ellas.

> [!warning] Se pagan aunque estén vacías
> Una vez aprovisionadas, **las container instances se pagan independientemente de los containers que tengas corriendo en ellas**. Aunque no estés ejecutando ninguna task ni service, las seguís pagando mientras estén corriendo. Por eso se espera que administres la cantidad de container hosts del cluster.

Con EC2 mode **sos responsable de esas instancias** que actúan como container hosts. ECS las aprovisiona, pero se espera que vos las administres, generalmente a través de las herramientas de ECS. Por lo tanto, **ECS en EC2 mode no es una solución serverless**: tenés que preocuparte por la **capacidad y la disponibilidad** de tu cluster.

ECS usa **container registries** (Docker Hub, donde se subió la image de container of cats, o ECR). Las tasks y los services usan images de los registries y, mediante las task definitions y service definitions, esas images se despliegan en los container hosts en forma de containers.

En EC2 mode, ECS gestiona algunas cosas (por ejemplo, la cantidad de tasks que se despliegan si usás services), pero **a nivel de cluster tenés que estar atento a la capacidad y administrarla vos**, porque las container instances no se entregan como un servicio managed: son solo instancias EC2.

> [!tip] Para el examen
> El **service auto scaling agrega o quita tasks, pero no instancias**. En EC2 mode, si las instancias no tienen CPU o memoria libre, las tasks nuevas **no tienen dónde ubicarse**. La capacidad del cluster se escala aparte, con un **capacity provider** asociado al ASG (**ECS cluster auto scaling**), que agrega o quita instancias según lo que necesiten las tasks.

#### Placement strategies y constraints

En EC2 mode también podés controlar cómo el placement engine elige la instancia para cada task:

| Tipo | Opción | Qué hace |
|---|---|---|
| **Placement strategy** | `binpack` | Llena cada instancia al máximo (según CPU o memoria) antes de usar otra → **menos instancias, más ahorro** |
| | `spread` | Reparte las tasks de forma pareja según un atributo, por ejemplo **entre AZs** → **HA** |
| | `random` | Las ubica al azar |
| **Placement constraint** | `distinctInstance` | Cada task en una **instancia distinta** |
| | `memberOf` | Limita las tasks a las instancias que cumplan una **expresión** (por ejemplo, un instance type o una AZ determinada) |

> [!tip] Para el examen
> En **Fargate no existen placement strategies ni constraints**: AWS decide dónde corre cada task y las reparte entre AZs.

#### Por qué EC2 mode es un punto medio

Si querés usar containers pero **necesitás sí o sí administrar la capacidad y la disponibilidad** de los container hosts, EC2 mode es para vos. Y como usa instancias EC2, si tu empresa tiene **Reserved Instances** podés aprovecharlas, o podés usar **Spot pricing**, pero todo eso lo tenés que gestionar vos.

En resumen: ECS como producto elimina gran parte del admin overhead de usar containers, pero en EC2 mode **conservás parte de ese overhead (y también algo de flexibilidad)**.

### Fargate mode

**Fargate mode** elimina todavía más el admin overhead: con Fargate **no tenés que administrar instancias EC2**.

Por mucho que al instructor no le guste el término _serverless_, Fargate es un **cluster model serverless**: no tenés servidores que administrar y, por eso, **no pagás por instancias EC2**, las estés usando o no.

#### Fargate shared infrastructure

El núcleo de la arquitectura es que AWS mantiene una plataforma compartida, la **Fargate shared infrastructure**, que se ofrece a todos los usuarios de Fargate. Así como EC2 aísla a los clientes entre sí, Fargate también lo hace: accedés a recursos de un pool compartido, del mismo modo que podés correr instancias EC2 en hardware compartido sin tener visibilidad de otros clientes.

Con Fargate usás las mismas task definitions y service definitions (image, puertos, recursos necesarios), pero en Fargate esos recursos se asignan (**allocated resources**) en la plataforma compartida.

#### Las tasks se inyectan en tu VPC

Seguís teniendo tu VPC: un deployment de Fargate igual usa un cluster, y el cluster usa una VPC que opera en AZs (en el ejemplo, AZ A y AZ B). La diferencia está en las tasks: **corren en la infraestructura compartida**, pero **desde el punto de vista de networking se inyectan en tu VPC**.

- Cada task recibe una **Elastic Network Interface (ENI)** con una dirección IP dentro de la VPC (ver [[06.14 Network Interfaces (ENI), IPs y DNS|ENI]]).
- A partir de ahí funcionan igual que cualquier otro recurso de la VPC: se puede acceder a ellas desde esa VPC, y también desde internet si la VPC está configurada para eso.
- Si la VPC usa **public subnets** que asignan automáticamente una IPv4 pública, las tasks y los services también pueden tener **direccionamiento IPv4 público**.

> [!tip] Idea clave
> Las tasks y los services **corren en la plataforma compartida de Fargate** y **se inyectan en tu VPC** a través de ENIs. Es a través de esas interfaces que se accede a ellas.

Fargate ofrece mucha personalización: podés desplegarlo en una VPC nueva o en una **custom VPC** que hayas diseñado.

#### Networking y cómo se conecta un ALB

Esto también cambia cómo se conecta un **ALB** a las tasks:

| Network mode | Dónde | Cómo lo ve el ALB |
|---|---|---|
| `awsvpc` | **Obligatorio en Fargate** (también disponible en EC2) | Cada task tiene **su propia ENI e IP** → el target group del ALB es de **tipo `ip`** y apunta directo a cada task |
| `bridge` | EC2 mode | **Dynamic port mapping**: si dejás el **host port en 0 (o vacío)** en el port mapping, Docker le asigna al container un **puerto efímero** en el host, y ECS registra la instancia con ese puerto en el target group automáticamente |

> [!tip] Para el examen
> Con `bridge` + dynamic port mapping, el **security group de las instancias** tiene que permitir el **rango de puertos efímeros** desde el security group del ALB. Ver [[05.07 VPC Security Groups (SGs)|VPC Security Groups]].

#### Costos de Fargate

Como las tasks y los services corren en la plataforma compartida, **solo pagás por los containers que usás, según los recursos que consumen**. No tenés visibilidad de costos de hosts, no necesitás administrar ni aprovisionar hosts, ni pensar en capacidad y disponibilidad: Fargate se encarga de todo eso.

Un matiz importante: en la práctica pagás por la **vCPU y la memoria que le asignás a la task en la task definition**, **por segundo** mientras corre, **aunque la app use menos**.

> [!tip] Para el examen
> Si la pregunta es sobre **bajar costos en Fargate**, la respuesta suele ser **ajustar el tamaño de la task (right-sizing)** o usar **Fargate Spot** para tasks que toleren interrupciones.

### EC2 mode vs Fargate mode

| | EC2 mode | Fargate mode |
|---|---|---|
| Dónde corren los containers | Container instances (EC2) en tu VPC, gestionadas por un ASG | Fargate shared infrastructure, inyectadas en tu VPC con una ENI |
| Admin overhead | Capacidad y disponibilidad de los hosts: **tuyas** | Ninguno sobre hosts |
| Serverless | No | Sí |
| Qué pagás | Las instancias EC2, **estén usadas o no** | vCPU + memoria asignadas a cada task, por segundo |
| Scaling de capacidad | Aparte, con capacity provider + ASG | No aplica |
| Placement strategies / constraints | Sí | No |
| Network mode | `awsvpc`, `bridge`, … | Solo `awsvpc` |
| Descuentos | Reserved Instances, Spot | Fargate Spot |
