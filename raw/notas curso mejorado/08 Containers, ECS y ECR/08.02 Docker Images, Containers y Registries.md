# Docker Images, Containers y Registries

### Image Anatomy

Empecemos por recordar qué es realmente una instancia EC2: es una **copia en ejecución de sus EBS volumes** (sus discos virtuales). Se arranca el **boot volume** de la instancia y, a partir de él, terminás con una copia en ejecución de un sistema operativo en un entorno virtualizado.

Un container no es diferente en este sentido: es una **copia en ejecución de una Docker image**. Pero las Docker images tienen algo especial, y es una de las razones por las que son tan buenas a nivel técnico: están formadas por varias **layers** (capas) independientes. Una Docker image es un **stack de layers**, no una única imagen de disco monolítica.

Las Docker images se crean a partir de un **Dockerfile**. Cada línea del Dockerfile se procesa **en orden, una por una**, y cada paso va creando **filesystem layers** dentro de la image resultante.

**Anatomía del Dockerfile del ejemplo** (una image con un web server adentro, listo para funcionar; el diagrama simplifica y muestra tres layers):

| Instrucción | Qué hace | Layer del diagrama |
|---|---|---|
| `FROM centos:7` | Define la **base image** (CentOS 7). Toda image se crea a partir de una base image o desde `scratch` (una image vacía). | Roja (`ab5ef0e58194`), la base sobre la que se apila todo |
| `MAINTAINER` y `LABEL` | Agregan metadata (quién mantiene la image, vendor, licencia y versión). | — |
| `RUN yum ... update && yum ... install httpd && yum clean all` | Actualiza los paquetes, instala Apache (`httpd`) y limpia la caché. Los tres comandos están encadenados con `&&` en **una sola** instrucción `RUN`, así que generan **una sola layer**. | Azul (`812de68fe4d8`) |
| `EXPOSE 80` | Indica que el container escucha en el puerto 80 (HTTP). | — |
| `ADD run-httpd.sh /run-httpd.sh` | Copia el script de arranque dentro de la image. | Verde (`573b4329b3b1`) |
| `RUN chmod -v +x /run-httpd.sh` | Le da permisos de ejecución al script. | — |
| `CMD ["/run-httpd.sh"]` | Define el comando que se ejecuta cuando arranca el container (levanta el web server). | — |

### Container Anatomy

Las Docker images son la forma en que creamos Docker containers. Un **Docker container** es simplemente una **copia en ejecución de una Docker image**, con una diferencia crucial: tiene una **filesystem layer adicional de lectura/escritura (R/W layer)**.

- Las layers que forman una Docker image son, por defecto, **read-only**: nunca cambian después de creadas.
- Por eso se agrega la **R/W layer**, que es lo que permite que los containers funcionen: todo lo que pase dentro del container (logs, datos que la aplicación genera o modifica) se guarda en la R/W layer.
- Cada layer es **diferencial**: guarda solo los cambios respecto a las layers de abajo. Todas juntas, apiladas, forman lo que el container ve como su filesystem.

Acá es donde los containers se vuelven realmente interesantes: podemos usar **la misma image** para crear otro container idéntico, con la única diferencia de que tiene **su propia R/W layer**. Eso es lo que mantiene a los containers separados y aislados. Y como las layers de la image son read-only, **los dos containers las comparten** y cada uno solo suma su propia R/W layer.

> [!tip] Idea clave
> _Shared fs layers = efficient_: N containers de la misma image comparten las layers read-only; lo único propio de cada uno es su R/W layer.

### Container Registry

Una vez creada una image, hace falta un lugar donde guardarla y desde donde distribuirla: para eso están los **container registries**.

**Flujo:** Dockerfile → **build** → container image → **push** al registry → cualquier **Docker host** hace **pull** y ejecuta containers a partir de ella.

Un registry guarda muchas images distintas, y cada host baja las que necesita. El ejemplo más conocido es **Docker Hub**, que es el que se usa en la [[08.03 Demostración - Container of cats (Docker en EC2)|demo]]. El registry de AWS es [[08.08 Elastic Container Registry (ECR)|ECR]].

### Container Key Concepts
- Los **Dockerfiles** se usan para hacer el **build de las images**.
- Los containers son **portables**: son self-contained, así que siempre corren como se espera.
- Son **livianos** (lightweight): usan el OS del host (parent OS) y **las fs layers se comparten**.
- Un container solo ejecuta **la aplicación y el entorno** que esa aplicación necesita.
- Brindan gran parte del **aislamiento** que dan las VMs.
- Los puertos se **exponen** (_exposed_) al host y, desde ahí, hacia afuera.
- Los application stacks pueden ser **multi-container**.
