# S3 — Simple Storage Service

## ¿Qué es?

**[[object-storage|Object storage]]** público, region-based y [[region-resilient]]: los objetos se replican entre las AZs de la region y no salen de ella salvo configuración explícita. Escala de cero a ilimitado. **No es file store ni block store**: no se monta como disco.

## Casos de uso

- Offload de contenido estático (imágenes, video) fuera de los servidores.
- Input/output de servicios AWS (logs, datasets, backups).
- Static website hosting, data lakes.

## Características clave

### Objects y Buckets

- **Object** = key (nombre) + value (0 bytes – **5 TB**) + version ID + metadata.
- **Estructura plana**: `old/koala.jpg` es una key con barras; las "carpetas" son ilusión de la consola ([[prefix|prefijos]]).
- Nombres de bucket: **únicos globalmente** (por DNS: `bucket.s3.amazonaws.com`), 3–63 chars, minúsculas, empiezan con letra/número, sin underscores, no formato IP; puntos permitidos pero rompen HTTPS wildcard (en la práctica: solo guiones). **100 buckets/cuenta** (soft, hasta 1.000). El **nombre es global aunque los datos sean regionales**.
- **[[durability|Durabilidad]] ≠ [[availability|disponibilidad]]**: durabilidad **11 nueves** (99.999999999% — "no se pierde") vs. disponibilidad **99.99%** en Standard ("puedo llegar a él ahora"). [[blast-radius|Blast radius]] de un bucket = la **region**.
- Límites: object máx **5 TB**; single PUT máx **5 GB** (más → [[multipart-upload|multipart]]); replicado en **≥3 AZs**.
- Consistencia: **strong read-after-write** para todas las operaciones (dato de examen — doc oficial; no es [[eventual-consistency|eventualmente consistente]]).
- **Cuatro tipos de bucket** (doc oficial): **general purpose** (el clásico, todo lo de esta página), **directory** (para S3 Express One Zone: single-AZ, latencia de milisegundos de un dígito, 100/cuenta, público jamás), **table** (Apache Iceberg para analytics) y **vector** (embeddings para ML). El examen básico asume general purpose.
- Escrituras concurrentes al mismo key: **last-writer-wins** (sin locking). Para evitar sobrescribir existe el **conditional write** `If-None-Match` en PUT/CompleteMultipartUpload.
- La **bucket policy tiene un máximo de 20 KB**; los objetos previos a habilitar versioning quedan con **version ID `null`**.

### Seguridad

**S3 es privado por defecto** — solo el account root user de la cuenta dueña tiene acceso inicial.

| Mecanismo | Cuándo usarlo |
|---|---|
| **Identity policies** | Administrar permisos desde IAM, misma cuenta |
| **Bucket policy** (resource, con [[principal|`Principal`]]) | Foco en el bucket, acceso **anónimo** o **[[cross-account]]** |
| **ACLs** | **Nunca** — legacy, deshabilitadas por default (Object Ownership "bucket owner enforced") |

La diferencia es de **perspectiva**: la identity policy responde *"¿qué puede hacer esta identidad?"*; la bucket policy, *"¿quién puede acceder a este recurso?"*. Y de eso salen dos capacidades que **solo** tiene la resource policy:

- Permite Allow/Deny a identidades de **otras cuentas** (la identity policy solo se administra dentro de la propia).
- Permite Allow/Deny a **principals anónimos** — acceso sin autenticar. Una identity policy no puede, por definición necesita una identidad a la que adjuntarse.

> **Truco de identificación:** ¿tiene campo `Principal`? → **resource policy**. ¿No lo tiene? → identity policy (el principal es implícito).

![[Pasted image 20260709012636.png]]

- Bucket policies con `Condition`: bloquear por IP (`NotIpAddress`), exigir MFA (`aws:MultiFactorAuthAge`), forzar HTTPS (`aws:SecureTransport`), exigir un método de cifrado (`s3:x-amz-server-side-encryption`).
- **Un bucket = una sola bucket policy** (con múltiples statements). Deny explícito gana ([[iam-policy-evaluation]]).

Los cuatro patrones de `Condition` que hay que reconocer:

```json
// Solo desde una IP: "Deny a todos, cuando la IP NO sea esta"
{ "Effect":"Deny", "Principal":"*", "Action":"s3:*",
  "Resource":"arn:aws:s3:::bucket/*",
  "Condition": {"NotIpAddress": {"aws:SourceIp":"1.3.3.7/32"}} }

// Exigir MFA solo en un prefijo — "Null: true" = la clave NO viene en la request
{ "Effect":"Deny", "Principal":"*", "Action":"s3:*",
  "Resource":"arn:aws:s3:::bucket/boris/*",
  "Condition": {"Null": {"aws:MultiFactorAuthAge": true}} }

// Forzar HTTPS — ojo: hacen falta LOS DOS ARNs (bucket y objetos)
{ "Effect":"Deny", "Principal":"*", "Action":"s3:*",
  "Resource":["arn:aws:s3:::bucket","arn:aws:s3:::bucket/*"],
  "Condition": {"Bool": {"aws:SecureTransport":"false"}} }

// Rechazar uploads que no vengan cifrados con KMS
{ "Effect":"Deny", "Principal":"*", "Action":"s3:PutObject",
  "Resource":"arn:aws:s3:::bucket/*",
  "Condition": {"StringNotEquals": {"s3:x-amz-server-side-encryption":"aws:kms"}} }
```

**ACLs — por qué murieron.** Es todo lo que pueden expresar: cinco permisos, **sin condiciones y sin Deny**.

| Permiso | Sobre el bucket | Sobre el objeto |
|---|---|---|
| `READ` | Listar objetos | Leer el objeto y su metadata |
| `WRITE` | Crear/sobrescribir/borrar cualquier objeto | *no aplica* |
| `READ_ACP` | Leer la ACL del bucket | Leer la ACL del objeto |
| `WRITE_ACP` | Modificar la ACL del bucket | Modificar la ACL del objeto |
| `FULL_CONTROL` | Los cuatro anteriores | READ + READ_ACP + WRITE_ACP |
- **Block Public Access**: barrera final contra buckets públicos por accidente; viene **activada por defecto** en buckets nuevos. Opciones "new" (**no empeorar** — frena config pública futura sin romper lo existente; se usa en migraciones) vs. "any" (**cerrar todo ya** — ignora incluso lo ya configurado; para un bucket que jamás debería ser público).
- ⚠️ BPA se interpone **solo entre los principals públicos/anónimos** y el bucket: **no afecta el acceso de identidades de AWS autenticadas**. Se configura a **nivel cuenta o bucket**, y el de **cuenta gana**: si está activo ahí, ningún bucket puede ser público aunque su config propia lo permita.

### El orden completo de evaluación en S3

Cuando llega una request, la decisión sale de combinar capas **en este orden**:

1. Si **Block Public Access** aplica y la request es pública/anónima → **denegado**, sin más.
2. Si hay un **Deny explícito** en cualquier policy (bucket policy, IAM, SCP) → **denegado**.
3. Si hay un **Allow explícito** en la bucket policy, en una IAM policy o en una ACL → **permitido**.
4. Si nada permite → **deny implícito**.

Para razonar los casos **cross-account**: hacen falta las **dos** puntas — que la cuenta dueña del bucket lo permita (bucket policy o ACL) **y** que la cuenta que accede se lo permita a su identidad (IAM policy).

![[Pasted image 20260709014142.png]]

Detalle de los **cuatro settings** de Block Public Access (doc oficial — se aplican a access point, bucket, cuenta u organización; gana siempre la **combinación más restrictiva**):

| Setting | Qué hace |
|---|---|
| `BlockPublicAcls` | **Rechaza** PUTs nuevos con ACL pública (las existentes no se tocan) |
| `IgnorePublicAcls` | **Ignora** todas las ACLs públicas existentes (los PUTs con ACL pública no fallan, solo no surten efecto) |
| `BlockPublicPolicy` | Rechaza `PutBucketPolicy` si la policy es pública — aplicarlo a nivel **cuenta** (a nivel bucket, quien edita la policy podría desactivarlo) |
| `RestrictPublicBuckets` | Bucket con policy pública → solo acceden principals de la cuenta dueña y service principals: **corta todo el cross-account**, incluso statements no-públicos de esa policy |

- Gotchas de BPA: **no modifica** policies ni ACLs existentes — al desactivar un setting, lo público vuelve a ser público. Una policy es "pública" salvo que restrinja con valores **fijos** (`aws:SourceVpc`, `aws:SourceIp` no demasiado amplio, principal concreto, etc.); `"Principal": "*"` sin condition la hace pública y un solo statement público **contamina toda la policy** para `RestrictPublicBuckets`. No existe BPA **por objeto**. A nivel organización se activan los 4 juntos (todo o nada, vía [[Organizations]]).
- **Condition keys de S3 útiles en policies** (doc oficial): `s3:x-amz-server-side-encryption` (exigir cifrado — ver [[s3-encryption]]), `s3:x-amz-copy-source` (restringir el origen de un copy), `s3:VersionId` (permitir GET de una versión concreta), `s3:prefix` (limitar `ListBucket` a un prefijo), `s3:max-keys` (limitar tamaño de listados), `s3:TlsVersion` (exigir TLS mínimo, ej. `NumericLessThan 1.2` en Deny), `aws:PrincipalAccount` (deny a todo el que no sea de la cuenta X). Gotcha fino: en Denies por red (`aws:SecureTransport`, `aws:SourceIp`) conviene excluir service principals con **`aws:PrincipalIsAWSService: false`** — en llamadas service-to-service ese contexto viene redactado y el Deny bloquearía a los propios servicios de AWS.

### Static Website Hosting

- Habilitarlo define **index document** (cuando no se pide una página puntual) y **error document**; crea un **website endpoint**.
- **Estático de verdad**: S3 sirve archivos tal cual y **no ejecuta código del lado del servidor** (nada de PHP, Node ni base de datos). La lógica dinámica corre en el navegador llamando a APIs. Si el escenario pide procesamiento server-side, S3 hosting **no alcanza**.
- Dominio propio vía [[Route53]] → **el bucket debe llamarse igual que el dominio**. La razón técnica: el nombre viaja en el header **`Host`** de la request, y S3 usa ese header para decidir a qué bucket enrutar. Si no existe un bucket con ese nombre exacto, no sabe qué servir.
- Casos de uso: **offloading** (assets estáticos fuera de los servidores de la app) y **páginas out-of-band** (mantenimiento/estado — siguen funcionando aunque tu infra esté caída, justamente porque S3 no depende de tus servidores).

**Los dos endpoints de un bucket** — se comportan distinto:

| Endpoint | Formato | Comportamiento |
|---|---|---|
| **REST API** | `bucket.s3.region.amazonaws.com` | El "normal": devuelve objetos, respeta permisos por objeto, errores en **XML** |
| **Website** | `bucket.s3-website-region.amazonaws.com` | Aplica index/error document, HTML de error amigable, **solo HTTP — no HTTPS** |

> **Causa #1 de "configuré el hosting y me da 403":** hacen falta **dos cosas a la vez** — desactivar **Block Public Access** en el bucket **y** una bucket policy que permita `s3:GetObject` a `"Principal": "*"`. Con una sola no alcanza.

### Versioning y MFA Delete

- Se controla a nivel bucket. Tres estados: **Unversioned (default) → Enabled → Suspended**. **Una vez habilitado, jamás vuelve a Disabled** — solo se suspende. Todas las versiones ocupan espacio y **se facturan**: cada versión es el **objeto completo**, no un diff (3 versiones = pagás 3 objetos).
- Al habilitar/suspender, los objetos existentes **no cambian** — cambia cómo S3 trata los requests futuros. Los previos al versioning quedan con version ID **`null`**.
- **`Suspended` en detalle**: no es "modo sin versiones", es "convive con las viejas pero no crea nuevas". Los objetos nuevos se guardan con ID `null`, así que si subís dos veces la misma key estando suspendido **la segunda sí pisa a la primera** (ambas son `null`) — pero cualquier versión con ID real anterior **sigue guardada debajo**.
- Delete sin version ID → **[[delete-marker]]** (borrado lógico, reversible; el marker pasa a ser la versión current). Delete **con** version ID → destrucción permanente.
- El delete marker **es en sí mismo una versión, con su propio version ID** → se borra como cualquier otra especificando ese ID, y eso es el **undelete**. **No tiene tamaño de datos**, así que casi no cuesta almacenamiento: lo que cuesta son las versiones que quedan debajo.
- 💸 **El costo oculto del versioning**: con versioning activado **nada se borra de verdad** salvo que lo hagas a propósito por version ID. Un bucket con archivos que se sobrescriben seguido (logs, exports diarios, imágenes reemplazadas) puede **pesar cinco veces lo que muestra la vista normal**. La solución no es apagar el versioning (no se puede) sino una **lifecycle rule que expire las versiones noncurrent** — es la combinación estándar: versioning para protección + regla que limpia.
- Gotcha de lifecycle (doc oficial): si un bucket sin versioning tenía una regla de **expiración** y habilitás versioning, para conservar el mismo comportamiento de borrado real hay que agregar una regla de **noncurrent expiration** (la expiración simple ahora solo crea delete markers).
- **MFA Delete**: exige MFA para (1) cambiar el **estado del versioning** del bucket y (2) **borrar permanentemente una versión**. Solo lo puede habilitar el **bucket owner (cuenta root)**, únicamente vía **CLI/API** (no consola): `put-bucket-versioning` con `MFADelete=Enabled` y `--mfa "serial código"` (se concatena el **número de serie del token + el código**) — vive en la misma subresource *versioning* del bucket. **Incompatible con lifecycle configurations**. No confundir con **MFA-protected API access** (condition `aws:MultiFactorAuthAge` en policies, para cualquier operación sensible).
- Por qué existe: aunque roben las credenciales de un admin, **sin el dispositivo MFA físico no puede destruir versiones ni apagar el versioning**. Contra: al pedir el token en **cada** borrado de versión, **rompe la automatización** (un script desatendido no tiene el código) → se reserva para buckets muy críticos donde el borrado es siempre manual y deliberado.

### Performance

- **Single PUT**: 1 stream, máx **5 GB**, si falla se reinicia todo.
- **[[multipart-upload|Multipart Upload]]**: partes de **5 MB–5 GB**, máx **10.000 partes**, reintento por parte, velocidad = suma de streams. Las herramientas lo activan solo desde ~100 MB. Regla: usarlo siempre que se pueda — **no hay situación donde un single PUT valga la pena por encima de 100 MB**. (Y 10.000 partes × 5 GB **es** de dónde sale el límite de 5 TB por objeto.)
- **Throughput por [[prefix|prefijo]]**: **3.500 PUT/COPY/POST/DELETE** y **5.500 GET/HEAD por segundo por prefijo**. Se escala repartiendo la carga entre varios prefijos (los prefijos determinan la performance; por eso `logs/2026/07/22/...`).
- **Transfer Acceleration**: sube vía la **[[edge-location|edge location]] más cercana** y viaja por la red privada de AWS. Requiere nombre de bucket **sin puntos** y DNS-compatible. Off por defecto.
  - Por qué ayuda: el ruteo de internet público está diseñado para **flexibilidad y resiliencia, no para velocidad** — el tráfico puede tomar caminos largos con muchos saltos entre proveedores. TA acorta el tramo público a lo mínimo y hace el resto por la red global de AWS.
  - ⚠️ La ganancia **depende de la distancia**: para un usuario en la **misma region** que el bucket **no aporta nada**. El escenario típico es usuarios globales subiendo a un bucket centralizado.

![[Pasted image 20260710070525.png]]

- Gotcha de costos: multipart incompletos se facturan invisibles → lifecycle rule `AbortIncompleteMultipartUpload`.
- Permisos multipart: iniciar/subir/completar usan `s3:PutObject`; abortar requiere `s3:AbortMultipartUpload` y listar partes `s3:ListMultipartUploadParts`.
- El **[[etag|ETag]] de un objeto multipart NO es el MD5** del contenido (es un checksum de checksums, con sufijo `-N`) — rompe verificaciones ingenuas de integridad.

### Replication (CRR / SRR)

- **CRR** (cross-region: resiliencia global, latencia) / **SRR** (misma region: agregación de logs, sync PROD→TEST, soberanía).
- Config en el bucket source + **IAM role** (trust: S3; permisos: leer source, escribir destination). Cross-account: bucket policy en el destination autorizando al rol.
- **Requisitos y gotchas** (examen): versioning en **ambos** buckets; **no retroactiva** por defecto (S3 Batch Replication para lo existente); one-way (existe opción bidireccional); **no** replica Glacier/Deep Archive ni delete markers (opt-in) ni cambios de lifecycle (**system events**: lo que mueve el lifecycle en el source no se replica, solo cambios de usuario); réplicas de réplicas no se re-replican (one-hop). **RTC** = [[sla|SLA]] de 15 min ($$).
- Un **DELETE con version ID en el source no se replica** (protección anti-borrado malicioso). Sí se replican objetos SSE-C/S3/KMS y la **retención de Object Lock**. El tráfico de replicación viaja **cifrado por SSL**.
- **Es asincrónica**: el PUT en el source responde apenas se guarda ahí y la copia ocurre después, en segundo plano. Sin RTC la mayoría se replica en segundos, pero **no hay garantía** — para eso existe RTC.
- **Conserva la metadata**: version ID, tags, ACLs, timestamps y config de cifrado se mantienen. La copia es **fiel al original**, no una versión "nueva".
- ⚠️ **Ownership**: por defecto los objetos replicados **pertenecen a la cuenta del source**. En cross-account eso significa que **la cuenta destino no puede leer sus propios objetos replicados** — hay que cambiar el owner al destino explícitamente.
- **Storage class en destino**: por defecto la misma que en origen; se puede elegir otra (ej. replicar a One Zone-IA para abaratar las copias — ver [[s3-storage-classes]]).
- El owner del bucket source **necesita permisos sobre los objetos**: si hay objetos subidos por otras cuentas de los que no es dueño, **no se replican**.

> Que los delete markers no se repliquen por defecto **es una protección**: evita que un borrado accidental o malicioso en el source destruya también la copia. Con `DeleteMarkerReplication` sí se copian, pero **el version delete real nunca se replica** — borrar una versión concreta en el source jamás borra la del destino. Eso hace de la réplica un buen respaldo contra borrados.

### Presigned URLs

Acceso temporal a un objeto **con las credenciales de quien genera la URL**. El server de la app la genera y el cliente descarga directo del bucket (offload sin hacer nada público). Sirve para GET y PUT.

![[Pasted image 20260717143553.png]]

Las tres trampas de examen:
1. Podés generar una URL para un objeto al que **no tenés acceso** (se genera igual; falla al usarla).
2. Los permisos evaluados son los del generador **al momento del uso**, no de la generación.
3. **No generarlas con un rol**: la URL muere cuando expiran las credenciales temporales (máx 7 días con IAM user + SigV4).

**Qué es por dentro** (explica todas sus propiedades): la URL normal del objeto **+ query params** con las credenciales del generador, un timestamp, la validez y una **firma criptográfica SigV4** de todo eso. S3 recalcula la firma y verifica que nadie alteró los parámetros → **no se puede "editar" la URL** para apuntar a otro objeto o extender su vida. Y por eso tampoco hace falta que el generador esté online cuando se usa: **toda la autorización viaja dentro de la URL**.

El caso de **upload** es igual de útil: el servidor genera una [[presigned-url|presigned URL]] de tipo **PUT** y el usuario sube **directo al bucket**, sin que el archivo pase por el servidor de la app. Es el patrón estándar de los formularios de carga en aplicaciones serverless.

Expiración por origen (doc oficial): consola **1 min–12 h**; CLI/SDK hasta **7 días**; con credenciales de instance role ~6 h, con AssumeRole ~1 h. La bucket policy puede rechazar firmas viejas con la condition **`s3:signatureAge`**.

> 💥 **El dolor de cabeza recurrente**: presigned URLs generadas **desde una Lambda** (que corre con un rol) "se vencen antes de tiempo". La vida real de la URL es **el menor** entre su propia expiración y la de las credenciales que la firmaron — y las de un rol suelen ser de 1 hora.

### CORS

Seguridad **del navegador**, no permisos AWS. El origin = **esquema + dominio + puerto**; basta que uno difiera para ser cross-origin (`http://` vs `https://`, `catagram.io` vs `www.catagram.io`, vs `:8080`). Las cross-origin requests requieren que **el otro origen** las permita vía config JSON (`AllowedOrigins/Methods/Headers`). Requests complejas → **preflight `OPTIONS`** previo, cacheado por `Access-Control-Max-Age`.

> ⚠️ **CORS lo impone el navegador, no S3.** `curl`, Postman o un script del lado del servidor **lo ignoran por completo** — pueden pedir lo que quieran. CORS solo entra en juego cuando **JavaScript de una página** pide un recurso de otro origen. Es la confusión más común del tema.
>
> Y **no son permisos** ("*these AREN'T permissions*"): CORS le dice al navegador qué está permitido; los permisos reales los siguen definiendo bucket policy / IAM. Hacen falta **las dos cosas**.

Por qué existe: sin same-origin, una página maliciosa podría usar el JS de tu navegador para pegarle a tu banco **aprovechando tu sesión abierta**. CORS es el mecanismo controlado para hacer excepciones cuando el dueño del otro dominio da permiso explícito. Corolario: **tu origin siempre te permite; son los demás los que tienen que aprobarte**.

Las reglas del JSON se procesan **en orden y se aplica la primera que coincide**:

```json
[
  { "AllowedMethods": ["PUT","POST","DELETE"], "AllowedOrigins": ["http://catagram.io"],
    "AllowedHeaders": ["*"], "ExposeHeaders": [] },
  { "AllowedMethods": ["GET"], "AllowedOrigins": ["*"],
    "AllowedHeaders": [], "ExposeHeaders": [] }
]
```

| Header de respuesta | Qué le dice al navegador |
|---|---|
| **`Access-Control-Allow-Origin`** | Desde qué orígenes se acepta. Si el tuyo no está, **bloquea la respuesta**. Es el header central |
| **`Access-Control-Allow-Methods`** | Qué métodos HTTP se permiten (↔ `AllowedMethods`) |
| **`Access-Control-Allow-Headers`** | Qué headers custom puede llevar la request (↔ `AllowedHeaders`) |
| **`Access-Control-Max-Age`** | Cuántos segundos se cachea el resultado del preflight |
| **`Access-Control-Allow-Credentials`** | Si la request puede llevar cookies/credenciales. ⚠️ **No se puede combinar `true` con `Allow-Origin: *`** — con credenciales hay que nombrar un origin concreto |

**Qué dispara preflight:** una request es "simple" (y va directo) si usa solo `GET`/`HEAD`/`POST` con headers y content-types básicos. En cuanto aparece `PUT`, `DELETE` o headers custom, el navegador manda primero un `OPTIONS`. Por eso los GET de imágenes "simplemente funcionan" y los PUT de subida casi siempre preflightean.

**Cómo se reconoce un problema de CORS:** la consola dice *"blocked by CORS policy: No 'Access-Control-Allow-Origin' header"* y en la pestaña de red hay un `OPTIONS` que falló **antes** de la request real. El síntoma que lo confirma: **funciona si abrís el recurso directo en el navegador** (eso es same-origin) **pero falla desde el JavaScript**. Si ves ese patrón, es CORS, no permisos.

### S3 Select y Glacier Select

Consultar **partes de un objeto** con una expresión estilo SQL que se ejecuta **del lado de S3** (server-side filter): en vez de bajar un objeto de 5TB y filtrar en el cliente, S3 entrega solo lo filtrado (hasta 400% más rápido, 80% más barato). Formatos: CSV, JSON, Parquet, BZIP2.

> Nota: AWS marcó S3 Select como legacy para clientes nuevos; para consultar **datasets enteros** la herramienta es **Athena**. Aun así el concepto "filtrar server-side vs client-side" sigue cayendo en el examen.

### Event Notifications / EventBridge

- Eventos del bucket → **SNS, SQS, Lambda**. SQS **FIFO no soportado**. Cuidado con loops (bucket → Lambda → mismo bucket).

| Categoría | Eventos | Uso típico |
|---|---|---|
| **Object Created** | Put, Post, Copy, CompleteMultiPartUpload | Se sube una imagen → Lambda genera el thumbnail |
| **Object Delete** | `*`, Delete, DeleteMarkerCreated | Auditar o reaccionar a borrados |
| **Object Restore** | Post (Initiated), Completed | Avisar cuando un restore de Glacier inicia y cuando termina |
| **Replication** | OperationMissedThreshold, OperationReplicatedAfterThreshold, OperationNotTracked, OperationFailedReplication | Monitorear la salud de la replicación (RTC) |

> ⚠️ **Lo que más falla al configurarlo:** no alcanza con elegir la cola o la función como destino — **el destino tiene que autorizar a S3**. En SQS es una policy de la cola con `"Principal": {"Service": "s3.amazonaws.com"}`; en Lambda es una resource-based policy que se agrega con `AddPermission`. **Si falta, la notificación se pierde en silencio.**
- Entrega **at least once** (puede duplicar) y normalmente en segundos, pero puede demorar más de un minuto — diseñar consumidores **[[idempotency|idempotentes]]**.
- **[[EventBridge]] es el default moderno**: más eventos, más destinos, mejores filtros.

### Access Logs

- Source bucket → target bucket. Mecanismo clásico (el del curso): el S3 Log Delivery Group escribe en el target **vía ACL** — una de las pocas features que aún las usa. **Best-effort**, horas de delay.
- La doc actual configura esto vía **`PutBucketLogging`** y agrega un destino moderno: entrega directa a **CloudWatch Logs**.
- El lifecycle de los logs es responsabilidad tuya (lifecycle rules en el target).
- El target bucket debe estar en la **misma region y misma cuenta** que el source, y cifrado con **SSE-S3** (no SSE-KMS).

### Requester Pays

Config **por bucket** (`Payer=Requester`): quien descarga paga el transfer-out. Requiere requesters **autenticados** (no funciona con website hosting ni acceso anónimo) + header `x-amz-request-payer`. Caso de uso: datasets públicos enormes.

### Access Points, Object Lambda y Batch Operations

- **Access Points**: "puertas de entrada" con nombre, **policy propia** y config de red propia (se pueden restringir a una VPC) para datasets compartidos — evitan que la bucket policy crezca sin control. Tienen su propio Block Public Access.
- **Object Lambda**: inyecta una Lambda en los GET/HEAD/LIST para **transformar la respuesta al vuelo** (filtrar filas, redimensionar imágenes, redactar datos sensibles) sin duplicar los datos.
- **Batch Operations**: opera sobre **miles de millones de objetos** con un job (Copy, Invoke Lambda, Restore, tagging, ACLs, retención de Object Lock, cambiar SSE). Es la vía para **re-cifrar retroactivamente** objetos existentes (Copy in-place) — recordar que cambios de cifrado/bucket keys nunca son retroactivos por sí solos.

Detalles de Access Points (doc oficial — caen en DVA):

- **Solo operaciones de objetos** (`GetObject`/`PutObject`…); no sirven para operaciones de bucket (borrar bucket, configurar replication) ni como **destino de replication**.
- **Doble llave**: para acceder a través de un access point deben permitirlo **la access point policy Y la bucket policy**. Patrón recomendado — la bucket policy **delega** todo el control a los access points con la condition `s3:DataAccessPointAccount` (Allow `*` si el AP es de la cuenta X). En **cross-account** el dueño del bucket siempre retiene el control: crear el AP apuntando a un bucket ajeno no da acceso hasta que el dueño autorice en su bucket policy.
- **Límites y reglas**: 1 access point ↔ 1 bucket (inmutable); **10.000 por cuenta por region** (soft); policy máx **20 KB**; nombre único por cuenta+region (3–50 chars, DNS-compliant, sin `_` ni mayúsculas, no termina en `-s3alias`); el **network origin (Internet/VPC) y el BPA se fijan al crear y NO se pueden cambiar**; **solo HTTPS**; **sin acceso anónimo**; solo direccionamiento **virtual-hosted-style** con **SigV4**.
- **Tres formas de referenciarlo**: ARN `arn:aws:s3:region:cuenta:accesspoint/nombre` (objetos: `.../accesspoint/nombre/object/key`) · **alias** autogenerado `nombre-xxxxxxxx-s3alias` (se usa como si fuera un bucket name en operaciones de **data plane**, sin tocar código) · URI virtual-hosted `https://nombre-cuenta.s3-accesspoint.region.amazonaws.com`. Limitaciones del alias: **no** sirve en IAM policies, ni para control plane, ni como destino de access logs / CloudTrail.
- **Condition keys**: `s3:DataAccessPointArn`, `s3:DataAccessPointAccount`, `s3:AccessPointNetworkOrigin` (ej: SCP que exige `VPC` para todo `CreateAccessPoint`). Un AP con origen **VPC nunca es público**.
- **Monitoreo**: los eventos de [[CloudTrail]] hechos vía AP incluyen el ARN del access point en `resources`; las **CloudWatch request metrics** (opt-in, pagas, 1 min) pueden filtrarse por access point.

Detalles de Batch Operations: un **job** ejecuta **una** operación sobre los objetos de un **manifest** (S3 Inventory report o CSV, o autogenerado por filtros); cada llamada individual es una **task**. Default hasta **4 mil millones** de objetos por job (Copy/Tagging/Object Lock/Lambda/Batch Replication llegan a 20 mil millones). Genera **completion report** auditable. Se factura por job **aunque lo canceles**.

### Object Lock (WORM)

Almacenamiento inmutable ([[worm|WORM]]). Se habilita en **buckets nuevos** (activa versioning; **irreversible**) — para activarlo en un bucket **existente** hay que **contactar al soporte de AWS**. Bloquea **versiones individuales**: no delete, no overwrite. Que lo bloqueado sean versiones y no "el objeto" es coherente con el versioning: se pueden seguir subiendo versiones nuevas de la misma key, cada una con su propio candado.

| Mecanismo | Duración | ¿Bypass? |
|---|---|---|
| **Compliance** | Días/años | ❌ **Nadie**, ni root, hasta expirar |
| **Governance** | Días/años | ✅ `s3:BypassGovernanceRetention` + header |
| **Legal Hold** | ON/OFF indefinido | ✅ con `s3:PutObjectLegalHold` |

Detalles de la doc: fijar retención requiere `s3:PutObjectRetention`; la bucket policy puede acotar los períodos con la condition **`s3:object-lock-remaining-retention-days`**. Comportamiento HTTP: DELETE **con** version ID sobre versión bloqueada → **403**; DELETE simple → **200 + delete marker** (el lock no lo impide). En Compliance, la única salida antes de expirar es **cerrar la cuenta de AWS**.

- **Compliance no tiene salida de emergencia.** Si pusiste 7 años por error, **pagás su almacenamiento 7 años**: no hay permiso, header, ticket de soporte ni root user que lo saltee. Esa imposibilidad total es justamente lo que lo hace válido ante un auditor.
- En **Governance**, el header `x-amz-bypass-governance-retention:true` es **el default de la consola** — operando desde la consola con el permiso concedido el bypass se aplica solo; por API/CLI hay que incluirlo explícitamente.
- **Legal Hold no vence**: queda hasta que alguien con `s3:PutObjectLegalHold` lo saca a mano. Encaja con el caso que le da nombre: cuando arranca un litigio hay que preservar documentos, pero **nadie sabe cuánto dura el juicio**, así que una fecha fija no sirve.
- **Se combinan**: una misma versión puede tener retention en Governance **y** legal hold. Mientras **cualquiera** de los dos esté activo, el objeto no se borra — aunque expire el período, si el legal hold sigue puesto, sigue protegido.

Cómo elegir en un escenario: *"un regulador exige que no se puedan borrar por X años pase lo que pase"* → **Compliance**. *"Evitar borrados accidentales pero poder corregir con autorización"* → **Governance**. *"Juicio en curso, preservar por tiempo indeterminado"* → **Legal Hold**.

## Gotchas y trampas del examen

- "Montar S3 como filesystem compartido" → ❌, eso es EFS. S3 = objetos vía API.
- Bucket policy correcta que "no funciona" → falta el par de [[arn|ARNs]] (bucket + `/*`).
- Versioning suspendido ≠ versiones borradas: se siguen cobrando.
- "Detectar cambios en tiempo real" → S3 Events/EventBridge, no [[CloudTrail]] (15 min de delay).
- Lifecycle: mínimo 30 días antes de transicionar a IA; objetos chicos pagan mínimos (**128 KB** en IA/One Zone-IA/Glacier Instant) y en Glacier Flexible/Deep cada objeto suma **~40 KB de overhead de metadata**.
